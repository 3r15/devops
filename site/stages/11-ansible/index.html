예상 14시간 완료

이 단계를 끝내면

  • 빈 서버를 애플리케이션이 도는 상태로 만드는 과정을 코드로 적을 수 있다.

  • 환경별 차이를 변수와 템플릿으로 처리할 수 있다.
  • 비밀을 저장소에 넣지 않고 플레이북에 전달할 수 있다.

준비물

  • Ansible을 돌릴 머신(제어 노드) 하나. 파이썬만 있으면 된다.
  • 대상 서버 하나 이상. 없으면 localhost나 Stage 7의 컨테이너로 연습한다.
  • Stage 1에서 만든 SSH 키 인증. Ansible은 SSH로 동작한다.
python3 -m venv ~/.venvs/ansible && source ~/.venvs/ansible/bin/activate
pip install ansible-core ansible-lint
ansible --version

💡 에이전트가 없다는 것

Ansible은 대상 서버에 아무것도 설치하지 않는다. SSH로 접속해 파이썬 모듈을 보내 실행하고 결과를 받아 온 뒤 지운다. 그래서 "관리 대상"으로 만들기 위한 준비가 없다 — SSH로 들어갈 수 있으면 그것으로 끝이다. 이 단순함이 Ansible이 널리 쓰이는 이유다.

1. Terraform과의 경계

Stage 10을 마치면 자연스럽게 드는 질문이다. 둘 다 "인프라를 코드로" 아닌가? 경계는 이렇다.

TerraformAnsible
다루는 것자원을 만든다 (VM, 네트워크, DB)서버 안을 설정한다 (패키지, 파일, 서비스)
대상클라우드 APISSH로 접속한 OS
상태 추적state 파일없음 — 매번 현재를 확인한다
비유집을 짓는다집 안에 가구를 놓는다

흔한 조합은 Terraform으로 서버를 만들고, Ansible로 그 안을 채우는 것이다. Ansible로 클라우드 자원을 만들 수도 있고 Terraform에서 스크립트를 실행할 수도 있지만, 각자 잘하는 쪽에 두는 편이 낫다.

💡 컨테이너를 쓰면 Ansible이 덜 필요해진다

Stage 7에서 본 대로, 컨테이너 이미지 자체가 "무엇이 설치되어 있는가"를 고정한다. 그래서 쿠버네티스 위주의 환경에서는 Ansible의 역할이 줄어든다. 다만 클러스터 자체를 만드는 노드, 데이터베이스 서버, 네트워크 장비, 온프레미스 서버는 여전히 누군가 설정해야 하고 거기가 Ansible의 자리다.

2. 인벤토리

어떤 서버들을 관리하는지 적는 파일이다.

# inventory.yml
all:
  children:
    web:
      hosts:
        web01:
          ansible_host: 10.0.1.11
        web02:
          ansible_host: 10.0.1.12
      vars:
        app_port: 8000

    db:
      hosts:
        db01:
          ansible_host: 10.0.2.21

  vars:
    ansible_user: deploy
    ansible_ssh_private_key_file: ~/.ssh/id_ed25519
ansible-inventory -i inventory.yml --list       # 파싱 결과 확인
ansible-inventory -i inventory.yml --graph
ansible web -i inventory.yml -m ping            # 연결 확인

그룹으로 묶으면 "web 그룹 전체에" 같은 지정이 가능해진다. 그룹은 중첩할 수 있고, 한 호스트가 여러 그룹에 속할 수도 있다.

3. 애드혹 명령

플레이북을 쓰기 전에, 한 번만 실행하고 싶을 때 쓴다.

ansible all -i inventory.yml -m ping
ansible web -i inventory.yml -m command -a "uptime"
ansible web -i inventory.yml -m apt -a "name=nginx state=present" --become
ansible all -i inventory.yml -m setup            # 수집된 사실(facts) 전부 보기

--become이 sudo에 해당한다. Stage 1에서 배운 대로 필요한 작업에만 붙인다.

-m setup이 보여주는 facts는 대상 서버에서 수집한 정보다 — OS 종류, 메모리, IP, 디스크. 플레이북 안에서 ansible_facts로 참조해 "우분투면 apt, 로키면 dnf" 같은 분기를 만든다.

4. 플레이북

여러 작업을 순서대로 적은 YAML이다. weatherboard가 돌 서버를 만들어 보자.

# site.yml
- name: weatherboard 실행 환경 구성
  hosts: web
  become: true

  vars:
    app_user: weatherboard
    app_dir: /opt/weatherboard
    app_port: 8000

  tasks:
    - name: 필요한 패키지 설치
      ansible.builtin.apt:
        name:
          - python3
          - python3-venv
          - nginx
        state: present
        update_cache: true
        cache_valid_time: 3600

    - name: 애플리케이션 사용자 생성
      ansible.builtin.user:
        name: "{{ app_user }}"
        system: true
        shell: /usr/sbin/nologin
        home: "{{ app_dir }}"

    - name: 애플리케이션 디렉터리
      ansible.builtin.file:
        path: "{{ app_dir }}"
        state: directory
        owner: "{{ app_user }}"
        group: "{{ app_user }}"
        mode: "0755"

    - name: systemd 유닛 배치
      ansible.builtin.template:
        src: templates/weatherboard.service.j2
        dest: /etc/systemd/system/weatherboard.service
        mode: "0644"
      notify: restart weatherboard

    - name: 서비스 활성화
      ansible.builtin.systemd_service:
        name: weatherboard
        enabled: true
        state: started
        daemon_reload: true

  handlers:
    - name: restart weatherboard
      ansible.builtin.systemd_service:
        name: weatherboard
        state: restarted
        daemon_reload: true
ansible-playbook -i inventory.yml site.yml --syntax-check
ansible-playbook -i inventory.yml site.yml --check --diff    # 드라이런
ansible-playbook -i inventory.yml site.yml

💡 --check --diff 를 먼저 돌린다

Terraform의 plan에 해당한다. 실제로 바꾸지 않고 무엇이 바뀔지 보여준다. --diff를 함께 주면 파일 내용의 차이까지 보여준다. 완벽하지는 않다 — 앞 작업의 결과에 의존하는 뒤 작업은 정확히 예측하지 못한다. 그래도 프로덕션에 돌리기 전 습관으로 삼을 값어치가 있다.

5. 멱등성 — 이 단계의 핵심

몇 번을 돌려도 결과가 같아야 한다. 이것이 Ansible의 설계 원칙이고, 플레이북이 스크립트와 다른 결정적 이유다.

PLAY RECAP ****************************************************
web01 : ok=5  changed=5  unreachable=0  failed=0    ← 첫 실행
web01 : ok=5  changed=0  unreachable=0  failed=0    ← 두 번째 (이래야 정상)

두 번째 실행에서 changed=0이 나오는 것이 목표다. changed가 계속 나온다면 그 작업이 멱등하지 않은 것이고, 핸들러가 매번 서비스를 재시작해 불필요한 다운타임을 만든다.

대부분의 모듈은 멱등하다. 깨뜨리는 것은 대개 command와 shell이다.

# 멱등하지 않다 — 매번 실행되고 매번 changed
- name: 압축 해제
  ansible.builtin.shell: tar xzf /tmp/app.tar.gz -C /opt

# 멱등하다 — 전용 모듈은 상태를 확인한다
- name: 압축 해제
  ansible.builtin.unarchive:
    src: /tmp/app.tar.gz
    dest: /opt
    remote_src: true
    creates: /opt/app/bin/run          # 이 파일이 있으면 건너뛴다
피할 것대신 쓸 것
shell: apt install ...ansible.builtin.apt
shell: mkdir -p ...ansible.builtin.file
shell: echo ... >> filelineinfile / blockinfile
shell: systemctl restart ...systemd_service + 핸들러
shell: git clone ...ansible.builtin.git

정말 command를 써야 한다면 조건을 붙여 멱등하게 만든다.

- name: 초기화 스크립트 (한 번만)
  ansible.builtin.command: /opt/app/init.sh
  args:
    creates: /opt/app/.initialized      # 이 파일이 있으면 실행하지 않는다

- name: 상태를 확인하고 필요할 때만
  ansible.builtin.command: /usr/bin/app-migrate
  register: migrate
  changed_when: "'applied' in migrate.stdout"
  failed_when: migrate.rc != 0 and 'already' not in migrate.stderr

changed_when과 failed_when이 중요하다. Ansible은 command가 성공하면 무조건 changed로 본다. 실제로 무언가 바뀌었을 때만 changed가 되도록 우리가 알려 줘야 한다.

6. 변수와 템플릿

변수는 여러 곳에서 올 수 있고 우선순위가 있다(뒤가 이긴다).

  1. group_vars/all.yml — 전체 기본값
  2. group_vars/web.yml — 그룹별
  3. host_vars/web01.yml — 호스트별
  4. 플레이북의 vars:
  5. -e "key=value" — 명령행 (가장 강함)
ansible-playbook -i inventory.yml site.yml -e "app_port=9000"

Jinja2 템플릿

# templates/weatherboard.service.j2
[Unit]
Description=weatherboard
After=network.target

[Service]
Type=simple
User={{ app_user }}
WorkingDirectory={{ app_dir }}
Environment=HOST=127.0.0.1
Environment=PORT={{ app_port }}
ExecStart={{ app_dir }}/.venv/bin/python -m weatherboard.app
Restart=on-failure

[Install]
WantedBy=multi-user.target

Stage 4에서 손으로 쓰던 systemd 유닛이 여기서 템플릿이 된다. 환경마다 다른 값만 변수로 빼면 파일 하나로 모든 환경을 덮는다.

# 조건과 반복
- name: 우분투에서만
  ansible.builtin.apt:
    name: nginx
  when: ansible_facts['os_family'] == "Debian"

- name: 여러 디렉터리 생성
  ansible.builtin.file:
    path: "{{ item }}"
    state: directory
  loop:
    - /opt/app/logs
    - /opt/app/config

7. 핸들러

핸들러는 무언가 실제로 바뀌었을 때만 실행되는 작업이다. 설정 파일이 바뀌었을 때만 서비스를 재시작하는 데 쓴다.

  tasks:
    - name: nginx 설정 배치
      ansible.builtin.template:
        src: templates/weatherboard.conf.j2
        dest: /etc/nginx/sites-available/weatherboard
      notify: reload nginx        # 바뀌었을 때만 알린다

  handlers:
    - name: reload nginx
      ansible.builtin.systemd_service:
        name: nginx
        state: reloaded

Stage 6에서 배운 reload와 restart의 차이가 여기서 그대로 쓰인다. 설정 변경에는 reload다.

⚠ 핸들러는 플레이 끝에 한 번만 실행된다

다섯 작업이 같은 핸들러를 notify해도 한 번만 돈다. 좋은 설계다. 다만 그래서 플레이 중간에 서비스를 재시작해야 하는 경우에는 맞지 않는다. 그럴 때는 meta: flush_handlers로 그 자리에서 실행시킬 수 있다.

    - name: 여기까지의 핸들러를 지금 실행
      ansible.builtin.meta: flush_handlers

8. 롤

플레이북이 길어지면 롤로 나눈다. Terraform의 모듈과 같은 발상이다.

roles/
└── weatherboard/
    ├── tasks/main.yml
    ├── handlers/main.yml
    ├── templates/weatherboard.service.j2
    ├── files/
    ├── defaults/main.yml      # 가장 낮은 우선순위 기본값
    ├── vars/main.yml          # 높은 우선순위 값
    └── meta/main.yml          # 의존 롤
# site.yml
- name: 웹 서버 구성
  hosts: web
  become: true
  roles:
    - common
    - weatherboard
    - nginx

디렉터리 구조가 정해져 있어서 tasks/main.yml, handlers/main.yml은 자동으로 읽힌다. templates/와 files/의 경로도 자동으로 잡혀 상대 경로를 적을 필요가 없다.

ansible-galaxy init roles/weatherboard      # 구조를 만들어 준다
ansible-galaxy install -r requirements.yml # 남의 롤 가져오기

9. Vault — 비밀 다루기

DB 비밀번호나 API 키를 플레이북에 평문으로 둘 수는 없다. ansible-vault가 파일을 암호화한다.

ansible-vault create group_vars/prod/vault.yml     # 새로 만들기
ansible-vault edit group_vars/prod/vault.yml       # 수정
ansible-vault view group_vars/prod/vault.yml       # 보기
ansible-vault encrypt existing.yml                 # 기존 파일 암호화

ansible-playbook site.yml --ask-vault-pass
ansible-playbook site.yml --vault-password-file ~/.vault-pass    # CI에서

암호화된 파일은 Git에 커밋해도 된다 — 그것이 목적이다. 암호만 저장소 밖에 둔다.

💡 변수 이름은 밖에, 값만 안에

vault 파일 안의 변수를 직접 참조하면, 그 변수가 어디서 오는지 알기 어려워진다. 관례는 vault에 vault_db_password로 넣고, 평문 파일에서 db_password: "{{ vault_db_password }}"로 연결하는 것이다. 그러면 어떤 비밀이 쓰이는지는 보이고 값만 감춰진다.

⚠ vault는 만능이 아니다

암호 하나로 모든 비밀이 풀린다. 그 암호를 아는 사람은 전부를 안다. 규모가 커지면 클라우드의 시크릿 관리 서비스나 HashiCorp Vault(이름이 같지만 다른 것)로 옮기고, Ansible은 그것을 조회만 하게 만든다. Stage 14의 주제다.

자주 하는 실수

두 번째 실행에도 changed가 나온다

PLAY RECAP ****
web01 : ok=8  changed=3  ...        ← 두 번째 실행인데 3개가 바뀌었다?

멱등하지 않은 작업이 있다는 뜻이다. -v로 어느 작업인지 찾는다. 범인은 대개 command/shell이거나, 매번 내용이 달라지는 템플릿(타임스탬프를 넣었다든지)이다. 핸들러가 매번 돌아 서비스가 매번 재시작되고 있으니 반드시 고쳐야 한다.

Failed to connect to the host via ssh

fatal: [web01]: UNREACHABLE! => {"msg": "Failed to connect to the host via ssh:
Permission denied (publickey)."}

Stage 1의 그 에러가 그대로 나온다. Ansible을 의심하기 전에 SSH로 직접 붙어 본다.

ssh -i ~/.ssh/id_ed25519 deploy@10.0.1.11        # 이게 되면 Ansible 설정 문제
ansible web -i inventory.yml -m ping -vvv        # 어떤 명령을 실행하는지 다 보여준다

sudo: a password is required

fatal: [web01]: FAILED! => {"msg": "Missing sudo password"}

become: true를 썼는데 대상 사용자가 비밀번호 없는 sudo가 아닌 것이다. --ask-become-pass(-K)로 물어보게 하거나, 대상 서버의 sudoers를 설정한다.

변수가 정의되지 않았다

fatal: [web01]: FAILED! => {"msg": "The task includes an option with an
undefined variable. The error was: 'app_port' is undefined"}

변수 이름 오타이거나, 있어야 할 group_vars 파일이 그 호스트에 적용되지 않은 것이다. 무엇이 실제로 보이는지 확인한다.

ansible web01 -i inventory.yml -m debug -a "var=hostvars[inventory_hostname]"

기본값이 있어야 하는 변수는 defaults/main.yml에 두거나 {{ app_port | default(8000) }}로 방어한다.

플레이북이 느리다

서버가 늘어나면 눈에 띄게 느려진다. 세 가지가 효과가 크다.

# ansible.cfg
[defaults]
forks = 20                    # 동시에 몇 대씩 (기본 5)
gathering = smart             # facts를 매번 다시 모으지 않는다

[ssh_connection]
pipelining = True             # SSH 왕복 횟수를 줄인다

필요 없는 플레이에서는 gather_facts: false로 아예 끌 수도 있다. facts 수집은 서버마다 수 초씩 걸린다.

직접 해보기

과제 1 — localhost로 시작하기

서버가 없어도 된다. localhost를 대상으로 디렉터리를 만들고 템플릿에서 파일을 렌더링하는 플레이북을 쓴다.

ansible-playbook -i localhost, -c local site.yml

검증: --syntax-check가 통과하는가. --check --diff가 만들려는 파일의 내용을 보여주는가.

과제 2 — 멱등성 확인

이 과제가 이 단계의 핵심이다. 과제 1의 플레이북을 두 번 연속 실행한다.

ansible-playbook -i localhost, -c local site.yml | tail -3
ansible-playbook -i localhost, -c local site.yml | tail -3

그다음 일부러 shell: mkdir -p /tmp/x 같은 작업을 넣어 changed가 계속 나오게 만들고, creates:나 전용 모듈로 고친다.

검증: 두 번째 실행이 changed=0인가. 멱등하지 않던 작업을 어떻게 고쳤는지 설명할 수 있는가.

과제 3 — weatherboard 배포 플레이북

빈 서버(또는 Stage 7의 우분투 컨테이너)를 weatherboard가 도는 상태로 만든다. 패키지 설치 → 사용자 생성 → 코드 배치 → 가상환경 → systemd 유닛 → 서비스 시작.

검증: 깨끗한 서버에서 한 번에 성공하는가. 두 번째 실행이 changed=0인가. curl localhost:8000/healthz가 응답하는가.

과제 4 — 핸들러가 필요할 때만 도는지

템플릿을 notify로 핸들러에 연결하고, (1) 아무것도 안 바꾸고 실행, (2) 템플릿 변수를 바꾸고 실행 두 경우를 비교한다.

검증: 1번에서 핸들러가 실행되지 않고, 2번에서만 실행되는가. 이것이 왜 중요한지(불필요한 재시작 = 다운타임) 설명할 수 있는가.

과제 5 — vault로 비밀 감추기

API 키를 vault 파일에 넣고 플레이북에서 참조한다. 파일을 cat해서 실제로 암호화됐는지 확인하고, Git에 커밋해도 되는지 판단한다.

검증: cat했을 때 평문이 안 보이는가. --ask-vault-pass 없이 실행하면 실패하는가. vault 암호 자체는 어디에 뒀는가(저장소 밖이어야 한다).
