1. 컨테이너가 푸는 문제

Stage 6까지 weatherboard는 서버 한 대에 손으로 설치되어 있다. 파이썬 버전, 가상환경, requirements, systemd 유닛, Nginx 설정. 다른 서버에 올리려면 이걸 전부 다시 한다. 그리고 한 단계라도 다르면 "제 컴퓨터에선 되는데요"가 시작된다.

컨테이너는 애플리케이션과 그것이 필요로 하는 모든 것을 하나의 이미지로 묶는다. 그 이미지는 내 노트북에서든 CI에서든 프로덕션에서든 같은 파일이다.

가상 머신컨테이너
격리 대상하드웨어부터프로세스와 파일시스템
커널각자 따로호스트 커널을 공유
시작 시간수십 초수십 밀리초
크기GB수십~수백 MB

커널을 공유한다는 점이 핵심이다. 가볍고 빠른 이유이자, VM만큼 강한 격리는 아니라는 한계이기도 하다. 리눅스 컨테이너는 리눅스에서만 돈다(맥/윈도우의 Docker는 내부에 작은 리눅스 VM을 띄운다).

2. 이미지와 컨테이너 다루기

이미지는 설계도, 컨테이너는 그것을 실행한 인스턴스다. 같은 이미지로 컨테이너를 여러 개 띄울 수 있다.

docker run -d --name web -p 8080:80 nginx:1.27-alpine
#          ^  ^            ^         ^
#          |  |            |         이미지:태그
#          |  |            호스트:8080 → 컨테이너:80
#          |  이름을 붙인다
#          배경 실행

docker ps                 # 도는 컨테이너
docker ps -a              # 멈춘 것까지
docker logs -f web        # 로그 따라가기
docker exec -it web sh    # 안으로 들어가기
docker stop web && docker rm web

⚠ latest 태그를 쓰지 않는다

nginx:latest는 "지금 최신"이라는 움직이는 이름표다. 어제 빌드한 이미지와 오늘 빌드한 이미지가 조용히 달라져서, 재현이 불가능해지고 원인 모를 장애가 난다. nginx:1.27-alpine처럼 버전을 고정하자. 프로덕션이라면 다이제스트 (nginx@sha256:...)까지 고정하는 것이 가장 안전하다.

docker images                 # 로컬 이미지 목록
docker pull python:3.12-slim
docker rmi <이미지>
docker system df              # 디스크를 얼마나 쓰고 있나
docker system prune -a        # 안 쓰는 이미지/컨테이너/네트워크 정리 (주의)

Stage 1의 "디스크가 찼다"가 도커 쓰는 서버에서는 대개 여기다. docker system df가 첫 확인 지점이다.

3. 레이어와 캐시

이미지는 레이어의 스택이다. Dockerfile의 각 명령이 레이어 하나를 만들고, 내용이 바뀌지 않은 레이어는 캐시에서 재사용된다. 이 규칙 하나가 빌드 속도를 좌우한다.

# 나쁜 순서 — 코드 한 줄만 고쳐도 pip install을 다시 한다
COPY . /app
RUN pip install -r /app/requirements.txt

# 좋은 순서 — 의존성이 안 바뀌면 pip install은 캐시된다
COPY requirements.txt /app/
RUN pip install -r /app/requirements.txt
COPY . /app

규칙은 자주 바뀌는 것을 뒤로다. 의존성 목록은 가끔 바뀌고 소스는 매번 바뀌니, 의존성 설치를 먼저 두면 대부분의 빌드에서 그 레이어를 건너뛴다. 한 레이어가 무효화되면 그 아래 전부가 다시 실행된다는 점을 기억하자.

docker history <이미지>      # 레이어별 크기 — 무엇이 이미지를 키웠나

💡 지운 파일은 사라지지 않는다

레이어는 쌓이기만 한다. 한 레이어에서 만든 파일을 다음 레이어에서 rm해도 앞 레이어에는 그대로 남아 이미지 크기에 포함된다. 그래서 정리는 같은 RUN 안에서 한다.

RUN apt-get update && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*

비밀도 마찬가지다. 빌드 중 COPY한 키를 나중에 지워도 이미지 안에 남는다. Stage 3의 "커밋한 비밀은 이력에 남는다"와 같은 함정이다.

4. Dockerfile 쓰기

weatherboard의 첫 Dockerfile이다.

# weatherboard/Dockerfile
FROM python:3.12-slim

WORKDIR /app

# 의존성 먼저 — 캐시가 잘 듣도록
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# 그다음 소스
COPY weatherboard/ ./weatherboard/

# root로 돌지 않는다
RUN useradd --create-home --uid 10001 app
USER app

ENV HOST=0.0.0.0 PORT=8000
EXPOSE 8000

CMD ["python", "-m", "weatherboard.app"]

HOST=0.0.0.0이 여기서 필요한 이유가 Stage 2·5·6에서 쌓아 온 것이다. 컨테이너 안에서 127.0.0.1에 바인딩하면 그 컨테이너 안에서만 접근 가능하고, 포트 매핑으로도 밖에서 닿지 않는다. 컨테이너는 이미 격리되어 있으므로 0.0.0.0이 맞다.

명령하는 일주의
FROM기반 이미지버전을 고정한다
WORKDIR작업 디렉터리 (없으면 생성)RUN cd는 다음 줄에 이어지지 않는다
COPY호스트 → 이미지ADD는 URL·압축 해제까지 해서 예측이 어렵다. COPY를 쓴다
RUN빌드 시점에 실행레이어가 하나 생긴다
ENV환경변수이미지에 박힌다 — 비밀은 넣지 않는다
EXPOSE문서용 표시포트를 열지 않는다. 여는 건 -p
CMD기본 실행 명령docker run 뒤 인자로 덮인다
ENTRYPOINT항상 실행되는 부분CMD가 그 인자가 된다

.dockerignore

# weatherboard/.dockerignore
.git
.venv
__pycache__
*.pyc
tests/
.env
README.md

COPY . .는 이 목록을 뺀 나머지를 넣는다. .venv를 빼는 것만으로도 이미지가 수백 MB 줄고 빌드가 빨라진다. .git과 .env는 보안상 반드시 뺀다.

docker build -t weatherboard:0.1 .
docker run --rm -p 8000:8000 weatherboard:0.1
curl localhost:8000/healthz

헬스체크

HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
  CMD python -c "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/healthz')" || exit 1

Stage 5에서 만든 /healthz가 처음으로 쓰이는 곳이다. docker ps의 STATUS에 (healthy)가 표시된다. Stage 8의 쿠버네티스 프로브가 같은 경로를 다시 쓴다.

5. 멀티스테이지 빌드

빌드에 필요한 것(컴파일러, 개발 헤더)과 실행에 필요한 것은 다르다. 멀티스테이지는 빌드 결과물만 최종 이미지로 옮긴다.

FROM python:3.12-slim AS builder

WORKDIR /app
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt


FROM python:3.12-slim

RUN useradd --create-home --uid 10001 app
COPY --from=builder /opt/venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH" HOST=0.0.0.0 PORT=8000

WORKDIR /app
COPY weatherboard/ ./weatherboard/
USER app
EXPOSE 8000
CMD ["python", "-m", "weatherboard.app"]

빌드 도구가 최종 이미지에 남지 않는다. 이미지가 작아지는 것도 이득이지만, 공격 표면이 줄어드는 것이 더 큰 이득이다 — 컴파일러가 없는 이미지에서는 침입자가 할 수 있는 일이 적다. Stage 14에서 이 이야기를 이어간다.

기반 이미지대략 크기특징
python:3.12~1GB빌드 도구 포함. 개발용
python:3.12-slim~150MB대부분의 경우 적당한 선택
python:3.12-alpine~60MBmusl libc — C 확장 패키지가 빌드에 실패하기도 한다
gcr.io/distroless/python3~50MB셸조차 없다. 가장 안전하지만 디버깅이 어렵다

⚠ alpine이 항상 작고 빠른 것은 아니다

alpine은 musl libc를 쓴다. 파이썬 패키지 중 미리 빌드된 wheel이 glibc용만 있는 경우가 많아, alpine에서는 소스에서 컴파일하느라 빌드가 몇 배 느려지고 이미지도 커질 수 있다. 크기를 재보지 않고 alpine부터 고르지 말자. slim으로 시작하는 편이 무난하다.

6. 볼륨 — 데이터를 지키기

컨테이너의 파일시스템은 컨테이너와 함께 사라진다. 남아야 하는 데이터는 밖에 둬야 한다.

# 이름 있는 볼륨 — Docker가 관리한다. DB 데이터에 적합
docker volume create pgdata
docker run -d --name db -v pgdata:/var/lib/postgresql/data postgres:16

# 바인드 마운트 — 호스트의 특정 경로. 설정 파일이나 개발 중 소스에 적합
docker run --rm -v "$PWD/nginx.conf:/etc/nginx/nginx.conf:ro" nginx:1.27-alpine

docker volume ls
docker volume inspect pgdata

:ro는 읽기 전용이다. 설정 파일을 넣을 때는 붙이는 습관을 들이자 — 컨테이너가 호스트 파일을 고치는 사고를 막는다.

💡 어느 쪽을 쓰나

이름 있는 볼륨은 데이터가 목적일 때(DB, 업로드 파일). Docker가 위치를 관리하고 백업 도구와도 잘 맞는다. 바인드 마운트는 호스트의 특정 파일이 목적일 때 (설정 주입, 개발 중 소스 실시간 반영). 프로덕션에서 바인드 마운트를 쓰면 호스트 경로에 의존하게 되어 이식성이 떨어진다.

7. 네트워크

docker network create wb-net
docker run -d --name api --network wb-net weatherboard:0.1
docker run --rm --network wb-net curlimages/curl:8.10.1 curl -s http://api:8000/healthz

같은 사용자 정의 네트워크에 있는 컨테이너는 이름으로 서로를 찾는다. Docker가 내부 DNS를 제공하기 때문이다. IP를 알 필요가 없고, 컨테이너가 재시작되어 IP가 바뀌어도 상관없다. Stage 8의 Service가 하는 일이 정확히 이것의 확장판이다.

드라이버동작
bridge (기본)격리된 사설 네트워크. 이름 해석 제공
host호스트 네트워크를 그대로 씀. 격리 없음, 포트 매핑 불필요
none네트워크 없음

기본 bridge 네트워크(docker run에 --network를 안 줬을 때)에서는 이름 해석이 되지 않는다. 컨테이너끼리 통신해야 한다면 반드시 네트워크를 만들어 붙이자.

8. Compose

컨테이너가 둘 이상이 되면 docker run 명령이 길어지고 기억할 수 없게 된다. Compose는 그것을 파일로 적는다.

# compose.yaml
services:
  app:
    build: .
    environment:
      HOST: 0.0.0.0
      PORT: "8000"
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "python", "-c",
             "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/healthz')"]
      interval: 30s
      timeout: 3s
      retries: 3

  proxy:
    image: nginx:1.27-alpine
    ports:
      - "80:80"
    volumes:
      - ./nginx/weatherboard.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      app:
        condition: service_healthy
    restart: unless-stopped

Nginx 설정은 Stage 6의 것을 거의 그대로 쓰되, proxy_pass의 대상만 컨테이너 이름으로 바꾼다.

# nginx/weatherboard.conf
server {
    listen 80;
    location / {
        proxy_pass http://app:8000;      # ← 서비스 이름으로 찾는다
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
    location /healthz {
        proxy_pass http://app:8000/healthz;
        access_log off;
    }
}
docker compose up -d --build
docker compose ps
docker compose logs -f app
curl localhost/healthz
docker compose down            # 컨테이너와 네트워크 제거 (볼륨은 남는다)
docker compose down -v         # 볼륨까지 제거

💡 depends_on만으로는 부족하다

depends_on은 기본적으로 "컨테이너가 시작됐는가"만 본다. DB가 뜨는 데 10초 걸리는데 앱이 즉시 붙으려 하면 실패한다. 위처럼 condition: service_healthy와 healthcheck를 함께 써야 "준비됐는가"를 기다린다. 그래도 애플리케이션은 재시도 로직을 갖는 게 맞다 — Stage 8에서는 재시작이 일상이 된다.

9. 컨테이너 디버깅

docker logs --tail 50 -f <컨테이너>      # 첫 번째 확인 지점
docker exec -it <컨테이너> sh            # 안에서 둘러보기
docker inspect <컨테이너>                 # 설정 전체 (마운트, 네트워크, 환경변수)
docker stats                              # 실시간 CPU/메모리
docker top <컨테이너>                     # 안에서 도는 프로세스

컨테이너가 즉시 죽어서 exec가 안 될 때는 이렇게 한다.

docker run --rm -it --entrypoint sh weatherboard:0.1   # CMD를 무시하고 셸로 진입
docker logs <죽은-컨테이너-ID>                          # 죽은 것도 로그는 남아 있다

💡 로그는 stdout/stderr로 낸다

컨테이너 안에서 파일로 로그를 쓰면 docker logs에 안 보이고, 컨테이너가 사라질 때 함께 사라진다. Stage 4·5에서 정한 "stdout은 결과, stderr는 말"이 여기서 구조적 요구사항이 된다. Stage 13의 로그 수집도 이 전제 위에 선다.

자주 하는 실수

포트를 매핑했는데 접속이 안 된다

docker run -d -p 8000:8000 weatherboard:0.1
curl localhost:8000
# curl: (56) Recv failure: Connection reset by peer

컨테이너 안에서 애플리케이션이 127.0.0.1에 바인딩된 것이다. Stage 2에서 본 문제가 컨테이너 안에서 반복된다 — 컨테이너의 127.0.0.1은 그 컨테이너 자신일 뿐이라 포트 매핑이 닿지 못한다.

docker exec <컨테이너> ss -lntp     # 안에서 확인 (ss가 없으면 로그의 listening 줄을 본다)
# LISTEN 127.0.0.1:8000   ← 이러면 밖에서 절대 안 된다

애플리케이션이 0.0.0.0에 바인딩하도록 HOST를 준다.

코드를 고쳤는데 컨테이너에 반영되지 않는다

이미지는 빌드 시점의 스냅샷이다. 호스트의 파일을 고쳐도 이미 만들어진 이미지는 바뀌지 않는다. 다시 빌드해야 한다.

docker compose up -d --build      # 빌드 후 재생성
docker build --no-cache -t app .  # 캐시를 완전히 무시하고 (원인을 모를 때)

개발 중이라면 소스를 바인드 마운트해 매번 빌드하지 않을 수 있다. 다만 그건 개발 전용이고, 배포 이미지는 반드시 소스를 COPY로 담아야 한다.

Permission denied — 볼륨 안의 파일에

docker run -v "$PWD/data:/data" -u 10001 myapp
# PermissionError: [Errno 13] Permission denied: '/data/out.txt'

바인드 마운트한 호스트 디렉터리의 소유자 UID와 컨테이너 안 사용자의 UID가 다른 것이다. 컨테이너는 이름이 아니라 숫자 UID로 권한을 판단한다. 호스트 쪽 소유권을 맞춘다.

sudo chown -R 10001:10001 ./data

이미지가 너무 크다

docker images weatherboard
# weatherboard  0.1  a1b2c3  1.2GB      ← 파이썬 앱치고 너무 크다

docker history weatherboard:0.1     # 어느 레이어가 범인인가

흔한 원인 셋이다. .dockerignore가 없어 .venv와 .git이 통째로 들어갔거나, slim이 아닌 기반 이미지를 썼거나, apt-get install 후 캐시를 지우지 않은 것이다.

디스크가 가득 찼다

docker system df
# TYPE          TOTAL   ACTIVE  SIZE     RECLAIMABLE
# Images        47      3       28.4GB   26.1GB (91%)
# Build Cache   312     0       9.8GB    9.8GB

빌드를 반복하면 중간 이미지와 캐시가 쌓인다. Stage 1의 "디스크가 찼다"가 도커 서버에서 나타나는 형태다.

docker system prune              # 안 쓰는 컨테이너/네트워크/dangling 이미지
docker system prune -a --volumes # 전부 (볼륨까지 — 데이터가 사라진다. 확인하고 쓸 것)
docker builder prune             # 빌드 캐시만

직접 해보기

과제 1 — weatherboard 컨테이너화

Dockerfile과 .dockerignore를 쓰고 이미지를 만든다. root로 돌지 않게 하고 HEALTHCHECK를 넣는다.

검증: docker run --rm -p 8000:8000 후 /healthz가 응답하는가. docker exec <c> id가 root가 아닌가. docker ps의 STATUS에 (healthy)가 뜨는가.

과제 2 — 캐시를 눈으로 확인하기

이 과제가 이 단계의 핵심이다. Dockerfile을 두 버전으로 만든다 — COPY . .를 먼저 하는 것과, requirements.txt를 먼저 하는 것. 각각에서 소스 한 줄만 고치고 재빌드하며 시간을 잰다.

time docker build -t wb:bad -f Dockerfile.bad .
echo "# touch" >> weatherboard/app.py
time docker build -t wb:bad -f Dockerfile.bad .     # 두 번째 빌드

검증: 좋은 순서 쪽 재빌드에서 CACHED 표시가 나오고 시간이 확연히 짧은가. 몇 배 차이인가.

과제 3 — 이미지 줄이기

과제 1의 이미지를 멀티스테이지로 바꾸고 크기를 비교한다. docker history로 어느 레이어가 컸는지 확인한다.

검증: 최종 이미지가 200MB 이하인가. 줄어든 이유를 레이어별로 설명할 수 있는가. 이미지 안에 pip이나 컴파일러가 남아 있지 않은지 확인했는가.

과제 4 — Compose로 Nginx와 함께 띄우기

Stage 6의 Nginx 설정을 컨테이너 이름 기반으로 바꿔 Compose로 묶는다. 앱 컨테이너는 포트를 밖으로 열지 않고, Nginx만 80을 연다.

검증: curl localhost/는 되고 curl localhost:8000/은 안 되는가. docker compose down && up -d 후에도 그대로 동작하는가.

과제 5 — 데이터가 살아남는지 확인

이름 있는 볼륨을 붙인 컨테이너에서 파일을 만들고, 컨테이너를 rm한 뒤 새 컨테이너에서 그 파일이 있는지 본다. 볼륨 없이 같은 실험을 반복해 차이를 확인한다.

검증: 볼륨을 붙였을 때만 파일이 남는가. docker compose down과 down -v의 차이를 직접 확인했는가.
