1. 파일시스템 — 지도부터

리눅스에는 드라이브 문자가 없다. 모든 것이 /(루트) 하나에서 뻗어 나온 한 그루의 나무다. 디스크를 하나 더 붙여도 D:가 생기지 않고 /mnt/data 같은 디렉터리에 얹힌다(마운트).

운영에서 실제로 자주 들어가는 곳은 몇 군데뿐이다.

경로무엇이 있나언제 열게 되나
/etc시스템 설정 파일서비스 설정을 고칠 때
/var/log로그장애의 대부분은 여기서 시작한다
/var/lib서비스가 쓰는 데이터(DB 파일 등)디스크가 찼을 때
/home/<user>사용자 홈. ~로 줄여 쓴다늘
/usr/bin, /bin설치된 명령어 실행 파일명령을 못 찾을 때
/opt배포판 패키지 밖에서 설치한 소프트웨어수동 설치한 것을 찾을 때
/tmp임시 파일. 재부팅하면 사라질 수 있다중요한 것을 두면 안 되는 곳
/proc커널이 만드는 가짜 파일들(프로세스 정보)디스크를 차지하지 않는다

돌아다니기

pwd                 # 지금 어디인가
ls -lah /etc        # 자세히(-l), 숨김 포함(-a), 사람이 읽는 크기(-h)
cd /var/log
cd -                # 직전 위치로 되돌아가기
cd                  # 인자 없이 치면 홈(~)

경로에는 두 가지가 있다. /로 시작하면 절대 경로(어디서 치든 같은 곳), 아니면 현재 위치 기준의 상대 경로다. .은 현재 디렉터리, ..은 한 단계 위다.

찾기

find /etc -name "*.conf"              # 이름으로
find /var/log -type f -size +100M    # 100MB보다 큰 파일
find /home -mtime -1                 # 최근 하루 안에 수정된 것

which nginx                          # 이 명령의 실행 파일은 어디에 있나
type cd                              # 셸 내장 명령인가 실행 파일인가

💡 모르는 명령을 만났을 때

man find로 매뉴얼을 열고 /를 눌러 검색, q로 나온다. 매뉴얼이 길어서 버겁다면 find --help가 요약본이다. 이 두 개를 쓰는 습관이 이 단계에서 얻어갈 가장 오래 쓰는 기술이다.

2. 텍스트를 다루는 도구

유닉스의 설계 철학은 "작은 도구를 파이프로 잇는다"이다. 파이프 |는 왼쪽 명령의 출력을 오른쪽 명령의 입력으로 넘긴다. 이 하나를 익히면 나머지는 조합이다.

보기

cat /etc/hostname          # 짧은 파일 통째로
less /var/log/syslog       # 긴 파일을 스크롤하며 (q로 종료, /로 검색)
head -n 20 access.log      # 앞 20줄
tail -n 50 access.log      # 뒤 50줄
tail -f /var/log/syslog    # 새로 쌓이는 줄을 실시간으로 (Ctrl+C로 종료)

거르기와 세기

grep "error" /var/log/syslog             # 이 단어가 든 줄만
grep -i "error" /var/log/syslog          # 대소문자 무시
grep -c "error" /var/log/syslog          # 몇 줄인지만
grep -rn "listen" /etc/nginx/            # 디렉터리 전체를 줄번호와 함께

# 조합: 오늘 로그에서 error를 뽑아 개수 세기
grep "error" /var/log/syslog | wc -l

자르고 세우고 묶기

# 접속이 많은 IP 상위 10개 — 파이프라인의 전형적인 모양
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head -10
#   IP만 뽑고    → 정렬  → 중복을 세고 → 많은 순  → 위 10줄

cut -d: -f1 /etc/passwd    # : 로 나눠 첫 번째 칸(사용자 이름)만

바꾸기

sed 's/8080/9090/' app.conf         # 화면에만 바꿔 출력 (파일은 그대로)
sed -i.bak 's/8080/9090/' app.conf # 파일을 직접 수정, app.conf.bak으로 백업

⚠ sed -i 는 되돌릴 수 없다

-i는 파일을 그 자리에서 덮어쓴다. 확장자를 붙인 -i.bak 형태로 백업을 남기는 습관을 들이자. 설정 파일을 바꿀 때는 먼저 -i 없이 실행해 결과를 눈으로 확인하는 것이 안전하다.

출력 방향 바꾸기

ls -l > files.txt          # 덮어쓰기
ls -l >> files.txt         # 이어붙이기
command 2> errors.txt      # 에러(stderr)만 따로
command > out.txt 2>&1     # 출력과 에러를 한곳에

프로그램은 보통 두 갈래로 말한다. 정상 출력(stdout, 1번)과 에러(stderr, 2번)다. 파이프 |는 기본적으로 1번만 넘긴다. 에러가 파이프를 타지 않는다면 이것이 이유다.

3. 권한과 소유권

ls -l의 첫 열이 권한이다. 이걸 읽을 줄 알면 "왜 안 되지"의 절반이 풀린다.

ls -l /etc/shadow
# -rw-r----- 1 root shadow 1.4K Aug 25 09:12 /etc/shadow
#  ^^^ ^^^ ^^^   ^     ^
#   |   |   |    |     └ 그룹
#   |   |   |    └ 소유자
#   |   |   └ 나머지 모든 사용자(others): 아무 권한 없음
#   |   └ 그룹(shadow): 읽기만
#   └ 소유자(root): 읽기+쓰기

맨 앞 한 글자는 종류다. -는 일반 파일, d는 디렉터리, l은 심볼릭 링크다.

기호숫자파일에서디렉터리에서
r4내용을 읽는다목록을 본다(ls)
w2내용을 고친다안에 파일을 만들거나 지운다
x1실행한다안으로 들어간다(cd)

디렉터리의 x가 헷갈리는 지점이다. r만 있고 x가 없으면 파일 이름은 보이는데 그 안으로 들어가지도, 내용을 읽지도 못한다.

바꾸기

chmod 640 secrets.env      # 소유자 rw-, 그룹 r--, 나머지 ---
chmod +x deploy.sh         # 실행 권한 추가
chmod -R 755 /var/www      # 디렉터리 아래 전부 (-R은 재귀)

chown deploy:deploy app.log       # 소유자와 그룹을 함께
chown -R deploy /var/www/app

숫자는 r=4, w=2, x=1을 더한 것이다. 640은 소유자 4+2=6, 그룹 4, 나머지 0이라는 뜻이다. 자주 쓰는 조합은 644(일반 파일), 755(실행 파일과 디렉터리), 600(비밀 파일) 정도다.

⚠ chmod 777 은 해결책이 아니다

권한 문제를 만나면 777(모두에게 모든 권한)로 뚫고 싶어진다. 그러면 그 서버의 아무 프로세스나 그 파일을 고칠 수 있게 된다. 설정 파일이나 키 파일에 이걸 하면 그 순간 보안이 사라진다. 대신 누가 이 파일에 접근해야 하는지를 정하고 소유자나 그룹을 맞춰라.

sudo

sudo systemctl restart nginx   # 이 명령만 관리자 권한으로
sudo -u deploy whoami          # 특정 사용자로 실행
sudo -i                        # 관리자 셸로 진입 (오래 머물지 말 것)

sudo는 필요한 명령 하나에만 붙인다. 습관적으로 sudo -i로 들어가 작업하면, 실수 하나가 시스템 전체에 닿는다.

4. 프로세스와 시그널

실행 중인 프로그램 하나가 프로세스다. 각각 번호(PID)를 갖는다.

ps aux                       # 지금 도는 모든 프로세스
ps aux | grep nginx          # 그중 nginx만
pgrep -a nginx               # 같은 일을 더 깔끔하게

top                          # 실시간 (q로 종료)
top -o %MEM                  # 메모리 많이 쓰는 순으로

ps aux의 열 중 실제로 보는 것은 몇 개다. PID(번호), %CPU, %MEM, STAT(상태), 그리고 마지막의 COMMAND(무엇을 어떤 인자로 실행했는지)다.

멈추기

kill 1234              # 정중히 종료 요청 (SIGTERM). 기본값
kill -HUP 1234         # 설정을 다시 읽어라 (많은 데몬이 지원)
kill -9 1234           # 강제 종료 (SIGKILL). 마지막 수단
pkill -f "python app.py"   # 명령줄로 찾아서

⚠ -9 를 먼저 쓰지 않는다

SIGTERM(기본)은 "정리하고 끝내라"이고, 프로그램은 이때 열린 파일을 닫고 쓰던 데이터를 저장한다. -9는 그 기회를 주지 않고 즉시 죽인다. 데이터베이스나 쓰기 중인 프로세스에 -9를 쓰면 손상된 파일이 남을 수 있다. 먼저 kill, 몇 초 기다려도 안 죽으면 그때 -9다.

배경으로 돌리기

./long-job.sh &            # 배경 실행
jobs                       # 이 셸의 배경 작업 목록
fg %1                      # 앞으로 가져오기
Ctrl+Z                     # 실행 중인 것을 일시 정지 → bg 로 배경 전환

nohup ./long-job.sh &      # 로그아웃해도 계속 (출력은 nohup.out으로)

다만 실제 서비스를 이렇게 띄우지는 않는다. 그건 systemd의 일이다.

5. 패키지 관리

소프트웨어를 소스에서 빌드하지 않고 배포판 저장소에서 받아 설치한다.

sudo apt update                  # 저장소 목록 갱신 (설치 전 항상)
sudo apt install nginx           # 설치
apt search nginx                 # 검색
apt show nginx                   # 버전, 의존성, 설명
sudo apt remove nginx            # 제거 (설정 파일은 남김)
sudo apt purge nginx             # 설정까지 제거
sudo apt upgrade                 # 설치된 것 전체 업그레이드

dpkg -l | grep nginx             # 설치된 패키지 목록에서 찾기
dpkg -L nginx                    # 이 패키지가 어떤 파일을 깔았나

💡 apt update 와 apt upgrade 는 다르다

update는 "저장소에 무엇이 있는지 목록만 새로 받는다"이고, upgrade가 실제로 패키지를 올린다. update 없이 install하면 오래된 목록을 보고 없는 버전을 받으려다 실패하는 경우가 있다.

하는 일Debian/UbuntuRHEL/Rocky/Alma
목록 갱신apt updatednf check-update
설치apt install Xdnf install X
제거apt remove Xdnf remove X
검색apt search Xdnf search X
어느 패키지의 파일인가dpkg -S /pathrpm -qf /path

6. 서비스와 systemd

서버에서 계속 떠 있어야 하는 프로그램(웹 서버, DB, 에이전트)은 systemd가 관리한다. 부팅 시 자동 시작, 죽으면 재시작, 로그 수집이 전부 여기에 묶여 있다.

systemctl status nginx        # 지금 상태 — 가장 많이 치게 될 명령
sudo systemctl start nginx
sudo systemctl stop nginx
sudo systemctl restart nginx  # 껐다 켜기
sudo systemctl reload nginx   # 무중단으로 설정만 다시 읽기 (지원하는 경우)

sudo systemctl enable nginx   # 부팅 시 자동 시작 켜기
sudo systemctl disable nginx
systemctl is-enabled nginx

systemctl list-units --type=service --state=running   # 지금 도는 서비스 전부
systemctl --failed                                    # 실패한 것만

systemctl status의 출력에서 볼 곳은 세 군데다.

systemctl status nginx
# ● nginx.service - A high performance web server
#      Loaded: loaded (/lib/systemd/system/nginx.service; enabled; ...)
#      Active: active (running) since Mon 2026-08-25 09:12:03 UTC; 2h ago
#    Main PID: 1234 (nginx)
#
# Aug 25 09:12:03 web01 systemd[1]: Started A high performance web server.
  • Loaded 끝의 enabled/disabled — 부팅 시 자동 시작 여부.
  • Active — active (running)이면 정상, failed면 죽은 것, inactive (dead)면 그냥 꺼져 있는 것.
  • 맨 아래 몇 줄 — 최근 로그. 여기서 원인이 바로 보이는 경우가 많다.

유닛 파일

서비스의 정의는 /etc/systemd/system/(직접 만든 것)이나 /lib/systemd/system/(패키지가 설치한 것)에 있다.

systemctl cat nginx           # 이 서비스의 유닛 파일 내용 보기
sudo systemctl edit nginx     # 원본을 건드리지 않고 덮어쓰기 조각 추가

sudo systemctl daemon-reload  # 유닛 파일을 고쳤다면 반드시

⚠ 유닛 파일을 고치고 daemon-reload 를 빼먹는 실수

systemd는 유닛 파일을 메모리에 올려 두고 쓴다. 파일만 고치고 systemctl restart를 하면 고치기 전 내용으로 재시작된다. "분명히 고쳤는데 안 먹는다"의 대부분이 이것이다. 순서는 항상 편집 → daemon-reload → restart다.

7. 로그 읽기

로그는 두 곳에 있다. systemd가 모으는 저널과, 프로그램이 직접 쓰는 /var/log 아래의 파일이다.

journalctl -u nginx                    # 이 서비스의 로그만
journalctl -u nginx -f                 # 실시간으로 따라가기
journalctl -u nginx --since "10 min ago"
journalctl -u nginx --since today -p err   # 에러 이상만
journalctl -b                          # 이번 부팅 이후 전체
journalctl -b -1                        # 직전 부팅 (갑자기 재부팅됐을 때)

tail -f /var/log/nginx/error.log       # 파일로 쓰는 로그는 이렇게

-p는 심각도다. err, warning, info 순으로 범위가 넓어진다. 장애를 볼 때는 -p err로 좁혔다가 필요하면 넓히는 편이 빠르다.

💡 로그가 통째로 사라졌다면

logrotate가 오래된 로그를 압축하고 지운다. /var/log에 syslog.1, syslog.2.gz처럼 번호가 붙은 파일이 그것이다. 압축된 것은 zgrep으로 바로 검색할 수 있다.

8. 디스크와 메모리

df -h                  # 파일시스템별 사용량
df -i                  # inode 사용량 (아래 설명)
du -sh /var/log        # 이 디렉터리가 차지하는 총량
du -h --max-depth=1 /var | sort -h    # 어느 하위 디렉터리가 큰지 한 눈에

free -h                # 메모리
uptime                 # 가동 시간과 부하(load average)

디스크가 찼을 때의 순서

df -h                                  # 1. 어느 파일시스템이 찼나
du -h --max-depth=1 / | sort -h        # 2. 루트부터 큰 디렉터리를 따라 내려간다
du -h --max-depth=1 /var | sort -h     # 3. 범인이 나올 때까지 반복
find /var/log -type f -size +100M      # 4. 큰 파일 직접 찾기

free -h에서 available이 실제로 쓸 수 있는 메모리다. free 열이 작다고 놀랄 필요 없다. 리눅스는 남는 메모리를 디스크 캐시로 쓰고, 필요하면 즉시 내준다.

9. 원격 접속(SSH)

ssh deploy@203.0.113.10
ssh -p 2222 deploy@example.com     # 포트가 다를 때
ssh -i ~/.ssh/id_ed25519 deploy@example.com   # 키를 지정해서

비밀번호 대신 키로

ssh-keygen -t ed25519 -C "내-노트북"     # 키 쌍 생성 (한 번만)
ssh-copy-id deploy@example.com           # 공개키를 서버에 등록
ssh deploy@example.com                   # 이제 비밀번호를 묻지 않는다

키는 두 짝이다. ~/.ssh/id_ed25519가 개인키(절대 남에게 주지 않는다), ~/.ssh/id_ed25519.pub가 공개키(서버에 등록하는 쪽)다. 서버에서는 ~/.ssh/authorized_keys에 공개키가 쌓인다.

접속 정보를 이름으로 저장하기

cat >> ~/.ssh/config <<'EOF'
Host web01
  HostName 203.0.113.10
  User deploy
  Port 2222
  IdentityFile ~/.ssh/id_ed25519
EOF

ssh web01     # 이제 이걸로 끝

파일 주고받기

scp app.tar.gz web01:/tmp/            # 올리기
scp web01:/var/log/app.log ./        # 내려받기
rsync -avz ./dist/ web01:/var/www/   # 큰 디렉터리는 rsync가 낫다 (변경분만)

자주 하는 실수

Permission denied (publickey)

ssh deploy@example.com
# deploy@example.com: Permission denied (publickey).

서버가 비밀번호 인증을 끄고 공개키만 받는 상태인데, 내 키가 등록돼 있지 않거나 서버가 그 키를 찾지 못한 것이다. ssh -v로 어떤 키를 시도했는지 확인하고, ssh-copy-id로 등록한다. 등록했는데도 거부된다면 서버 쪽 ~/.ssh의 권한을 본다. ~/.ssh는 700, authorized_keys는 600이어야 하며, 더 열려 있으면 SSH가 의도적으로 무시한다.

sudo 를 붙였더니 command not found

terraform version
# Terraform v1.9.5
sudo terraform version
# sudo: terraform: command not found

sudo는 보안을 위해 PATH를 초기화한다. 내 계정의 PATH에만 있는 명령(예: /usr/local/bin이나 홈 디렉터리 아래)은 보이지 않는다. 절대 경로로 부르거나(sudo /usr/local/bin/terraform), 애초에 sudo가 필요한 명령인지 다시 생각해 본다.

No space left on device — 그런데 df 는 여유가 있다고 한다

touch /var/log/test
# touch: cannot touch '/var/log/test': No space left on device
df -h /var
# /dev/sda1  40G  22G  17G  57% /var

두 가지 중 하나다.

  1. inode 고갈. 용량은 남았지만 파일 개수 한도가 찼다. df -i로 확인한다. 작은 파일을 수백만 개 만드는 서비스에서 생긴다.
  2. 지워졌지만 열려 있는 파일. 로그 파일을 rm했는데 프로세스가 아직 그 파일을 열고 있으면 공간이 반환되지 않는다. lsof +L1로 찾고, 해당 서비스를 재시작하거나 HUP을 보내면 공간이 돌아온다.

그래서 로그를 지울 때는 rm 대신 비우는 편이 안전하다.

truncate -s 0 /var/log/huge.log     # 파일은 두고 내용만 비운다

설정을 고쳤는데 반영되지 않는다

순서대로 확인한다. (1) 고친 파일이 정말 그 서비스가 읽는 파일인가 — systemctl cat <서비스>로 유닛이 가리키는 경로를 확인한다. (2) 유닛 파일을 고쳤다면 daemon-reload를 했는가. (3) restart가 아니라 reload만 해서 반영이 안 되는 종류의 변경은 아닌가. (4) 문법 오류로 서비스가 예전 설정으로 남아 있는 것은 아닌가 — journalctl -u <서비스> -p err를 본다.

rm -rf 로 엉뚱한 것을 지웠다

리눅스에 휴지통은 없다. 특히 변수를 쓴 명령이 위험하다. rm -rf "$DIR"/에서 DIR이 비어 있으면 rm -rf /가 된다. 습관을 두 개만 들이자. 지우기 전에 같은 경로로 ls를 먼저 쳐 보는 것, 그리고 스크립트에서는 rm 앞에 경로가 비었는지 검사하는 것이다. (스크립트에서의 방어는 Stage 4에서 set -euo pipefail과 함께 다룬다.)

과제 1 — 서버 상태 요약 스크립트

실행하면 아래를 한 화면에 보여주는 sysreport.sh를 만든다. 지금은 명령을 나열하는 수준으로 충분하다. Stage 4에서 인자 처리와 에러 처리를 붙여 완성한다.

  • 호스트명, 가동 시간, 부하

  • 메모리 사용량
  • CPU를 많이 쓰는 프로세스 5개
  • 실패한 systemd 서비스 목록

검증: bash sysreport.sh가 위 다섯 항목을 모두 출력하고, 종료 코드가 0인가(echo $?).

과제 2 — 서비스를 죽였다가 되살리기

Nginx를 설치하고, 프로세스를 강제로 죽인 뒤, 로그만 보고 무슨 일이 있었는지 설명한 다음 되살린다.

sudo apt update && sudo apt install -y nginx
systemctl status nginx
sudo kill -9 $(systemctl show -p MainPID --value nginx)
systemctl status nginx
journalctl -u nginx --since "5 min ago"

검증: systemctl status nginx가 다시 active (running)이고, 저널에서 프로세스가 비정상 종료된 시점을 짚을 수 있는가.

과제 3 — 디스크를 채우고 범인 찾기

mkdir -p ~/lab && fallocate -l 500M ~/lab/big.bin

du만 써서 홈 디렉터리 아래에서 이 파일을 찾아낸다. 위에서부터 좁혀 내려가는 순서를 몸에 익히는 것이 목적이다. 다 했으면 지운다.

검증: du -h --max-depth=1을 두세 번 반복해 경로를 특정했는가. find로 한 번에 찾지 않았는가.

과제 4 — 비밀번호 없이 접속하기

키 쌍을 만들고 서버에 등록한 뒤, ~/.ssh/config에 별칭을 넣어 ssh <별칭>만으로 들어간다.

검증: 비밀번호를 묻지 않고 접속되는가. ls -ld ~/.ssh가 drwx------인가.
