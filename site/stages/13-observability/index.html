1. 메트릭·로그·트레이스

세 가지는 서로 다른 질문에 답한다. 하나로 전부 하려 들면 비용이 폭발하거나 필요할 때 답이 없다.

메트릭로그트레이스
답하는 질문지금 상태가 어떤가그때 무슨 일이 있었나이 요청이 어디서 느렸나
형태시간에 따른 숫자타임스탬프가 붙은 사건요청 하나의 구간별 시간
비용싸다 (집계된 숫자)비싸다 (양이 많다)중간 (대개 샘플링)
강점알럿, 추세, 대시보드구체적 원인, 디버깅분산 시스템의 병목
약점"왜"를 모른다집계와 알럿에 부적합계측 부담

실무의 순서는 이렇다. 메트릭이 이상을 알리고 → 대시보드로 범위를 좁히고 → 로그에서 구체적 원인을 찾고 → 필요하면 트레이스로 어느 구간인지 짚는다. 이 순서가 Stage 2의 장애 분류와 같은 구조다.

2. 무엇을 측정할 것인가

측정할 수 있는 것은 무한하다. 시작점으로 검증된 두 묶음이 있다.

RED — 요청을 처리하는 서비스

지표뜻왜 보나
Rate초당 요청 수트래픽이 사라졌거나 폭증했나
Errors실패한 요청 비율사용자가 실제로 실패를 겪나
Duration응답 시간 분포느려졌나

USE — 자원

CPU, 메모리, 디스크, 네트워크 각각에 대해 Utilization(얼마나 쓰나) · Saturation(대기가 쌓이나) · Errors를 본다.

⚠ 평균 응답 시간은 거짓말을 한다

요청 100개 중 99개가 10ms, 1개가 10초면 평균은 약 110ms다. 괜찮아 보인다. 하지만 그 1명의 사용자는 10초를 기다렸다. 백분위수를 봐야 한다 — p50(중앙값), p95, p99. 알럿은 대개 p95나 p99에 건다.

3. Prometheus의 데이터 모델

Prometheus는 당겨 온다(pull). 각 대상이 /metrics 경로로 현재 값을 내놓으면, Prometheus가 주기적으로 긁어 간다. 이 방식 덕분에 대상이 사라지면 "긁을 수 없다"는 사실 자체가 신호가 된다.

# /metrics 응답은 이렇게 생겼다
http_requests_total{method="GET",path="/",status="200"} 1027
http_requests_total{method="GET",path="/",status="500"} 3
http_request_duration_seconds_bucket{le="0.1"} 980
http_request_duration_seconds_bucket{le="0.5"} 1020
http_request_duration_seconds_bucket{le="+Inf"} 1030

이름 뒤 중괄호 안이 라벨이다. 같은 메트릭을 라벨로 쪼개 볼 수 있다 — 이것이 Prometheus의 핵심이다.

타입성격예
counter증가만 한다 (재시작 시 0으로)총 요청 수, 총 에러 수
gauge오르내린다현재 메모리, 큐 길이
histogram구간별 개수 — 백분위 계산용응답 시간 분포
summary클라이언트에서 백분위 계산집계가 안 되니 histogram을 선호

⚠ 라벨에 고유값을 넣지 않는다

라벨 값의 조합마다 별도의 시계열이 생긴다. 사용자 ID나 요청 ID를 라벨로 넣으면 시계열이 수백만 개가 되어 Prometheus가 메모리를 다 쓰고 죽는다. 이것을 카디널리티 폭발이라고 한다. 라벨은 값의 종류가 적고 유한한 것만 (메서드, 상태 코드, 엔드포인트 이름). 경로도 /user/123이 아니라 /user/:id로 정규화해야 한다.

4. 애플리케이션 계측

Stage 5의 weatherboard에 메트릭을 붙인다.

pip install prometheus-client
# weatherboard/metrics.py
from prometheus_client import Counter, Histogram, Gauge

REQUESTS = Counter(
    "weatherboard_requests_total",
    "총 요청 수",
    ["path", "status"],            # 라벨은 값 종류가 적은 것만
)

LATENCY = Histogram(
    "weatherboard_request_duration_seconds",
    "요청 처리 시간",
    ["path"],
    buckets=(0.05, 0.1, 0.25, 0.5, 1.0, 2.5, 5.0),
)

UPSTREAM_UP = Gauge(
    "weatherboard_upstream_up",
    "날씨 API 호출 성공 여부 (1/0)",
)
# app.py 안에서
import time
from prometheus_client import generate_latest, CONTENT_TYPE_LATEST

class Handler(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path == "/metrics":
            body = generate_latest()
            self.send_response(200)
            self.send_header("Content-Type", CONTENT_TYPE_LATEST)
            self.send_header("Content-Length", str(len(body)))
            self.end_headers()
            self.wfile.write(body)
            return

        started = time.perf_counter()
        status = 200
        try:
            ...  # 기존 처리
        finally:
            LATENCY.labels(path=self.path).observe(time.perf_counter() - started)
            REQUESTS.labels(path=self.path, status=str(status)).inc()

finally에 둔 것이 중요하다. 예외가 나도 기록되어야 에러율이 실제 에러율이 된다.

내가 안 만든 것들 — exporter

Nginx, PostgreSQL, 리눅스 호스트는 Prometheus 형식으로 말하지 않는다. exporter가 통역한다.

대상exporter얻는 것
리눅스 호스트node_exporterCPU, 메모리, 디스크, 네트워크
컨테이너cAdvisor컨테이너별 자원 사용
Nginxnginx-prometheus-exporter연결 수, 요청 수
블랙박스 점검blackbox_exporter밖에서 본 응답 여부와 시간

5. PromQL

처음에는 낯설지만, 실무에서 쓰는 패턴은 몇 개뿐이다.

# 지금 값
weatherboard_upstream_up

# 초당 요청 수 — counter에는 반드시 rate()를 씌운다
rate(weatherboard_requests_total[5m])

# 에러율 (0~1)
sum(rate(weatherboard_requests_total{status=~"5.."}[5m]))
  / sum(rate(weatherboard_requests_total[5m]))

# p95 응답 시간
histogram_quantile(0.95,
  sum(rate(weatherboard_request_duration_seconds_bucket[5m])) by (le))

# 경로별로 나눠서
sum(rate(weatherboard_requests_total[5m])) by (path)

# 디스크가 4시간 뒤 가득 찰까 (Stage 1의 그 문제를 예측으로)
predict_linear(node_filesystem_avail_bytes{mountpoint="/"}[6h], 4*3600) < 0

⚠ counter를 그냥 그리지 않는다

http_requests_total을 그대로 그래프에 넣으면 계속 올라가는 직선만 보인다. 의미 있는 것은 변화율이다. counter에는 항상 rate()나 increase()를 씌운다. 그리고 rate()의 구간은 스크레이프 간격의 4배 이상으로 잡는다(15s 간격이면 최소 1m, 보통 5m).

6. 대시보드

대시보드는 예쁘라고 만드는 게 아니라 장애 때 5초 안에 상황을 파악하려고 만든다. 좋은 대시보드는 위에서 아래로 읽힌다.

  1. 맨 위 — 지금 정상인가? (에러율, p95 지연, 요청 수 — 큰 숫자 세 개)
  2. 가운데 — 어디가 문제인가? (경로별·인스턴스별로 쪼갠 그래프)
  3. 아래 — 자원은 괜찮은가? (CPU, 메모리, 디스크)

💡 패널을 줄이는 것이 개선이다

패널이 40개인 대시보드는 아무도 읽지 않는다. 장애 상황에서 눈이 갈 곳이 없기 때문이다. 한 화면에 들어오는 8~12개로 유지하고, 세부는 별도 대시보드로 내린다. "이 패널이 빨개지면 나는 무엇을 할 것인가"에 답할 수 없는 패널은 지운다.

Grafana 대시보드는 JSON으로 내보낼 수 있다. 저장소에 커밋하자 — 사람이 손으로 만든 대시보드는 그 사람이 떠나면 사라진다. Stage 10의 "코드로 관리한다"가 여기에도 적용된다.

7. 알럿 설계

이 절이 이 단계에서 가장 중요하다. 나쁜 알럿은 없는 것만 못하다 — 사람들이 무시하기 시작하면 진짜 장애도 무시된다.

# alerts.yml
groups:
  - name: weatherboard
    rules:
      - alert: HighErrorRate
        expr: |
          sum(rate(weatherboard_requests_total{status=~"5.."}[5m]))
            / sum(rate(weatherboard_requests_total[5m])) > 0.05
        for: 10m                          # 10분간 지속될 때만 — 순간 스파이크 무시
        labels:
          severity: page                  # 사람을 깨운다
        annotations:
          summary: "에러율 5% 초과 ({{ $value | humanizePercentage }})"
          runbook: "https://github.com/3r15/devops/blob/main/RUNBOOK.md#higherrorrate"

      - alert: UpstreamDown
        expr: weatherboard_upstream_up == 0
        for: 15m
        labels:
          severity: ticket                # 업무 시간에 처리
        annotations:
          summary: "날씨 API 호출이 15분째 실패 중"

      - alert: DiskWillFill
        expr: predict_linear(node_filesystem_avail_bytes{mountpoint="/"}[6h], 4*3600) < 0
        for: 30m
        labels:
          severity: ticket
등급뜻기준
page새벽에도 깨운다사용자가 지금 피해를 보고 있고 즉시 조치가 필요하다
ticket업무 시간에 본다곧 문제가 되지만 지금은 아니다
없음대시보드에만알아두면 좋은 것

⚠ "CPU 80% 초과"는 좋은 알럿이 아니다

CPU가 높은 것 자체는 문제가 아니다 — 자원을 잘 쓰고 있다는 뜻일 수도 있다. 사용자가 느려짐을 겪지 않는다면 깨울 이유가 없다. 증상에 알럿을 걸고, 원인은 대시보드에서 찾는다. 좋은 알럿은 "응답이 느리다", "에러가 난다", "요청이 안 들어온다"처럼 사용자가 겪는 것을 말한다.

알럿마다 갖춰야 할 것 셋이다.

  • for: — 지속 시간. 순간 스파이크로 깨우지 않는다
  • 런북 링크 — 새벽 3시에 깬 사람이 무엇을 할지 적힌 문서
  • 명확한 요약 — 알림 제목만 보고 심각도를 판단할 수 있어야

알럿 피로를 막는 습관

  • 발동한 알럿은 전부 회고한다 — 조치가 필요 없었다면 그 알럿을 고치거나 지운다
  • 같은 원인의 알럿은 묶는다 (Alertmanager의 grouping)
  • 배포 중이나 점검 중에는 silence를 건다
  • 월 1회 "이번 달에 울린 알럿 목록"을 보고 정리한다

8. 로그 파이프라인

Stage 7에서 "로그는 stdout/stderr로"라고 한 이유가 여기 있다. 컨테이너의 표준 출력은 수집기가 자동으로 가져간다.

애플리케이션 (stdout)
  → 수집기 (Promtail / Fluent Bit / Filebeat)
    → 저장소 (Loki / Elasticsearch / CloudWatch Logs)
      → 조회 (Grafana / Kibana)
스택성격
ELK (Elasticsearch + Logstash + Kibana)전문 검색이 강하다. 무겁고 운영 부담이 크다
Loki + Promtail + Grafana라벨만 인덱싱해 가볍고 싸다. Prometheus와 같은 라벨 체계
클라우드 매니지드운영이 없다. 양이 늘면 비용이 빠르게 는다

구조화된 로그

# 사람만 읽을 수 있는 로그 — 검색과 집계가 어렵다
log.info("사용자 %s 요청 실패, 소요 %sms", user_id, elapsed)

# 구조화된 로그 — 필드로 검색·집계된다
log.info("request_failed", extra={
    "user_id": user_id,
    "elapsed_ms": elapsed,
    "path": path,
    "status": 500,
})

JSON 형태로 남기면 "status=500이고 elapsed_ms>1000인 것"을 바로 찾을 수 있다. Stage 5에서 logging을 쓰라고 한 것이 이 확장을 염두에 둔 것이다.

⚠ 로그에 민감정보를 남기지 않는다

비밀번호, 토큰, 주민번호, 카드번호. 한 번 로그 저장소에 들어가면 여러 시스템으로 복제되고 오래 보관된다. 요청 본문을 통째로 로깅하는 코드가 가장 흔한 사고 경로다. 이 주제는 Stage 14에서 이어진다.

보존 기간

로그 비용은 보존 기간 × 양이다. 30일이면 대부분의 디버깅에 충분하고, 감사 목적의 로그만 따로 오래 보관한다. 기간을 정하지 않으면 무한히 쌓이고, Stage 12에서 본 "조용히 돈이 새는 곳"이 된다.

9. SLI와 SLO

용어뜻예
SLI측정하는 지표성공 응답 비율, p95 지연
SLO목표치30일간 성공률 99.9%
에러 버짓허용되는 실패량99.9%면 30일 중 약 43분

SLO의 실용적 가치는 "충분히 안정적인가"를 숫자로 판정하는 데 있다. 에러 버짓이 남아 있으면 새 기능을 배포하고, 다 썼으면 안정화에 집중한다 — "더 안정적으로"와 "더 빨리"의 다툼을 감정이 아니라 데이터로 정리하는 장치다.

💡 100%를 목표로 하지 않는다

가용성 100%는 불가능하고, 99.99%와 99.9%의 비용 차이는 크다. 사용자가 체감하지 못하는 마지막 0.09%에 예산을 쏟는 대신, 사용자가 실제로 원하는 수준을 정하는 것이 SLO의 요점이다.

자주 하는 실수

알럿이 너무 많아 아무도 안 본다

가장 흔하고 가장 위험한 실패다. 진짜 장애가 소음에 묻힌다. 치료법은 공격적으로 지우는 것이다. 지난 한 달 알럿 중 "받고 아무 조치도 안 한 것"을 전부 삭제하거나 ticket으로 내린다. 남길 것은 "이게 울리면 내가 지금 무언가 한다"뿐이다.

카디널리티 폭발로 Prometheus가 죽는다

# 어떤 메트릭이 시계열을 많이 만드나
topk(10, count by (__name__)({__name__=~".+"}))

라벨에 요청 ID, 사용자 ID, 정규화하지 않은 URL 경로를 넣은 것이 원인이다. Prometheus의 메모리 사용량이 계속 늘다가 OOM으로 죽는다(Stage 8의 그 OOMKilled다). 문제 라벨을 제거하고, 경로는 템플릿으로 정규화한다.

대시보드는 초록인데 사용자는 못 쓴다

안에서 본 지표만 보고 있는 것이다. 애플리케이션은 200을 반환하지만 DNS·로드밸런서·CDN·인증서 중 어딘가가 막혀 있을 수 있다. 밖에서 보는 점검(blackbox exporter나 외부 모니터링)을 하나 두면 "우리가 보는 것"과 "사용자가 겪는 것"의 차이를 잡을 수 있다.

장애 때 로그를 찾을 수 없다

보존 기간이 짧았거나, 인덱스가 없어 검색이 느리거나, 로그가 컨테이너와 함께 사라진 경우다. 평소에 실제로 검색해 보는 것이 유일한 예방책이다 — "지난주 화요일 14시의 500 에러"를 지금 찾아보자. 못 찾으면 장애 때도 못 찾는다.

메트릭이 사라졌는데 알럿이 안 울린다

# 대상이 죽으면 메트릭 자체가 사라져 > 조건은 절대 참이 안 된다
- alert: TargetDown
  expr: up == 0            # ← up 메트릭은 Prometheus가 항상 만든다
  for: 5m
  labels: { severity: page }

# absent()로 특정 메트릭의 부재를 잡을 수도 있다
- alert: NoMetrics
  expr: absent(weatherboard_requests_total)
  for: 10m

"에러율 > 5%" 알럿은 서비스가 완전히 죽으면 울리지 않는다. 요청 자체가 없어 분모가 0이기 때문이다. up == 0과 absent()를 함께 걸어야 이 구멍이 막힌다.

직접 해보기

과제 1 — weatherboard에 메트릭 붙이기

/metrics 엔드포인트를 추가하고 RED 세 지표를 노출한다. Prometheus를 띄워 스크레이프되는지 확인한다.

검증: curl localhost:8000/metrics가 값을 내는가. Prometheus UI의 Targets에서 UP인가. 요청을 몇 번 보낸 뒤 rate(weatherboard_requests_total[1m])이 0보다 큰가.

과제 2 — 대시보드 한 장

Grafana에 패널 6~8개짜리 대시보드를 만든다. 맨 위에 에러율·p95·요청 수, 가운데에 경로별 분해, 아래에 CPU/메모리.

검증: 패널마다 "이게 이상해지면 나는 무엇을 하나"에 답할 수 있는가. 답할 수 없는 패널을 지웠는가. 대시보드 JSON을 저장소에 커밋했는가.

과제 3 — 알럿 3개와 런북

의미 있는 알럿 셋을 만든다. 서로 다른 성격이어야 한다 — (1) 사용자 피해(에러율), (2) 예측(디스크), (3) 부재(up == 0). 각각에 런북 항목을 쓴다.

검증: 각 알럿이 왜 그 for: 값인지 설명할 수 있는가. 런북에 "무엇을 확인하고 무엇을 실행하는가"가 구체적으로 적혀 있는가 (새벽 3시의 나를 위한 문서다).

과제 4 — 장애를 만들고 잡기

이 과제가 이 단계의 핵심이다. 다음 셋을 각각 일으키고, 알럿이 울리는지와 대시보드에서 원인을 좁힐 수 있는지를 확인한다.

  1. 애플리케이션이 500을 반환하게 만든다 → 에러율 알럿
  2. 인위적 지연(sleep 3)을 넣는다 → p95 상승
  3. 컨테이너를 아예 죽인다 → up == 0 알럿

검증: 3번에서 에러율 알럿이 울리지 않는 것을 확인했는가? (요청이 없으니 분모가 0이다.) 그래서 up == 0이 왜 필요한지 이해했는가. 각 경우 알럿이 뜨기까지 몇 분 걸렸는가.

과제 5 — 로그에서 찾아내기

과제 4에서 만든 장애의 구체적 원인을 로그에서 찾는다. 가능하면 구조화된 로그로 바꾸고 필드로 검색해 본다.

검증: 메트릭이 알려준 시각으로 로그 범위를 좁혔는가. "메트릭 → 대시보드 → 로그" 순서를 실제로 밟았는가, 아니면 로그부터 뒤졌는가.
