Stage 14 · Operations & Security

Security (DevSecOps Basics)

최소 권한, 시크릿 관리, 취약점 스캔, 공급망 보안, 파이프라인 내 보안 게이트.

예상 18시간 완료

이 단계를 끝내면

  • 보안을 마지막 검사가 아니라 파이프라인의 일부로 만들 수 있다.
  • 커밋된 비밀과 취약한 의존성을 머지 전에 자동으로 막을 수 있다.
  • 컨테이너와 권한을 최소 권한 원칙에 맞게 좁힐 수 있다.
  • 공급망 위협이 무엇이고 무엇으로 줄이는지 설명할 수 있다.
  • 비밀이 유출됐을 때 무엇을 먼저 할지 안다.

준비물

  • Stage 9의 파이프라인. 이번 단계의 검사들은 전부 거기에 붙는다.
  • Stage 7의 이미지와 Stage 3의 저장소.

💡 이 단계는 회수의 장이다

지금까지 열세 단계에 걸쳐 보안 관련 경고를 흘려 뒀다 — chmod 777(1), 0.0.0.0/0 SSH(2, 12), 커밋된 비밀(3), rm -rf "$VAR"(4), shell=True(5), curl -k(2, 6), root로 도는 컨테이너(7), base64일 뿐인 Secret(8), 포크 PR 시크릿(9), 평문 state(10), vault의 한계(11), 공개 버킷(12), 로그 속 민감정보(13). 이 단계는 그것들을 한자리에 모으고, 사람의 기억 대신 자동으로 막는 장치를 붙인다.

1. 왼쪽으로 옮긴다

전통적으로 보안은 배포 직전의 검사였다. 그때 발견된 문제는 고치는 데 가장 비싸다 — 설계를 되돌려야 하고, 일정은 이미 끝나 있다.

발견 시점고치는 비용여기서 잡는 것
코드 작성 중몇 분IDE 경고, pre-commit 훅
PR몇 십 분시크릿 스캔, 의존성 검사, SAST
배포 전몇 시간이미지 스캔, 설정 검사
운영 중며칠런타임 탐지
유출 후측정 불가—

DevSecOps의 요점은 보안 담당자가 열심히 하는 것이 아니라, 검사를 자동화해 개발자가 만든 자리에서 바로 알게 하는 것이다.

⚠ 검사를 늘리면 사람들이 우회하기 시작한다

Stage 9의 "느린 파이프라인은 무시된다"가 여기서도 그대로다. 경고가 500개 나오는 스캐너는 아무도 안 본다. 차단할 것은 적게, 확실하게 정하고 나머지는 리포트로 남기자. 처음에는 "새로 추가되는 것만" 막는 것도 좋은 전략이다.

2. 무엇을 걱정할 것인가

모든 위협을 다 막을 수는 없다. 우리 시스템에 실제로 해당하는 것부터 본다.

위협구체적으로주된 방어
자격증명 유출커밋된 키, 로그에 찍힌 토큰스캔 + 단기 자격증명
취약한 의존성알려진 CVE가 있는 패키지SCA + 자동 업데이트
과도한 권한* 정책, root 컨테이너최소 권한
노출된 표면공개 버킷, 열린 포트기본 차단 + 설정 검사
공급망변조된 이미지, 악성 패키지고정 + 서명 + SBOM
애플리케이션 취약점주입, 인증 우회SAST/DAST, 리뷰

순서를 정할 때의 질문은 "이게 뚫리면 무엇을 잃는가"다. 고객 데이터가 있는 DB의 접근 권한이, 사내 위키의 XSS보다 먼저다.

3. 시크릿 관리

Stage 3에서 "커밋한 비밀은 이력에 영원히 남는다"고 했다. 그 뒤로 여러 단계에서 같은 문제가 형태를 바꿔 나타났다. 원칙은 하나다 — 비밀은 코드와 같은 곳에 두지 않는다.

수준방식평가
최악코드에 하드코딩이력에 영원히 남는다
나쁨.env 파일을 서버에 복사누가 언제 봤는지 알 수 없다
보통CI 시크릿 / k8s Secret접근 통제는 되지만 장기 자격증명
좋음시크릿 관리 서비스에서 조회중앙 관리, 감사 로그, 회전 가능
가장 좋음비밀 자체가 없다 — OIDC/워크로드 아이덴티티유출될 것이 없다

Stage 9의 OIDC와 Stage 12의 인스턴스 프로파일이 마지막 줄에 해당한다. "어떻게 안전하게 저장할까"보다 "저장하지 않을 수 있나"를 먼저 묻자.

커밋된 비밀 찾기

# gitleaks — 이력 전체를 스캔한다
docker run --rm -v "$PWD:/repo" zricethezav/gitleaks:latest detect \
  --source=/repo --verbose

# 커밋 전에 막기 (pre-commit 훅)
pip install pre-commit
cat > .pre-commit-config.yaml <<'YAML'
repos:
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.21.2
    hooks:
      - id: gitleaks
YAML
pre-commit install

GitHub은 Secret scanning을 기본 제공한다(공개 저장소는 무료). 주요 서비스의 키 형식을 알아보고, 발견되면 발급처에 자동으로 알려 폐기시킨다. Settings → Code security에서 켜자.

⚠ 유출됐을 때의 순서 — 폐기가 먼저다

키를 커밋했다는 걸 알았을 때 사람들은 대개 이력을 지우려 든다. 순서가 틀렸다.

  1. 즉시 폐기·재발급한다. 공개 저장소라면 이미 봇이 긁어 갔다고 가정한다
  2. 그 키로 무엇이 일어났는지 로그를 확인한다 (누가 언제 썼나)
  3. 그다음에 이력 정리를 고민한다 (git filter-repo 등 — 협업자 모두에게 영향이 간다)

이력에서 지워도 이미 클론한 사람, 포크, 캐시에는 남아 있다. 지우는 것은 유출을 되돌리지 못한다.

4. 의존성 취약점

내가 쓴 코드보다 내가 가져온 코드가 훨씬 많다. 파이썬 프로젝트 하나에 직접 의존성 5개, 전이 의존성 80개는 흔하다.

# 파이썬
pip install pip-audit
pip-audit -r requirements.txt

# 컨테이너 이미지와 파일시스템 (Stage 7의 이미지)
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
  aquasec/trivy:latest image weatherboard:0.1 --severity HIGH,CRITICAL

# 저장소 전체
trivy fs --scanners vuln,secret,misconfig .

GitHub의 Dependabot은 취약점을 알리고 업데이트 PR을 자동으로 열어 준다. Stage 5의 테스트와 Stage 9의 CI가 있으면 그 PR이 안전한지 자동으로 검증되니, 셋이 함께 있을 때 값을 한다.

# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: pip
    directory: /
    schedule: { interval: weekly }
  - package-ecosystem: docker
    directory: /
    schedule: { interval: weekly }
  - package-ecosystem: github-actions      # 액션도 의존성이다
    directory: /
    schedule: { interval: weekly }

💡 CVE가 있다고 전부 위험한 것은 아니다

스캐너가 CRITICAL 30개를 뱉어도 그중 대부분은 우리가 쓰지 않는 코드 경로이거나 공격자가 닿을 수 없는 위치에 있다. 그렇다고 무시하라는 뜻은 아니고, 맥락을 봐야 한다는 뜻이다. 우선순위는 (1) 인터넷에 노출된 컴포넌트, (2) 실제로 호출되는 코드 경로, (3) 익스플로잇이 공개된 것 순이다. 기준 없이 "CRITICAL 0개"를 요구하면 팀은 스캐너를 끄는 쪽을 택한다.

5. 코드 검사

# 파이썬 정적 분석
pip install bandit
bandit -r weatherboard/ -ll        # -ll: MEDIUM 이상만

# 셸 스크립트 — Stage 4의 그 도구가 보안 검사이기도 하다
shellcheck sysreport.sh

# 여러 언어를 한 번에
docker run --rm -v "$PWD:/src" semgrep/semgrep semgrep --config=auto /src

Stage 5에서 경고한 subprocess의 shell=True, Stage 4의 인용하지 않은 변수는 정적 분석이 자동으로 잡아 준다. 사람의 기억에 의존하지 않게 만드는 것이 이 절의 요점이다.

GitHub의 CodeQL은 저장소에 워크플로 하나로 붙고 결과를 Security 탭에 모은다. 공개 저장소는 무료다.

6. 컨테이너 하드닝

Stage 7에서 "root로 돌지 않는다"고 한 것의 나머지다.

FROM python:3.12-slim AS builder
# ... 빌드 ...

FROM python:3.12-slim
RUN useradd --create-home --uid 10001 app
COPY --from=builder /opt/venv /opt/venv
COPY weatherboard/ /app/weatherboard/
USER 10001                              # 숫자 UID로 (k8s가 검증할 수 있다)
ENV PATH="/opt/venv/bin:$PATH" HOST=0.0.0.0
EXPOSE 8000
CMD ["python", "-m", "weatherboard.app"]

쿠버네티스에서는 한 층 더 조인다.

      securityContext:
        runAsNonRoot: true
        runAsUser: 10001
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: app
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true      # 쓰기가 필요하면 emptyDir을 마운트
            capabilities:
              drop: ["ALL"]
          resources:
            limits: { cpu: 500m, memory: 256Mi }   # Stage 8의 그것 — 보안 장치이기도 하다
설정막는 것
runAsNonRoot컨테이너 탈출 시 피해 범위
readOnlyRootFilesystem침입자가 도구를 내려받아 심는 것
drop: ["ALL"]불필요한 커널 권한
allowPrivilegeEscalation: falsesetuid를 통한 권한 상승
리소스 limits한 파드가 노드 전체를 마비시키는 것

Stage 7에서 본 멀티스테이지가 보안 장치이기도 하다 — 컴파일러와 셸이 없는 이미지에서는 침입자가 할 수 있는 일이 적다. distroless 이미지가 그 극단이다.

⚠ docker.sock을 컨테이너에 마운트하지 않는다

Stage 7에서 "docker 그룹은 사실상 root"라고 했다. 컨테이너 안에 /var/run/docker.sock을 넣으면 그 컨테이너가 호스트의 root가 된다. CI 러너에서 흔히 보이는 패턴인데, 대안(Kaniko, BuildKit rootless, buildah)이 있다.

7. 공급망 보안

내가 쓰는 것이 정말 내가 의도한 그것인지를 다루는 영역이다.

고정한다

# 나쁨 — 무엇이 올지 모른다
FROM python:3.12-slim
- uses: actions/checkout@v4

# 좋음 — 다이제스트로 고정
FROM python:3.12-slim@sha256:1e8cfa0af74f8...
- uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683   # v4.2.2

Stage 7·8·10에서 반복한 "버전을 고정하라"가 여기서 보안 이유를 얻는다. 태그는 움직일 수 있고, 서드파티 액션이 침해되면 태그가 악성 커밋을 가리키게 된다. 실제로 일어난 사고다. 다이제스트는 움직이지 않는다.

SBOM과 서명

# SBOM — 이 이미지에 무엇이 들어 있는지의 목록
docker run --rm anchore/syft:latest weatherboard:0.1 -o spdx-json > sbom.json

# 서명과 검증 (Sigstore cosign, 키 없이 OIDC로)
cosign sign ghcr.io/3r15/weatherboard@sha256:...
cosign verify ghcr.io/3r15/weatherboard@sha256:... \
  --certificate-identity-regexp 'https://github.com/3r15/.*' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

SBOM이 있으면 새 CVE가 공개됐을 때 "우리가 영향을 받나"를 몇 초 안에 답할 수 있다. 서명은 "이 이미지가 우리 파이프라인에서 나왔다"를 증명한다 — Stage 9의 OIDC가 여기서도 열쇠 없는 인증으로 쓰인다.

8. 파이프라인 보안 게이트

지금까지의 검사를 Stage 9의 파이프라인에 붙인다.

name: Security

on:
  pull_request:
  push:
    branches: [main]
  schedule:
    - cron: "0 3 * * 1"        # 새 CVE는 코드가 안 바뀌어도 생긴다

permissions:
  contents: read

jobs:
  secrets:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }        # 이력 전체를 봐야 한다
      - uses: gitleaks/gitleaks-action@v2

  deps:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install pip-audit
      - run: pip-audit -r requirements.txt

  image:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t scan-target:${{ github.sha }} .
      - uses: aquasecurity/trivy-action@0.28.0
        with:
          image-ref: scan-target:${{ github.sha }}
          severity: HIGH,CRITICAL
          exit-code: "1"              # 발견되면 실패시킨다
          ignore-unfixed: true        # 고칠 방법이 없는 것은 제외

  code:
    runs-on: ubuntu-latest
    permissions:
      security-events: write          # 결과를 Security 탭에 올린다
    steps:
      - uses: actions/checkout@v4
      - uses: github/codeql-action/init@v3
        with: { languages: python }
      - uses: github/codeql-action/analyze@v3

💡 schedule이 있는 이유

어제 깨끗했던 이미지가 오늘 취약해질 수 있다 — 코드가 바뀌어서가 아니라 새 CVE가 공개돼서다. PR 때만 검사하면 오래 배포하지 않은 서비스는 영원히 모른다. 주 1회 정기 스캔이 그 구멍을 막는다.

무엇을 차단하고 무엇을 보고할 것인가

검사PR에서이유
시크릿 발견차단오탐이 적고 피해가 크다
고칠 수 있는 CRITICAL 취약점차단업데이트 한 줄이면 된다
고칠 수 없는 취약점보고막아도 할 수 있는 게 없다
SAST 신규 발견보고 (또는 리뷰 필수)오탐이 있어 판단이 필요하다
기존 코드의 SAST 결과보고차단하면 아무 PR도 못 올린다

9. 운영 중의 보안

파이프라인을 통과했다고 끝이 아니다. Stage 13의 관측이 보안에도 쓰인다.

  • 감사 로그 — 누가 무엇을 했나. 클라우드의 CloudTrail/Activity Log, 쿠버네티스 감사 로그
  • 이상 징후 알럿 — 평소 없던 곳에서의 로그인, 갑작스러운 데이터 전송량 증가, 권한 변경
  • 설정 드리프트 — Stage 10의 그 개념이 보안에서는 "누가 콘솔에서 방화벽을 열었나"가 된다
  • 자격증명 회전 — 남아 있는 장기 키는 주기적으로 교체. 사람이 하면 안 하게 되니 자동화한다

침해를 가정하고 준비한다

"뚫리지 않는다"가 아니라 "뚫렸을 때 무엇을 할 것인가"를 미리 적어 둔다. Stage 13에서 만든 런북과 같은 문서다.

  1. 격리 — 해당 자격증명 폐기, 인스턴스 분리 (지우지 말 것 — 증거다)
  2. 범위 파악 — 감사 로그로 무엇에 접근했는지
  3. 복구 — 깨끗한 이미지로 재배포 (Stage 9·10이 여기서 값을 한다)
  4. 회고 — 어떻게 들어왔고 왜 못 막았나

💡 Stage 9·10·11이 보안 도구이기도 하다

침해된 서버를 "깨끗한 상태로 되돌리는" 가장 빠른 방법은, 그 서버를 지우고 코드에서 다시 만드는 것이다. Terraform과 Ansible과 파이프라인이 있으면 몇 분이고, 없으면 며칠이다. 재현 가능한 인프라는 편의 기능이 아니라 복구 능력이다.

자주 하는 실수

비밀을 커밋하고 다음 커밋에서 지웠다

git rm --cached .env
git commit -m "Remove .env"        # ← 이력에는 그대로 남아 있다
git log -p --all -S "API_KEY" | head    # 여전히 찾을 수 있다

Stage 3에서 본 그대로다. 지우는 것은 유출을 되돌리지 못한다. 폐기·재발급이 먼저고, 이력 정리는 그다음이다.

스캐너 결과가 너무 많아 전부 무시한다

CRITICAL 200개짜리 리포트는 0개짜리와 같다. 처음 도입할 때는 기준선을 잡고 "새로 추가되는 것만" 차단하는 것이 현실적이다. 기존 것은 목록으로 만들어 우선순위대로 줄여 나간다. 완벽을 요구하면 도구가 꺼진다.

보안 그룹을 "일단" 열어 두고 잊는다

# 지금 열려 있는 것을 주기적으로 확인하는 습관
aws ec2 describe-security-groups --query \
  'SecurityGroups[?IpPermissions[?IpRanges[?CidrIp==`0.0.0.0/0`]]].[GroupId,GroupName]'

디버깅하느라 연 포트가 그대로 남는 것이 가장 흔한 노출 경로다. Stage 10의 Terraform으로 관리하면 plan에서 리뷰를 거치게 되고, 콘솔에서 손으로 연 것은 드리프트로 드러난다.

로그에 토큰이 찍힌다

log.info("요청: %s", request.headers)      # Authorization 헤더가 통째로 남는다

Stage 13에서 경고한 것이다. 헤더나 본문을 통째로 로깅하는 코드가 사고의 단골이다. 민감 필드를 마스킹하는 필터를 로깅 설정에 넣고, 로그 저장소에서 토큰 패턴을 주기적으로 스캔해 실제로 안 새는지 확인하자.

보안을 한 사람에게 맡긴다

"보안 담당자가 나중에 볼 것"이라는 구조에서는, 그 사람이 병목이 되고 개발자는 배우지 못한다. 이 단계의 도구들이 전부 파이프라인에 들어가는 이유다 — 피드백이 만든 사람에게, 만든 자리에서, 즉시 가야 학습이 일어난다.

직접 해보기

과제 1 — 일부러 심고 막히는지 보기

이 과제가 이 단계의 핵심이다. 다음 셋을 브랜치에 심고 PR을 연다.

  1. 가짜 API 키 한 줄 (형식이 진짜처럼 보이는 것)
  2. 알려진 취약점이 있는 옛 패키지 버전
  3. subprocess.run(cmd, shell=True)에 사용자 입력을 넘기는 코드

검증: 세 검사가 각각 어느 것을 잡고 어느 것을 놓쳤는가? PR이 머지 불가 상태가 되는가. 놓친 것이 있다면 왜인지 설명할 수 있는가.

과제 2 — 컨테이너 조이기

Stage 7의 이미지를 non-root + 읽기 전용 루트 + capability 전부 제거로 바꾼다. Trivy로 스캔해 전후를 비교한다.

검증: docker exec <c> id가 root가 아닌가. docker exec <c> touch /test가 실패하는가. 애플리케이션은 여전히 정상 동작하는가 (쓰기가 필요한 경로가 있다면 어떻게 해결했나).

과제 3 — 보안 파이프라인 붙이기

Stage 9의 저장소에 시크릿 스캔·의존성 검사·이미지 스캔을 추가하고, 주 1회 정기 실행도 건다. 무엇을 차단하고 무엇을 보고할지 정하고 그 이유를 적는다.

검증: 정상 PR에서 파이프라인이 몇 초 늘었는가. 그 비용이 감당할 만한가. 차단 기준을 정한 근거를 한 문단으로 쓸 수 있는가.

과제 4 — 유출 대응 연습

실제로 쓰지 않는 테스트용 API 키를 하나 만들어 커밋하고 push한 뒤, 대응 순서를 시간을 재며 밟는다. 폐기 → 사용 로그 확인 → 이력 정리 검토.

검증: 폐기까지 몇 분 걸렸는가. 그 키가 사용된 기록을 어디서 확인했는가. 이 절차를 RUNBOOK.md에 적어 뒀는가.

과제 5 — SBOM으로 답하기

이미지의 SBOM을 만들고, 특정 패키지(예: requests)가 어느 버전으로 들어 있는지 몇 초 안에 답해 본다.

syft weatherboard:0.1 -o json | jq '.artifacts[] | select(.name=="requests") | .version'

검증: 새 CVE 공지를 받았다고 가정하고, 영향 여부를 판단하는 데 몇 초가 걸렸는가. SBOM이 없다면 같은 질문에 어떻게 답할 것인가.
