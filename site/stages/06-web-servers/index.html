1. 왜 앞단이 필요한가

Stage 5의 weatherboard는 8000번 포트에서 혼자 돌고 있다. 그대로 인터넷에 노출하지 않는 이유가 여럿 있다.

앞단이 하는 일없으면
TLS 종료 (HTTPS 처리)애플리케이션마다 인증서를 다뤄야 한다
정적 파일 서빙이미지 한 장에도 파이썬 프로세스가 붙잡힌다
느린 클라이언트 흡수모바일 회선 하나가 워커 하나를 오래 점유한다
여러 백엔드로 분배확장이 불가능하다
80 → 443 리다이렉트, 헤더 추가애플리케이션 코드에 섞인다
낮은 포트(80/443) 점유애플리케이션을 root로 띄워야 한다

정리하면 애플리케이션은 비즈니스 로직만, 앞단은 HTTP의 잡일 전부다. 이 분리가 이후 모든 단계의 전제가 된다 — Stage 8의 Ingress도 결국 같은 역할이다.

2. 설정 파일의 구조

/etc/nginx/
├── nginx.conf                 # 전역 설정. 대개 손댈 일이 없다
├── sites-available/           # 사이트 설정을 여기에 쓰고
│   ├── default
│   └── weatherboard
├── sites-enabled/             # 여기에 심볼릭 링크를 걸어 활성화한다
│   └── weatherboard -> ../sites-available/weatherboard
└── conf.d/                    # 패키지가 넣는 조각들

Debian/Ubuntu의 관례가 sites-available + sites-enabled다. 파일을 지우지 않고 링크만 끊어 비활성화할 수 있어 되돌리기 쉽다.

sudo ln -s /etc/nginx/sites-available/weatherboard /etc/nginx/sites-enabled/
sudo rm /etc/nginx/sites-enabled/default      # 기본 페이지 비활성화 (파일은 남는다)

설정은 블록의 중첩이다. 안쪽이 바깥쪽을 덮어쓴다.

http {                      # 전체 HTTP 설정
  server {                  # 하나의 가상 호스트
    listen 80;
    server_name example.com;

    location /static/ {     # 경로별 규칙
      root /var/www;
    }
  }
}

⚠ 반영 순서를 지킨다

설정을 고쳤으면 반드시 문법 검사를 먼저 한다. 검사 없이 재시작하면 문법 오류일 때 Nginx가 뜨지 않아 서비스가 통째로 죽는다.

sudo nginx -t                    # 문법 검사 — 항상 먼저
sudo systemctl reload nginx      # 무중단 반영 (기존 연결은 유지)
sudo systemctl restart nginx     # 완전 재시작 (연결이 끊긴다)

reload는 기존 워커가 처리 중인 요청을 끝내고 물러난다. 설정 변경에는 언제나 reload를 쓴다. restart는 정말 필요할 때만.

3. 정적 파일 서빙

# /etc/nginx/sites-available/weatherboard
server {
    listen 80;
    server_name _;                      # 아무 호스트명이나 받는다

    root /var/www/weatherboard;
    index index.html;

    location / {
        try_files $uri $uri/ =404;      # 파일 → 디렉터리 → 없으면 404
    }

    location /assets/ {
        expires 7d;                      # 브라우저 캐시 7일
        add_header Cache-Control "public, immutable";
    }
}

💡 root와 alias는 다르다

location /assets/에서 root /var/www면 실제 경로는 /var/www/assets/...다(URL 경로가 붙는다). alias /var/www/static/면 /var/www/static/...다(URL 경로가 대체된다). 404가 나는데 파일은 분명히 있다면 십중팔구 이 둘을 혼동한 것이다. error_log에 Nginx가 찾으려 한 실제 경로가 찍히니 그것을 보자.

4. 리버스 프록시

이제 weatherboard를 뒤에 둔다. Stage 5에서 기본 HOST가 127.0.0.1이었던 것이 여기서 정확히 맞아떨어진다 — 애플리케이션은 밖에서 직접 접근할 수 없고, 오직 Nginx만 접근한다.

server {
    listen 80;
    server_name weather.example.com;

    location / {
        proxy_pass http://127.0.0.1:8000;

        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location /healthz {
        proxy_pass http://127.0.0.1:8000/healthz;
        access_log off;                 # 헬스체크로 로그를 채우지 않는다
    }
}

네 개의 proxy_set_header가 중요하다. 프록시를 거치면 애플리케이션이 보는 출발지 IP는 전부 127.0.0.1(Nginx)이 되고, 원래 요청이 HTTPS였는지도 모른다. 이 헤더들이 그 정보를 넘겨준다.

  • Host — 사용자가 요청한 도메인. 애플리케이션이 링크를 만들 때 쓴다
  • X-Real-IP, X-Forwarded-For — 진짜 클라이언트 IP
  • X-Forwarded-Proto — 원래 요청이 https였는지

⚠ proxy_pass의 끝 슬래시가 경로를 바꾼다

location /api/ {
    proxy_pass http://127.0.0.1:8000;    # → /api/users 그대로 전달
}
location /api/ {
    proxy_pass http://127.0.0.1:8000/;   # → /users  (/api/ 가 잘린다)
}

슬래시 하나로 백엔드가 받는 경로가 달라진다. 의도한 쪽이 아니면 백엔드에서 404가 난다. curl -v로 확인하고, 애플리케이션 로그에 찍힌 경로와 대조하자.

5. HTTPS 붙이기

Let's Encrypt는 무료로 인증서를 발급하고 자동 갱신해 준다. certbot이 Nginx 설정까지 고쳐 준다.

sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d weather.example.com

발급에는 도메인이 이 서버를 가리키고 80번 포트가 인터넷에서 접근 가능해야 한다 (Let's Encrypt가 소유권을 확인하러 온다). Stage 2의 도구가 여기서 쓰인다.

dig +short weather.example.com     # 이 서버 IP가 나오는가
nc -zv weather.example.com 80      # 밖에서 80이 열려 있는가

certbot이 만들어 주는 설정은 대략 이렇다.

server {
    listen 443 ssl;
    http2 on;
    server_name weather.example.com;

    ssl_certificate     /etc/letsencrypt/live/weather.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/weather.example.com/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

server {                                  # 80은 443으로 넘긴다
    listen 80;
    server_name weather.example.com;
    return 301 https://$host$request_uri;
}

💡 fullchain.pem을 쓴다

Stage 2의 "curl은 되는데 브라우저는 안 된다"가 바로 이것이다. cert.pem(서버 인증서만) 대신 fullchain.pem(중간 인증서 포함)을 써야 모든 클라이언트가 검증에 성공한다. certbot은 알아서 fullchain을 쓴다.

갱신 확인

sudo certbot renew --dry-run       # 실제로 갱신하지 않고 절차만 시험
systemctl list-timers certbot.timer

인증서는 90일짜리다. 자동 갱신 타이머가 도는지 지금 확인해 두자 — 3개월 뒤 새벽에 확인하게 되는 것보다 낫다. Stage 4에서 배운 systemd timer가 여기 쓰인다.

도메인이 없다면

sudo openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout /etc/ssl/private/selfsigned.key \
  -out /etc/ssl/certs/selfsigned.crt \
  -subj "/CN=localhost"

자체 서명 인증서는 브라우저가 경고를 띄운다. 연습용으로만 쓰고, curl -k로 접속해 TLS 자체는 동작하는 것을 확인하는 용도다.

6. 로드밸런싱

upstream weatherboard {
    server 127.0.0.1:8000;
    server 127.0.0.1:8001;
    server 127.0.0.1:8002 backup;      # 다른 게 다 죽었을 때만
}

server {
    listen 80;
    location / {
        proxy_pass http://weatherboard;
    }
}

기본 분배 방식은 라운드로빈이다. 필요에 따라 바꾼다.

지시어동작쓸 때
(기본)순서대로 돌아가며백엔드가 동일할 때
least_conn연결이 가장 적은 곳으로요청 처리 시간이 들쭉날쭉할 때
ip_hash클라이언트 IP로 고정세션이 서버에 붙어 있을 때

💡 ip_hash가 필요하다면 설계를 의심하자

특정 서버에 세션이 묶여 있으면 그 서버가 죽을 때 사용자도 함께 로그아웃된다. 확장도 어려워진다. 세션을 Redis나 DB 같은 공용 저장소로 빼는 편이 낫고, Stage 8의 쿠버네티스에서는 사실상 필수다.

7. 로그 읽기

tail -f /var/log/nginx/access.log     # 누가 무엇을 요청했나
tail -f /var/log/nginx/error.log      # 무엇이 잘못됐나

두 로그의 역할이 다르다. 액세스 로그는 트래픽, 에러 로그는 원인이다. 502가 났다면 액세스 로그에는 "502를 응답했다"만 있고, 왜는 에러 로그에 있다.

응답 시간을 로그에 남기기

기본 로그 형식에는 응답 시간이 없다. 느린 요청을 찾으려면 직접 넣어야 한다.

# /etc/nginx/nginx.conf 의 http { } 안
log_format timed '$remote_addr - $remote_user [$time_local] '
                 '"$request" $status $body_bytes_sent '
                 'rt=$request_time urt=$upstream_response_time';

access_log /var/log/nginx/access.log timed;
  • $request_time — 요청을 받아 응답을 다 보낼 때까지의 전체 시간
  • $upstream_response_time — 백엔드가 답하는 데 걸린 시간

둘의 차이가 크면 백엔드가 아니라 네트워크나 느린 클라이언트가 원인이다. 이 구분이 Stage 13(모니터링)에서 지연 시간을 볼 때 그대로 쓰인다.

# 느린 요청 상위 10개 — Stage 1의 파이프라인이 여기서 쓰인다
awk '{print $NF, $0}' /var/log/nginx/access.log | sort -rn | head -10

# 상태 코드별 개수
awk '{print $9}' /var/log/nginx/access.log | sort | uniq -c | sort -rn

8. 타임아웃과 크기 제한

server {
    client_max_body_size 10m;        # 업로드 최대 크기 (기본 1m)

    location / {
        proxy_pass http://127.0.0.1:8000;

        proxy_connect_timeout 5s;    # 백엔드에 연결하기까지
        proxy_send_timeout   30s;    # 요청을 보내는 동안
        proxy_read_timeout   30s;    # 응답을 기다리는 동안 → 넘으면 504
    }
}

proxy_read_timeout이 504를 만드는 값이다. 무작정 늘리는 것은 답이 아니다 — 백엔드가 30초씩 걸리는 이유를 먼저 봐야 한다. 다만 리포트 생성처럼 원래 오래 걸리는 엔드포인트가 있다면 그 location에만 늘려 준다.

보안 헤더 몇 가지

add_header X-Content-Type-Options "nosniff" always;
add_header X-Frame-Options "SAMEORIGIN" always;
add_header Strict-Transport-Security "max-age=31536000" always;   # HTTPS일 때만
server_tokens off;                    # 응답 헤더에서 버전 숨기기

⚠ HSTS는 되돌리기 어렵다

Strict-Transport-Security는 브라우저에게 "앞으로 이 도메인은 무조건 HTTPS로만 접속하라"고 max-age 기간 동안 기억시킨다. HTTPS 설정이 확실히 자리 잡은 뒤에 켜고, 처음에는 짧은 max-age로 시작하자. 이 주제는 Stage 14에서 다시 다룬다.

9. Apache와의 차이

Apache는 여전히 널리 쓰인다. 개념은 같고 이름만 다르다.

개념NginxApache
가상 호스트server { }<VirtualHost>
경로별 규칙location { }<Location>, <Directory>
프록시proxy_passProxyPass
설정 검사nginx -tapachectl configtest
활성화심볼릭 링크a2ensite / a2enmod
디렉터리별 재정의없음 (의도적).htaccess

가장 큰 차이는 동시성 모델이다. Apache는 전통적으로 연결마다 프로세스나 스레드를 쓰고, Nginx는 이벤트 루프로 적은 프로세스가 많은 연결을 처리한다. 그래서 동시 연결이 많은 환경에서 Nginx가 메모리를 훨씬 덜 쓴다. .htaccess가 없는 것도 의도적이다 — 매 요청마다 디렉터리를 뒤지는 비용을 없앤 것이다.

자주 하는 실수

502 Bad Gateway

curl -I http://localhost
# HTTP/1.1 502 Bad Gateway

tail -2 /var/log/nginx/error.log
# connect() failed (111: Connection refused) while connecting to upstream,
# upstream: "http://127.0.0.1:8000/"

백엔드에 연결하지 못했다는 뜻이다. Stage 2의 refused가 여기 그대로 나온다 — 패킷은 도착했고 그 포트에 아무도 없다. 순서대로 확인한다.

systemctl status weatherboard        # 애플리케이션이 떠 있나
sudo ss -lntp | grep 8000            # 그 포트를 정말 듣고 있나
curl -I http://127.0.0.1:8000        # Nginx를 빼고 직접 붙어 보기

세 번째가 성공하는데 Nginx만 502라면 proxy_pass의 주소나 포트가 틀린 것이다.

504 Gateway Timeout

백엔드에 연결은 됐는데 정해진 시간 안에 응답이 오지 않은 것이다. 502와 달리 애플리케이션은 살아 있다. 애플리케이션 쪽을 본다 — 느린 쿼리, 외부 API 대기, 무한 루프. proxy_read_timeout을 늘리는 것은 원인을 찾은 뒤의 선택이지 첫 대응이 아니다.

403 Forbidden — 파일은 분명히 있는데

tail -1 /var/log/nginx/error.log
# open() "/var/www/weatherboard/index.html" failed (13: Permission denied)

Stage 1의 권한이 여기서 돌아온다. Nginx는 www-data 사용자로 돈다. 파일을 읽을 권한이 있어야 하고, 거기까지 가는 모든 상위 디렉터리에 실행 권한(x)이 있어야 한다.

namei -l /var/www/weatherboard/index.html    # 경로의 각 단계별 권한을 한눈에
sudo chown -R www-data:www-data /var/www/weatherboard
sudo chmod 755 /var/www /var/www/weatherboard

설정을 고쳤는데 반영되지 않는다

Stage 1에서 본 패턴이다. 확인 순서는 이렇다.

sudo nginx -T | grep -n "server_name"    # Nginx가 실제로 읽고 있는 전체 설정
ls -l /etc/nginx/sites-enabled/          # 심볼릭 링크를 걸었나
sudo nginx -t && sudo systemctl reload nginx

nginx -T(대문자)는 모든 include를 펼친 최종 설정을 보여준다. "분명히 고쳤는데"의 답이 대개 여기 있다 — 고친 파일이 활성화되지 않았거나, 다른 server 블록이 먼저 매칭된 것이다.

기본 사이트가 계속 뜬다

요청한 Host와 맞는 server_name이 없으면 Nginx는 첫 번째 server 블록으로 보낸다. sites-enabled/default가 남아 있으면 그게 잡아채는 것이다. 링크를 끊거나, 내 블록에 default_server를 지정한다.

sudo rm /etc/nginx/sites-enabled/default
# 또는
listen 80 default_server;

직접 해보기

과제 1 — weatherboard를 Nginx 뒤에 두기

weatherboard를 systemd 서비스로 만들고(Stage 4의 유닛 파일), Nginx가 80번에서 받아 8000번으로 넘기게 한다. 애플리케이션은 127.0.0.1에만 바인딩된 상태를 유지한다.

검증: 밖에서 curl http://<서버IP>/는 되고 curl http://<서버IP>:8000/은 안 되는가(Stage 2의 timeout/refused). /healthz가 액세스 로그에 안 남는가.

과제 2 — 502와 504를 직접 만들기

이 과제가 이 단계의 핵심이다.

# 502: 백엔드를 멈춘다
sudo systemctl stop weatherboard
curl -I http://localhost
tail -2 /var/log/nginx/error.log

# 504: 백엔드를 느리게 만든다
# app.py의 do_GET 맨 앞에 time.sleep(40) 을 넣고 재시작
# nginx의 proxy_read_timeout 은 기본 60s 이므로 30s로 낮춘다
curl -I http://localhost

검증: 두 경우의 error.log 메시지가 어떻게 다른가. 각각을 보고 "애플리케이션이 죽었다" / "애플리케이션이 느리다"를 구분해 말할 수 있는가.

과제 3 — HTTPS 붙이기

도메인이 있으면 certbot으로, 없으면 자체 서명으로 443을 열고 80을 리다이렉트한다. 갱신 타이머까지 확인한다.

검증: curl -I http://<도메인>이 301과 Location: https://...를 주는가. openssl s_client로 확인한 인증서 체인에 중간 인증서가 포함되어 있는가(Stage 2의 방법). certbot renew --dry-run이 성공하는가.

과제 4 — 응답 시간 로그와 느린 요청 찾기

log_format에 $request_time과 $upstream_response_time을 추가하고, 백엔드에 인위적인 지연을 넣어 두 값의 차이를 관찰한다.

검증: 백엔드를 느리게 했을 때 두 값이 함께 커지는가. 그렇다면 이 로그로 "백엔드가 느린 것"과 "네트워크가 느린 것"을 어떻게 구분할지 설명할 수 있는가.

과제 5 — 로드밸런싱

weatherboard를 포트만 바꿔 두 개 띄우고 upstream으로 묶는다. 한쪽을 죽였을 때 서비스가 계속되는지 확인한다.

검증: 반복 요청 시 두 백엔드에 번갈아 로그가 남는가. 하나를 죽인 뒤에도 curl이 200을 받는가(첫 요청이 잠깐 느려질 수 있다 — 왜인지 생각해 보자).
