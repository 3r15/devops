1. 클릭으로 만든 인프라의 문제

Stage 9까지 파이프라인은 완성됐다. 그런데 그 파이프라인이 배포하는 서버는 누군가 콘솔에서 클릭해 만든 것이다. 여기서 생기는 문제들이 있다.

  • 재현 불가 — 똑같은 것을 하나 더 만들라면 며칠이 걸리고, 미묘하게 다르다
  • 기록 없음 — 왜 이 보안 그룹에 이 규칙이 있는지 아무도 모른다
  • 리뷰 불가 — 누가 무엇을 바꿨는지 콘솔 로그를 뒤져야 안다
  • 드리프트 — 급해서 손으로 고친 것이 문서와 어긋난 채 잊힌다

Terraform은 인프라를 선언하고, 현재 상태와 비교해 차이만 반영한다. Stage 8의 쿠버네티스와 같은 발상이 클라우드 자원 전체로 확장된 것이다. 그리고 그 선언이 Git에 있으니 Stage 3의 리뷰·이력·되돌리기가 전부 따라온다.

2. HCL 기초

# main.tf
terraform {
  required_version = "~> 1.9"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.60"          # 버전을 고정한다 (Stage 7의 latest 교훈)
    }
  }
}

provider "aws" {
  region = var.region
}

resource "aws_vpc" "main" {
  cidr_block           = "10.0.0.0/16"      # Stage 2의 CIDR
  enable_dns_hostnames = true

  tags = {
    Name        = "weatherboard"
    Environment = var.environment
    ManagedBy   = "terraform"               # 손으로 만든 것과 구분
  }
}

resource "aws_subnet" "public" {
  vpc_id                  = aws_vpc.main.id      # ← 참조가 의존 관계를 만든다
  cidr_block              = "10.0.1.0/24"
  map_public_ip_on_launch = true
}

aws_vpc.main.id처럼 다른 리소스를 참조하면 Terraform이 순서를 알아서 결정한다. VPC가 먼저 생기고 서브넷이 그다음이다. 의존 관계를 직접 적을 일은 거의 없다.

data이미 존재하는 것을 읽기만 한다

locals파일 안에서만 쓰는 계산된 값

data "aws_ami" "ubuntu" {          # 최신 우분투 AMI를 찾아온다 (만들지 않는다)
  most_recent = true
  owners      = ["099720109477"]
  filter {
    name   = "name"
    values = ["ubuntu/images/hvm-ssd/ubuntu-jammy-22.04-amd64-server-*"]
  }
}

locals {
  name_prefix = "${var.environment}-weatherboard"
  common_tags = {
    Environment = var.environment
    ManagedBy   = "terraform"
  }
}

반복

resource "aws_subnet" "public" {
  for_each = {
    a = { cidr = "10.0.1.0/24", az = "ap-northeast-2a" }
    c = { cidr = "10.0.2.0/24", az = "ap-northeast-2c" }
  }

  vpc_id            = aws_vpc.main.id
  cidr_block        = each.value.cidr
  availability_zone = each.value.az
  tags              = merge(local.common_tags, { Name = "${local.name_prefix}-${each.key}" })
}

⚠ count보다 for_each를 쓴다

count는 자원을 인덱스로 추적한다([0], [1]). 중간 항목을 지우면 뒤의 것들이 한 칸씩 밀려서, 바꿀 생각도 없던 자원이 파괴·재생성된다. for_each는 키로 추적하므로 이 문제가 없다. 개수만 세는 게 아니라면 for_each가 기본이다.

3. init · plan · apply

terraform init            # 프로바이더 다운로드, 백엔드 설정
terraform fmt -recursive  # 포맷 정리
terraform validate        # 문법과 참조 검사 (클라우드에 접속하지 않는다)
terraform plan            # 무엇이 바뀔지 보여준다 ← 항상 읽는다
terraform apply           # 실제로 반영 (한 번 더 확인을 묻는다)
terraform destroy         # 전부 삭제

plan 출력을 읽는 법이 이 단계의 핵심 기술이다.

Terraform will perform the following actions:

  # aws_subnet.public["c"] will be created
  + resource "aws_subnet" "public" {
      + cidr_block = "10.0.2.0/24"
    }

  # aws_instance.app will be updated in-place
  ~ resource "aws_instance" "app" {
      ~ instance_type = "t3.micro" -> "t3.small"
    }

  # aws_db_instance.main must be replaced
-/+ resource "aws_db_instance" "main" {
      ~ engine_version = "15.4" -> "16.1" # forces replacement
    }

Plan: 2 to add, 1 to change, 1 to destroy.
기호뜻주의
+생성비용이 는다
~제자리 수정대개 안전
-삭제멈추고 확인한다
-/+파괴 후 재생성가장 위험. 데이터가 사라질 수 있다

⚠ forces replacement를 그냥 넘기지 않는다

어떤 속성은 수정할 수 없어서 자원을 지웠다 다시 만든다. DB나 볼륨이라면 데이터가 사라진다. plan에 -/+가 보이면 그 자원이 무엇인지, 데이터가 있는지, 다운타임이 얼마나 되는지 확인하기 전에는 apply하지 않는다. 막아야 한다면 lifecycle { prevent_destroy = true }를 걸어 둔다.

terraform plan -out=tfplan     # 계획을 파일로 저장
terraform apply tfplan         # 저장한 그 계획을 그대로 적용 (사이에 바뀌어도 안전)

파이프라인에서는 이 두 단계 분리가 필수다. plan을 사람이 검토하고 승인한 바로 그 계획이 적용되어야 하기 때문이다.

4. state — 가장 중요한 개념

Terraform은 "내가 만든 자원이 무엇이고 어떤 속성인지"를 terraform.tfstate에 기록한다. 코드와 실제 인프라를 잇는 지도다.

terraform state list                    # 관리 중인 자원 목록
terraform state show aws_vpc.main       # 하나의 상세
terraform show                          # 전체

state가 없으면 Terraform은 aws_vpc.main이 실제 어느 VPC인지 모른다. 그래서 다음 세 가지가 따라온다.

  • state를 잃으면 Terraform은 자원들을 처음 만드는 것으로 여겨 중복 생성한다
  • state에 비밀이 들어간다 — DB 비밀번호 같은 값이 평문으로 저장된다
  • 동시에 두 사람이 apply하면 state가 깨진다

⚠ tfstate를 Git에 커밋하지 않는다

비밀이 평문으로 들어 있고(Stage 3의 "커밋한 비밀은 영원하다"), 동시 작업 시 충돌이 나며, 병합으로 해결할 수도 없다. .gitignore에 넣고 원격 백엔드를 쓴다.

*.tfstate
*.tfstate.*
.terraform/
*.tfvars        # 값이 민감할 수 있다 (예시용 .tfvars.example만 커밋)

5. 원격 백엔드와 잠금

terraform {
  backend "s3" {
    bucket       = "mycompany-tfstate"
    key          = "weatherboard/prod/terraform.tfstate"
    region       = "ap-northeast-2"
    encrypt      = true
    use_lockfile = true          # S3 네이티브 잠금 (Terraform 1.10+)
  }
}

원격 백엔드는 세 가지를 해결한다. state를 팀이 공유하고, 저장 시 암호화하고, apply 중에는 잠금을 걸어 동시 실행을 막는다.

💡 잠금 방식이 최근 바뀌었다

오래된 문서는 잠금에 DynamoDB 테이블을 쓰라고 한다(dynamodb_table). Terraform 1.10부터는 S3 자체 조건부 쓰기를 이용하는 use_lockfile = true가 들어와서 별도 테이블이 필요 없다. 쓰는 버전에 맞춰 고르자.

terraform force-unlock <LOCK_ID>    # apply가 중간에 죽어 잠금이 남았을 때만

force-unlock은 정말 아무도 실행 중이 아닐 때만 쓴다. 돌고 있는 apply의 잠금을 풀면 state가 깨진다.

환경 분리

dev와 prod를 나누는 방법은 두 가지다.

방법모양평가
workspace같은 코드, state만 분리간단하지만 환경별 차이를 표현하기 어렵다
디렉터리 분리envs/dev/, envs/prod/가 각자 백엔드를 가짐권장. 명시적이고 실수하기 어렵다

workspace는 "지금 어느 workspace인가"를 잊고 prod에 apply하는 사고가 나기 쉽다. 디렉터리가 분리되어 있으면 cd하는 순간 눈에 보인다.

6. 변수와 출력

# variables.tf
variable "region" {
  description = "배포할 리전"
  type        = string
  default     = "ap-northeast-2"
}

variable "environment" {
  description = "환경 이름"
  type        = string
  validation {
    condition     = contains(["dev", "staging", "prod"], var.environment)
    error_message = "environment는 dev, staging, prod 중 하나여야 한다."
  }
}

variable "instance_count" {
  type    = number
  default = 2
}

variable "db_password" {
  type      = string
  sensitive = true          # 출력에서 가려진다 (state에는 평문으로 남는다)
}
# outputs.tf
output "vpc_id" {
  value = aws_vpc.main.id
}

output "app_url" {
  description = "서비스 주소"
  value       = "https://${aws_lb.main.dns_name}"
}

값을 주는 방법은 여럿이고 우선순위가 있다(뒤가 이긴다).

terraform apply                                   # 1. 기본값, 없으면 물어본다
export TF_VAR_environment=prod                    # 2. 환경변수
terraform apply -var-file=prod.tfvars             # 3. 파일
terraform apply -var="environment=prod"           # 4. 명령행 (가장 강함)

⚠ sensitive는 출력만 가린다

sensitive = true는 CLI 출력과 로그에서 값을 (sensitive value)로 가려 준다. 하지만 state 파일에는 평문으로 저장된다. 진짜 비밀은 Terraform 변수로 넘기지 말고 클라우드의 시크릿 관리 서비스에 두고, Terraform은 그 참조만 다루는 것이 낫다. Stage 14에서 다시 다룬다.

7. 모듈

같은 구성을 환경마다 복사하기 시작하면 모듈로 뽑을 때다.

modules/
└── network/
    ├── main.tf
    ├── variables.tf
    └── outputs.tf
envs/
├── dev/
│   ├── main.tf
│   └── backend.tf
└── prod/
    ├── main.tf
    └── backend.tf
# envs/prod/main.tf
module "network" {
  source = "../../modules/network"

  environment = "prod"
  vpc_cidr    = "10.1.0.0/16"
  azs         = ["ap-northeast-2a", "ap-northeast-2c"]
}

resource "aws_instance" "app" {
  subnet_id = module.network.public_subnet_ids[0]   # 모듈의 output을 참조
  # ...
}

모듈은 함수와 같다. 입력(variable)을 받아 자원을 만들고 출력(output)을 돌려준다. 안의 구현은 밖에서 보이지 않는다.

module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"     # 공개 레지스트리
  version = "5.13.0"                             # ← 반드시 고정한다
  # ...
}

💡 모듈을 언제 만드나

처음부터 모듈로 쪼개지 말자. 같은 것을 세 번째 쓰게 될 때 뽑는 것이 적당하다. 너무 이르게 추상화한 모듈은 실제 요구가 나올 때마다 변수를 늘리게 되고, 결국 아무것도 감추지 못하는 껍데기가 된다.

8. 드리프트와 import

누군가 콘솔에서 손으로 고치면 코드와 실제가 어긋난다. 이것이 드리프트다.

terraform plan                       # 드리프트가 있으면 여기서 차이로 나타난다
terraform plan -refresh-only         # 코드는 그대로 두고 실제 상태만 비교

plan이 아무것도 안 바꾼다고 나와야 정상이다. 뭔가 나온다면 코드가 실제를 반영하지 못하고 있다는 뜻이고, 둘 중 하나를 골라야 한다 — 코드를 실제에 맞추거나, apply로 실제를 코드에 맞추거나.

손으로 만든 자원을 코드로 가져오기

# import.tf — Terraform 1.5+의 선언적 import
import {
  to = aws_vpc.main
  id = "vpc-0a1b2c3d4e5f"
}
terraform plan -generate-config-out=generated.tf    # 코드까지 생성해 준다
terraform apply                                      # state에 편입

예전에는 terraform import 명령으로 했고 코드는 직접 써야 했다. 지금은 블록으로 선언하면 plan에서 미리 확인할 수 있어 훨씬 안전하다.

terraform state mv aws_instance.old aws_instance.new   # 이름을 바꿨을 때
terraform state rm aws_instance.gone                   # 관리에서 뺀다 (자원은 안 지운다)

⚠ 리소스 이름을 바꾸면 파괴·재생성이 된다

Terraform은 aws_instance.app을 이름으로 추적한다. 코드에서 이름만 aws_instance.server로 바꾸면, Terraform은 "app은 사라지고 server가 새로 생겼다"고 이해한다. state mv로 옮기거나 moved 블록을 쓰면 파괴 없이 이름만 바뀐다.

moved {
  from = aws_instance.app
  to   = aws_instance.server
}

9. 파이프라인에 태우기

Stage 9의 파이프라인에 Terraform을 얹는 표준 형태는 이렇다 — PR에서 plan을 보여주고, 머지 후 apply한다.

jobs:
  plan:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      id-token: write            # OIDC (Stage 9)
      pull-requests: write       # plan 결과를 PR에 코멘트
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ vars.AWS_ROLE_ARN }}
          aws-region: ap-northeast-2
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
      - run: terraform fmt -check -recursive
      - run: terraform validate
      - run: terraform plan -no-color -out=tfplan
      - uses: actions/upload-artifact@v4
        with: { name: tfplan, path: tfplan }

  apply:
    needs: [plan]
    if: github.ref == 'refs/heads/main'
    environment: production       # 사람의 승인을 받는다
    runs-on: ubuntu-latest
    steps:
      # ... 같은 인증 절차 ...
      - uses: actions/download-artifact@v4
        with: { name: tfplan }
      - run: terraform apply -auto-approve tfplan

핵심은 PR에서 본 그 plan이 그대로 적용된다는 점이다. 아티팩트로 넘기지 않고 apply 단계에서 plan을 다시 돌리면, 그 사이에 인프라가 바뀌었을 때 리뷰하지 않은 변경이 적용될 수 있다.

자주 하는 실수

Error acquiring the state lock

Error: Error acquiring the state lock
Lock Info:
  ID:        3f2a...
  Operation: OperationTypeApply
  Who:       ci-runner@fv-az123
  Created:   2026-08-25 07:12:03 UTC

다른 누군가(또는 CI)가 apply 중이거나, 이전 실행이 잠금을 남긴 채 죽은 것이다. 먼저 확인한다 — Who와 Created를 보고 정말 죽은 잠금인지 판단한다. 돌고 있는 작업이 없다는 것이 확실할 때만 terraform force-unlock <ID>다.

plan에 예상치 못한 파괴가 들어 있다

Plan: 3 to add, 0 to change, 3 to destroy.

apply를 치기 전에 반드시 왜인지 밝힌다. 흔한 원인 셋이다.

  1. 리소스 이름을 바꿨다 → moved 블록이나 state mv
  2. count의 중간 항목을 지웠다 → for_each로 옮긴다
  3. 수정 불가 속성을 바꿨다 → plan의 forces replacement를 찾는다

Provider produced inconsistent final plan

프로바이더 버그이거나 버전 불일치인 경우가 많다. .terraform.lock.hcl을 커밋해 팀 전체가 같은 프로바이더 버전을 쓰게 하는 것이 예방책이다. 이 파일은 커밋해야 한다(.terraform/ 디렉터리와 헷갈리지 말 것).

state를 잃어버렸다

로컬 state를 지웠거나 백엔드 설정을 잘못 바꾼 경우다. Terraform은 자원들을 처음 만드는 것으로 여겨 중복 생성하려 한다. plan에 이미 있는 자원이 전부 +로 나오면 이것을 의심한다. 복구는 백업에서 state를 되살리거나, import로 하나씩 되찾는 것이다. 그래서 원격 백엔드에 버전 관리를 켜 둔다 — S3라면 버킷 버저닝이다.

apply가 중간에 실패했다

Terraform은 트랜잭션이 아니다. 절반쯤 만들어진 상태로 멈춘다. 당황하지 말고 원인을 고친 뒤 다시 apply하면, 이미 만들어진 것은 건너뛰고 나머지를 이어서 만든다. state를 손으로 고치려 하지 말자 — 상황을 더 나쁘게 만든다.

직접 해보기

과제 1 — 클라우드 없이 워크플로 익히기

계정이 없어도 된다. local과 random 프로바이더로 연습한다.

terraform {
  required_providers {
    random = { source = "hashicorp/random", version = "~> 3.6" }
    local  = { source = "hashicorp/local",  version = "~> 2.5" }
  }
}

resource "random_pet" "name" {
  length = 2
}

resource "local_file" "greeting" {
  filename = "${path.module}/hello.txt"
  content  = "hello, ${random_pet.name.id}\n"
}

output "pet" {
  value = random_pet.name.id
}

검증: apply 후 파일이 생겼는가. terraform state list에 자원 둘이 보이는가. random_pet의 length를 바꾸면 plan에 -/+가 나오고 파일도 함께 바뀌는 이유를 설명할 수 있는가.

과제 2 — plan 읽기 훈련

이 과제가 이 단계의 핵심이다. 과제 1의 구성에서 다음을 각각 시도하고 plan의 요약 줄(N to add, N to change, N to destroy)을 기록한다.

  1. content만 바꾼다
  2. filename을 바꾼다
  3. 리소스 이름을 local_file.greeting → local_file.msg로 바꾼다
  4. 3번을 moved 블록으로 다시 한다

검증: 3번과 4번의 plan이 어떻게 다른가. moved 없이 이름을 바꾸면 왜 파괴가 생기는지 설명할 수 있는가.

과제 3 — state를 들여다보기

terraform state list
terraform state show local_file.greeting
cat terraform.tfstate | python3 -m json.tool | head -40

state 파일을 직접 열어 구조를 본다. 그다음 terraform state rm으로 자원 하나를 관리에서 빼고 plan이 어떻게 달라지는지, 실제 파일은 어떻게 됐는지 확인한다.

검증: state rm 후 실제 파일이 남아 있는가(삭제가 아니다). plan이 그것을 새로 만들려 하는가. 이것이 "state를 잃으면 중복 생성된다"와 같은 현상임을 이해했는가.

과제 4 — 모듈로 뽑기

과제 1의 구성을 modules/greeting/으로 옮기고, envs/dev와 envs/prod에서 각각 다른 입력으로 호출한다. 두 환경의 state는 분리한다.

검증: 한 환경에서 destroy해도 다른 환경이 멀쩡한가. 두 state 파일이 실제로 다른 위치에 있는가.
