Networking Fundamentals

OSI/TCP-IP, IP·서브넷, DNS, HTTP, 방화벽. 장애의 절반은 네트워크에서 시작됩니다.

예상 16시간 완료

이 단계를 끝내면

  • "접속이 안 돼요"를 듣고 DNS·라우팅·방화벽·애플리케이션 중 어디가 끊겼는지 근거를 대고 좁힐 수 있다.
  • Connection refused와 Connection timed out이 각각 무엇을 말해주는지 구분할 수 있다.
  • 서버에서 어떤 포트가 누구에게 열려 있는지 확인하고 설명할 수 있다.
  • 도메인이 IP로 바뀌는 과정을 단계별로 추적할 수 있다.
  • curl -v 출력을 읽고 TLS 핸드셰이크와 HTTP 요청·응답을 분리해서 볼 수 있다.

준비물

  • Stage 1의 리눅스 환경. 셸에서 명령을 실행할 수 있으면 된다.

💡 오래된 명령을 쓰지 말자

ifconfig, netstat, route는 대부분의 배포판에서 기본 설치조차 되지 않는다. 각각 ip addr, ss, ip route가 대체한다. 인터넷의 오래된 글은 아직도 옛 명령을 알려주니, 검색 결과를 그대로 믿지 말고 새 도구를 익히자.

1. 계층으로 쪼개서 본다

네트워크 장애를 잘 다루는 사람과 그렇지 않은 사람의 차이는 지식의 양이 아니라 쪼개는 습관이다. "안 된다"는 하나의 문제가 아니라 여러 층 중 하나가 끊긴 것이고, 각 층은 서로 다른 명령으로 확인한다.

층하는 일대표이걸로 확인한다
L2 링크같은 네트워크 안에서 프레임 전달Ethernet, ARPip link, ip neigh
L3 네트워크다른 네트워크까지 패킷 전달IP, ICMPip addr, ip route, ping
L4 전송포트로 프로세스 구분, 신뢰성TCP, UDPss, nc -zv
L7 응용실제 주고받는 내용HTTP, DNS, TLScurl -v, dig

OSI 7계층을 외울 필요는 없다. 실무에서 쓰는 건 위 네 개고, 진단은 언제나 아래층부터 올라간다. IP가 안 닿는데 HTTP 응답을 들여다보는 것은 시간 낭비다.

2. IP 주소와 서브넷

ip addr show
# 2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 ...
#     inet 10.0.1.24/24 brd 10.0.1.255 scope global eth0

10.0.1.24/24에서 /24가 서브넷 마스크다. 앞 24비트가 네트워크, 나머지 8비트가 호스트라는 뜻이다. 같은 네트워크에 있는 상대에게는 라우터를 거치지 않고 바로 보내고, 아니면 게이트웨이로 보낸다. 이 한 줄이 "왜 저 서버에는 닿고 이 서버에는 안 닿나"의 답인 경우가 많다.

표기호스트 수범위 예시흔한 쓰임
/2425410.0.1.0 – 10.0.1.255작은 서브넷 하나
/1665,53410.0.0.0 – 10.0.255.255VPC 전체
/32110.0.1.24 하나방화벽 규칙에서 한 대만 지정
0.0.0.0/0전부모든 IP"어디서나" — 방화벽에서 조심

사설 IP 대역은 인터넷에 라우팅되지 않는다. 사내망이나 클라우드 VPC에서 쓰는 주소다.

  • 10.0.0.0/8 — 클라우드 VPC에서 가장 흔하다
  • 172.16.0.0/12 — Docker 기본 브리지가 이 대역을 쓴다
  • 192.168.0.0/16 — 가정용 공유기
  • 127.0.0.0/8 — 루프백. 자기 자신이다

3. 라우팅 — 이 패킷은 어디로 가나

ip route
# default via 10.0.1.1 dev eth0
# 10.0.1.0/24 dev eth0 proto kernel scope link src 10.0.1.24

ip route get 8.8.8.8      # 이 목적지로는 어떤 경로를 쓰나 — 추측하지 말고 물어보자
# 8.8.8.8 via 10.0.1.1 dev eth0 src 10.0.1.24

커널은 목적지에 가장 구체적으로 맞는 규칙을 고른다. 10.0.1.5로 보낼 때는 두 번째 줄(같은 서브넷이니 직접 전달)을, 8.8.8.8로 보낼 때는 매칭되는 게 default뿐이라 게이트웨이 10.0.1.1로 넘긴다.

ping -c 3 10.0.1.1          # 게이트웨이까지는 닿나
traceroute 8.8.8.8          # 어느 홉에서 멈추나
mtr 8.8.8.8                 # traceroute + ping을 실시간으로 (설치 필요)

⚠ ping이 안 된다고 서버가 죽은 것은 아니다

ping은 ICMP를 쓴다. 클라우드 보안 그룹과 많은 방화벽이 ICMP를 기본으로 막는다. 웹 서버는 멀쩡히 80/443을 응답하면서 ping에는 무응답인 경우가 흔하다. 살아 있는지 보려면 실제 쓰는 포트로 확인하는 게 맞다: nc -zv host 443.

4. 포트와 소켓, 그리고 TCP

IP가 건물 주소라면 포트는 호수다. 한 서버에서 여러 프로그램이 각자의 포트를 잡고 기다린다.

ss -lntp
# State  Recv-Q Send-Q Local Address:Port  Peer Address:Port Process
# LISTEN 0      511          0.0.0.0:80         0.0.0.0:*     users:(("nginx",pid=1234,fd=6))
# LISTEN 0      128        127.0.0.1:5432       0.0.0.0:*     users:(("postgres",pid=980,fd=5))

플래그는 -l 리스닝만, -n 이름 해석 없이 숫자로, -t TCP, -p 프로세스 표시다(-p는 보통 sudo가 필요하다). UDP는 -u다.

💡 Local Address의 앞부분이 핵심이다

0.0.0.0:80은 모든 인터페이스에서 받는다는 뜻이고, 127.0.0.1:5432는 이 서버 안에서만 접속할 수 있다는 뜻이다. "로컬에서는 되는데 밖에서는 안 붙어요"의 첫 번째 용의자가 바로 이 차이다.

TCP 연결이 맺어지는 과정

TCP는 데이터를 보내기 전에 3-way 핸드셰이크로 연결을 맺는다. 이 과정이 어디서 실패하느냐가 에러 메시지를 결정한다.

  1. 클라이언트 → 서버: SYN ("연결하자")
  2. 서버 → 클라이언트: SYN-ACK ("좋다")
  3. 클라이언트 → 서버: ACK ("시작하자")
결과무슨 일이 있었나어디를 보나
Connection refused패킷은 도착했고 서버가 RST로 거절했다. 그 포트에 뜬 프로세스가 없다서비스가 떠 있나, 바인딩 주소가 맞나
Connection timed out응답이 아예 없다. 중간에서 조용히 버려졌다방화벽, 보안 그룹, 라우팅
연결은 되는데 응답이 느림연결은 맺어졌고 애플리케이션이 답을 못 준다애플리케이션, 백엔드 DB

이 표 하나가 이 단계에서 가장 실용적인 지식이다. refused는 서버 문제, timeout은 길 문제로 시작하면 절반은 맞다.

nc -zv example.com 443     # 이 포트가 열려 있나 (연결만 하고 끊는다)
# Connection to example.com (93.184.215.14) 443 port [tcp/https] succeeded!

ss -ant state established  # 지금 맺어진 연결들
ss -s                      # 소켓 요약 통계

UDP는 다르다

UDP는 핸드셰이크가 없다. 보내고 잊는다. DNS, 일부 로그 전송, 게임 트래픽이 쓴다. 응답이 없어도 "연결 실패"라는 개념 자체가 없으므로, UDP 문제는 애플리케이션 레벨에서 타임아웃으로만 드러난다.

5. DNS — 이름이 주소가 되기까지

dig example.com

# ;; ANSWER SECTION:
# example.com.    3600  IN  A  93.184.215.14
#                  ^^^^                ^^^^^^
#                  TTL(초)             결과 IP

TTL은 이 답을 몇 초간 캐시해도 되는지다. DNS를 바꿨는데 반영이 안 된다면 거의 언제나 이 값 때문이다. 배포 전에 TTL을 미리 낮춰 두는 것이 관례다.

레코드뜻흔한 용도
A이름 → IPv4가장 기본
AAAA이름 → IPv6IPv6 지원
CNAME이름 → 다른 이름CDN, 로드밸런서 앞단
MX메일 서버메일 수신
TXT임의 문자열도메인 소유 증명, SPF
NS이 도메인의 권한 서버위임 확인

조회 과정을 눈으로 보기

dig +trace example.com     # 루트 → TLD → 권한 서버 순으로 따라간다
dig +short example.com     # 결과만
dig @8.8.8.8 example.com   # 특정 리졸버에게 직접 물어본다 (캐시 우회 확인)
dig NS example.com         # 이 도메인은 누가 관리하나

@8.8.8.8로 물었을 때와 기본 리졸버로 물었을 때 답이 다르면, 문제는 도메인이 아니라 내가 쓰는 리졸버의 캐시다.

💡 시스템은 dig와 다른 길로 갈 수 있다

dig는 DNS 서버에 직접 묻지만, 애플리케이션은 시스템 리졸버를 통한다. 그래서 /etc/hosts에 항목이 있으면 dig는 진짜 DNS 답을 보여주는데 curl은 다른 곳으로 간다. 둘이 다를 땐 getent hosts example.com으로 시스템이 실제로 쓰는 답을 확인한다.

6. HTTP와 TLS

curl -v 한 줄에 이 단계의 거의 모든 층이 담겨 있다. 출력을 읽는 법을 익히자.

curl -v https://example.com

# * Connected to example.com (93.184.215.14) port 443      ← L3/L4: 연결 성공
# * TLSv1.3 (OUT), TLS handshake, Client hello (1):        ← TLS 시작
# * SSL certificate verify ok.                             ← 인증서 검증 통과
# > GET / HTTP/2                                           ← 내가 보낸 요청
# > Host: example.com
# < HTTP/2 200                                             ← 서버 응답
# < content-type: text/html

*는 curl의 진단 메시지, >는 보낸 것, <는 받은 것이다. 어디까지 진행됐는지만 봐도 어느 층에서 끊겼는지 바로 나온다.

자주 쓰는 curl 옵션

curl -I https://example.com              # 헤더만 (HEAD 요청)
curl -sS -o /dev/null -w '%{http_code} %{time_total}s\n' https://example.com
curl -L https://example.com              # 리다이렉트를 따라간다
curl --resolve example.com:443:10.0.1.24 https://example.com/   # DNS를 무시하고 이 IP로
curl -k https://self-signed.local        # 인증서 검증 건너뛰기 (진단용으로만)

⚠ -k 는 진단 도구지 해결책이 아니다

-k로 넘어가면 "인증서가 문제"라는 것만 확인된 것이다. 그 상태로 스크립트나 서비스에 -k를 박아 두면 중간자 공격에 그대로 노출된다. 원인(만료, 체인 누락, 호스트명 불일치)을 찾아 고치는 데까지 가야 한다.

알아둘 상태 코드

코드뜻보통 누구 잘못인가
301 / 302영구 / 임시 이동정상. -L로 따라가 보자
401 / 403인증 필요 / 권한 없음자격 증명, 권한 설정
404없는 경로라우팅 설정 또는 오타
500애플리케이션이 터졌다애플리케이션 로그를 본다
502프록시가 백엔드에서 잘못된 응답을 받았다백엔드가 죽었거나 프록시 주소가 틀렸다
504프록시가 백엔드를 기다리다 지쳤다백엔드가 느리다. 타임아웃 설정

502와 504의 구분은 Stage 6(웹 서버)에서 다시 쓴다. 둘 다 "프록시는 살아 있고 그 뒤가 문제"라는 신호다.

TLS 들여다보기

echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null \
  | openssl x509 -noout -dates -subject -issuer
# notBefore=Jan  1 00:00:00 2026 GMT
# notAfter=Apr  1 23:59:59 2026 GMT      ← 만료일. 장애의 단골 원인
# subject=CN = example.com
# issuer=C = US, O = Let's Encrypt, CN = R11

-servername은 SNI다. 한 IP에 여러 도메인의 인증서가 있을 때 어느 것을 달라고 지정한다. 이걸 빼면 엉뚱한 인증서를 받아 보고 "인증서가 틀렸다"고 오진하게 된다.

7. NAT과 방화벽

사설 IP를 쓰는 서버가 인터넷과 통신할 수 있는 것은 NAT 덕분이다. 나갈 때 출발지 주소를 공인 IP로 바꾸고, 돌아오는 응답을 원래 주인에게 되돌려준다. 그래서 나가는 연결은 되는데 들어오는 연결은 안 되는 비대칭이 기본값이다.

리눅스 방화벽

sudo ufw status verbose        # Ubuntu의 간편 방화벽
sudo ufw allow 443/tcp
sudo ufw allow from 10.0.1.0/24 to any port 5432 proto tcp   # 특정 대역에만

sudo nft list ruleset          # 실제 규칙 전체 (nftables)
sudo iptables -L -n -v         # 구형 도구. 아직 많이 보인다

⚠ 원격 서버에서 방화벽을 만질 때

SSH 포트를 막으면 그 순간 자기 자신이 잠긴다. 규칙을 바꾸기 전에 SSH를 명시적으로 허용해 두고(sudo ufw allow 22/tcp), 접속 중인 세션은 끊지 말고 새 터미널로 접속이 되는지 확인한 뒤 원래 세션을 닫는다.

클라우드에서는 층이 하나 더 있다

클라우드 인스턴스는 OS 방화벽 바깥에 보안 그룹(AWS)이나 방화벽 규칙(GCP)이 또 있다. 둘 다 통과해야 패킷이 도착한다. "OS 방화벽은 다 열었는데 안 된다"면 바깥층을 보면 된다. 이 층은 대개 timeout을 만들고, OS 방화벽의 REJECT는 refused를 만든다.

8. 진단 도구 상자

확인할 것명령
내 IP와 인터페이스ip addr
이 목적지로 가는 경로ip route get <IP>
중간에 어디서 막히나traceroute <host>, mtr <host>
내가 여는 포트ss -lntup
상대 포트가 열렸나nc -zv <host> <port>
이름이 어떤 IP로 풀리나dig +short <name>, getent hosts <name>
HTTP/TLS 전 과정curl -v <url>
인증서 상세openssl s_client -connect host:443 -servername host
진짜 패킷이 오가나sudo tcpdump -ni any port 443

tcpdump는 마지막 수단이다. 위 도구들이 서로 모순되는 답을 줄 때, 실제로 패킷이 오는지 아닌지를 확인해 논쟁을 끝낸다.

sudo tcpdump -ni any port 443 -c 20        # 20개만 잡고 종료
sudo tcpdump -ni eth0 host 10.0.1.5        # 이 상대와의 트래픽만

9. 장애 분류 순서

"안 돼요"를 받았을 때 위에서부터 순서대로 내려간다. 각 단계는 다음 단계를 볼 필요가 있는지 결정한다. 이 순서를 외워 두면 낯선 장애에서도 헤매지 않는다.

  1. 이름이 풀리나? dig +short api.example.com
    결과가 없으면 DNS 문제다. 여기서 끝. 아니면 다음으로.
  2. 그 IP가 내가 기대한 IP인가?
    옛 IP가 나온다면 캐시나 TTL 문제다. dig @8.8.8.8로 대조한다.
  3. 그 IP까지 닿나? traceroute <IP>
    중간에서 멈추면 라우팅이나 경로상의 방화벽이다.
  4. 포트가 열려 있나? nc -zv <IP> <port>
    timed out → 방화벽/보안 그룹. refused → 서버에 그 포트로 뜬 프로세스가 없다.
  5. (서버에서) 정말 그 주소로 듣고 있나? sudo ss -lntp | grep <port>
    127.0.0.1에만 묶여 있으면 밖에서는 영원히 안 붙는다.
  6. TLS가 성립하나? curl -v https://...의 handshake 부분
    인증서 만료, 호스트명 불일치, 체인 누락을 여기서 잡는다.
  7. 애플리케이션이 답하나? 상태 코드와 응답 시간
    여기까지 왔다면 네트워크는 무죄다. 애플리케이션 로그로 넘어간다.

✓ 이 순서의 핵심

각 단계는 다음 단계를 건너뛸 수 있는지를 알려준다. 1번에서 실패하면 2~7번은 볼 필요가 없다. 위에서부터 내려가는 습관이 없으면, 사람들은 대개 7번(애플리케이션 로그)부터 들여다보다가 한 시간을 쓴다.

자주 하는 실수

Connection refused 를 방화벽 문제로 오해한다

curl http://10.0.1.24:8080
# curl: (7) Failed to connect to 10.0.1.24 port 8080: Connection refused

refused는 패킷이 도착했다는 증거다. 서버의 커널이 "그 포트엔 아무도 없다"며 RST를 돌려준 것이다. 방화벽이 막았다면 대개 아무 응답도 없어 timed out이 난다. 그러니 여기서 볼 것은 방화벽이 아니라 서비스다 — 떠 있는지, 그리고 어느 주소에 묶였는지.

sudo ss -lntp | grep 8080     # 아무것도 안 나오면 서비스가 안 떠 있는 것

로컬에서는 되는데 밖에서는 안 붙는다

sudo ss -lntp | grep 8080
# LISTEN 0 128 127.0.0.1:8080 0.0.0.0:* users:(("python3",pid=4521,fd=3))

127.0.0.1에만 바인딩되어 있다. 서버 안에서 curl localhost:8080은 되지만 외부에서는 절대 붙지 않는다. 애플리케이션의 바인드 주소를 0.0.0.0으로 바꿔야 한다 (많은 프레임워크의 기본값이 127.0.0.1이다).

⚠ 다만 0.0.0.0이 항상 정답은 아니다

데이터베이스처럼 밖에서 붙으면 안 되는 것은 127.0.0.1에 묶어 두는 게 맞다. "밖에서 안 붙는다"가 의도된 설계인 경우를 먼저 의심하자.

DNS를 바꿨는데 반영이 안 된다

dig +short api.example.com          # 10.0.1.9  (옛 IP)
dig +short @8.8.8.8 api.example.com # 10.0.1.24 (새 IP)

권한 서버는 이미 새 값을 주고 있는데 내 리졸버가 옛 답을 TTL 동안 붙들고 있는 것이다. 기다리는 것 외에 방법이 없다 — 그래서 IP를 바꿀 계획이 있으면 며칠 전에 미리 TTL을 60초 같은 낮은 값으로 내려 둔다. 로컬 캐시는 이렇게 비운다.

resolvectl flush-caches       # systemd-resolved를 쓰는 경우
resolvectl status             # 어떤 리졸버를 쓰고 있는지

curl은 되는데 브라우저는 안 된다

대개 셋 중 하나다. (1) 브라우저는 HSTS 때문에 https를 강제하는데 서버가 http만 연다. (2) 인증서 체인이 불완전해서 — 중간 인증서를 빼먹으면 curl은 시스템 저장소에서 알아서 찾아내지만 브라우저는 실패한다. (3) 회사 프록시나 VPN이 끼어 있다. 체인은 이렇게 확인한다.

echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null \
  | grep -E "^ *[0-9]+ s:|^ *i:"
# 인증서가 서버 → 중간 → (루트) 순으로 나와야 한다. 서버 것만 나오면 체인 누락

포트를 열었는데도 timeout 이다

클라우드에서는 층이 둘이다. OS 방화벽(ufw)과 보안 그룹. ufw만 열고 보안 그룹을 안 열면 패킷은 인스턴스 근처에도 못 온다. 서버에서 tcpdump로 확인하면 논쟁이 끝난다.

sudo tcpdump -ni any port 8080
# 클라이언트에서 접속 시도할 때 아무것도 안 잡히면 → 패킷이 도착조차 못 함 (바깥층 문제)
# SYN은 잡히는데 응답이 없으면 → 서버 안쪽 문제

직접 해보기

과제 1 — 내 서버의 포트 지도

지금 서버에서 열려 있는 모든 TCP/UDP 포트를 나열하고, 각각에 대해 세 가지를 적는다. 어떤 프로세스인가, 어느 주소에 묶였나(전체 공개인가 로컬 전용인가), 밖에 열려 있어야 하는 게 맞나.

sudo ss -lntup

검증: 0.0.0.0에 묶인 포트마다 "왜 밖에 열려 있어야 하는지" 한 줄로 답할 수 있는가. 답하지 못하는 포트가 있다면 그건 닫아야 할 후보다.

과제 2 — DNS 조회를 끝까지 추적

dig +trace example.com

출력에서 루트 서버 → TLD(.com) 서버 → 권한 서버로 넘어가는 지점을 짚고, 최종 답을 준 서버가 누구인지 확인한다. 그다음 dig NS example.com과 대조한다.

검증: 최종 A 레코드를 준 서버가 NS 레코드에 있는 서버 중 하나인가.

과제 3 — refused와 timeout을 직접 만들어 보기

이 과제가 이 단계의 핵심이다. 두 에러를 눈으로 구분해 보면 다시는 헷갈리지 않는다.

# 1) 아무것도 안 뜬 포트로 접속 → refused
nc -zv 127.0.0.1 9999

# 2) 서버를 하나 띄우고 접속 → 성공
python3 -m http.server 9999 &
nc -zv 127.0.0.1 9999

# 3) 방화벽으로 조용히 버리게 만든 뒤 접속 → timeout
sudo iptables -I INPUT -p tcp --dport 9999 -j DROP
nc -zv -w 5 <이-서버의-사설IP> 9999

# 정리
sudo iptables -D INPUT -p tcp --dport 9999 -j DROP
kill %1

⚠ 3번은 반드시 정리한다

-I로 넣은 규칙은 재부팅 전까지 남는다. 같은 규칙을 -D로 지워야 한다. SSH 포트(22)에는 절대 시도하지 말 것.

검증: 1번은 즉시 refused, 3번은 5초를 기다린 뒤 timed out이 나는가. 이 시간 차이(즉시 vs 대기)도 실전에서 유용한 단서다.

과제 4 — curl -v 로 계층 읽기

아무 HTTPS 사이트에 curl -v를 실행하고, 출력을 네 덩어리로 나눠 표시한다: (1) DNS 해석과 TCP 연결, (2) TLS 핸드셰이크, (3) 내가 보낸 HTTP 요청, (4) 받은 응답.

검증: 각 덩어리의 시작 줄을 지목할 수 있는가. 그리고 존재하지 않는 도메인, 닫힌 포트, 자체 서명 인증서에 대해 각각 어느 덩어리에서 멈추는지 예측하고 확인했는가.
