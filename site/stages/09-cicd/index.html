Stage 09 · Delivery & Infrastructure

CI/CD (GitHub Actions / Jenkins)

빌드-테스트-배포 파이프라인, 아티팩트, 시크릿, 환경별 배포 전략.

예상 20시간 완료

이 단계를 끝내면

  • 커밋 하나로 테스트·빌드·배포가 이어지는 파이프라인을 만들 수 있다.

  • 시크릿을 저장소에 넣지 않고 파이프라인에 전달할 수 있다.
  • 배포를 한 번의 조작으로 되돌릴 수 있다.
  • Jenkins를 만나도 개념을 대응시켜 읽을 수 있다.

준비물

1. CI와 CD가 각각 무엇인가

무엇인가없으면
CI 지속적 통합커밋마다 자동으로 빌드·테스트"내 브랜치에선 되는데" 상태로 머지된다
CD 지속적 배포/전달통과한 것을 자동으로 배포배포가 사람의 기억과 손에 달린다

핵심은 자동화 자체가 아니라 피드백 속도다. 깨진 코드를 30초 만에 알면 고치는 데 5분이 걸리고, 일주일 뒤에 알면 하루가 걸린다. 그래서 파이프라인이 느려지면 사람들이 무시하기 시작하고, 무시되는 파이프라인은 없느니만 못하다. 빠르게 유지하는 것이 이 단계의 숨은 주제다.

2. 워크플로의 구조

# .github/workflows/ci.yml
name: CI

on:                          # 언제 도나
  pull_request:
  push:
    branches: [main]

jobs:                        # 무엇을 하나 (job끼리는 병렬, 서로 다른 머신)
  test:
    runs-on: ubuntu-latest
    steps:                   # step끼리는 순차, 같은 머신
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - run: pip install -r requirements.txt -r requirements-dev.txt
      - run: pytest -q
개념뜻
workflow파일 하나. .github/workflows/*.yml
job독립된 러너(가상 머신)에서 도는 작업 묶음. 기본은 병렬
stepjob 안의 한 단계. 순차 실행, 파일시스템 공유
uses남이 만든 액션을 가져다 쓴다
run셸 명령을 직접 실행한다

⚠ job이 다르면 파일이 공유되지 않는다

job마다 새 가상 머신이다. build job에서 만든 파일을 deploy job이 그냥 쓸 수 없다. 넘기려면 아티팩트로 업로드/다운로드하거나 (Stage 7처럼) 레지스트리에 이미지를 올려야 한다. 순서를 강제하려면 needs:를 쓴다.

3. CI — 테스트와 검사

Stage 5에서 만든 테스트가 여기서 값을 한다. CI는 그 테스트를 모든 커밋에 돌린다.

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install ruff
      - run: ruff check .

  shell:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: sudo apt-get install -y shellcheck      # Stage 4의 그 도구
      - run: shellcheck sysreport.sh

  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install -r requirements.txt -r requirements-dev.txt
      - run: pytest -q --junitxml=report.xml
      - uses: actions/upload-artifact@v4
        if: always()                    # 실패해도 결과는 남긴다
        with:
          name: test-report
          path: report.xml

if: always()가 중요하다. 기본적으로 앞 step이 실패하면 뒤는 건너뛰는데, 실패했을 때야말로 리포트가 필요하다.

💡 Stage 5의 "네트워크 없이 통과하는 테스트"가 여기서 값을 한다

CI 러너는 외부 API에 붙지 못할 수도 있고, 상대 서버가 느리면 파이프라인이 흔들린다. 가끔 실패하는 테스트(flaky test)는 사람들이 "또 그거네" 하며 무시하게 만들고, 그 순간 CI는 신뢰를 잃는다. monkeypatch로 외부 호출을 끊어 둔 것이 바로 이 때문이다.

4. 캐시와 매트릭스

의존성 설치가 매번 2분이면 하루에 수십 분을 버린다. Stage 7의 레이어 캐시와 같은 발상이다.

      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip                      # requirements.txt 해시로 캐시

      # 또는 직접
      - uses: actions/cache@v4
        with:
          path: ~/.cache/pip
          key: pip-${{ hashFiles('requirements.txt') }}
          restore-keys: pip-

key가 같으면 캐시를 그대로 쓰고, 다르면 restore-keys로 비슷한 것을 찾아 부분 재사용한다. requirements.txt가 안 바뀌면 설치를 건너뛴다.

  test:
    strategy:
      fail-fast: false                    # 하나 실패해도 나머지는 끝까지
      matrix:
        python: ["3.11", "3.12", "3.13"]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python }}
      - run: pytest -q

매트릭스는 조합마다 job을 하나씩 만들어 병렬로 돌린다. 지원 버전을 실제로 검증하는 가장 싼 방법이다.

5. 이미지 빌드와 태깅

Stage 8에서 "latest 태그 때문에 옛 버전이 돈다"는 사고를 봤다. 그 해결이 여기다 — 커밋마다 고유한 태그를 CI가 붙인다.

  build:
    needs: [test]                          # 테스트가 통과해야 빌드한다
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write                      # GHCR에 push하기 위해
    steps:
      - uses: actions/checkout@v4

      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - id: meta
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository }}
          tags: |
            type=sha,prefix=,format=short      # a1b2c3d
            type=ref,event=tag                 # v1.2.3
            type=raw,value=latest,enable={{is_default_branch}}

      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

type=sha가 핵심이다. 커밋 해시가 태그가 되므로 어떤 이미지가 어떤 코드인지 항상 추적된다. 장애가 났을 때 "지금 도는 게 어느 커밋인가"를 즉시 답할 수 있다.

cache-from/to: type=gha는 Docker 레이어 캐시를 Actions 캐시에 저장한다. Stage 7에서 배운 레이어 순서가 여기서 CI 시간으로 직결된다.

6. 시크릿과 OIDC

      - run: ./deploy.sh
        env:
          API_KEY: ${{ secrets.API_KEY }}        # Settings → Secrets에 등록

시크릿은 로그에서 자동으로 ***로 가려진다. 다만 완벽하지 않다 — base64로 인코딩하거나 문자열을 쪼개면 새어 나갈 수 있다.

⚠ pull_request 트리거에서는 시크릿이 없다

포크에서 온 PR에 시크릿을 주면, 누구나 워크플로를 고친 PR을 열어 시크릿을 빼갈 수 있다. 그래서 GitHub은 포크 PR에 시크릿을 주지 않는다. pull_request_target은 시크릿을 주지만 base 브랜치의 워크플로로 도는 위험한 트리거다 — 꼭 필요한 경우가 아니면 쓰지 말자.

장기 자격증명을 없애는 법 — OIDC

클라우드 배포에 액세스 키를 시크릿으로 넣는 것은 오래된 방식이다. 그 키는 만료되지 않고, 유출되면 그대로 쓰인다. OIDC는 실행할 때마다 단기 토큰을 발급받는다.

    permissions:
      id-token: write                       # OIDC 토큰 요청 권한
      contents: read
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/github-deploy
          aws-region: ap-northeast-2

클라우드 쪽에 "이 저장소의 이 브랜치에서 온 요청만 이 역할을 맡을 수 있다"고 신뢰 관계를 설정해 둔다. 저장소에 영구 키가 존재하지 않는다. Stage 12와 14에서 다시 다룬다.

권한은 최소로

permissions:
  contents: read                # 워크플로 전체의 기본값을 읽기로

jobs:
  build:
    permissions:
      contents: read
      packages: write           # 필요한 job에만 필요한 권한을

7. CD — 배포

  deploy:
    needs: [build]
    if: github.ref == 'refs/heads/main'      # main에서만
    runs-on: ubuntu-latest
    environment:
      name: production                       # 승인 게이트를 걸 수 있다
      url: https://weather.example.com
    steps:
      - uses: actions/checkout@v4

      - uses: azure/setup-kubectl@v4

      - run: |
          echo "${{ secrets.KUBECONFIG }}" > /tmp/kubeconfig
          export KUBECONFIG=/tmp/kubeconfig
          kubectl set image deployment/weatherboard \
            app=ghcr.io/${{ github.repository }}:${{ github.sha }}
          kubectl rollout status deployment/weatherboard --timeout=120s

rollout status가 중요하다. 이것이 없으면 배포 명령만 보내고 성공했다고 보고한다. Stage 8에서 본 대로 kubectl set image는 즉시 반환되고 실제 교체는 그 뒤에 일어난다. --timeout이 지나면 실패로 끝나 파이프라인이 빨갛게 된다 — 그래야 사람이 안다.

💡 environment로 승인 게이트 걸기

저장소 Settings → Environments에서 production에 리뷰어를 지정하면, 그 job은 사람이 승인할 때까지 멈춘다. "자동 배포"와 "자동 준비 + 수동 승인" 사이에서 고를 수 있다. 처음에는 승인을 걸어 두고, 신뢰가 쌓이면 푸는 것이 순서다.

GitOps라는 다른 방식

위 방식은 파이프라인이 클러스터에 밀어 넣는다(push). 그래서 CI에 클러스터 자격증명을 줘야 한다. GitOps는 반대로 클러스터 안의 에이전트(Argo CD, Flux)가 Git 저장소를 계속 지켜보다 당겨 간다(pull).

이 경우 CI는 매니페스트의 이미지 태그를 고쳐 커밋만 하면 된다. 클러스터 자격증명이 CI에 없어도 되고, Git이 곧 배포 상태의 기록이 된다. Stage 10의 "코드로 인프라"와 같은 철학이다.

8. 배포 전략과 되돌리기

전략방식대가
롤링조금씩 교체 (Stage 8의 기본)두 버전이 잠깐 공존한다
블루/그린새 환경을 통째로 띄우고 트래픽을 한 번에 전환자원이 두 배 필요
카나리일부(5%)에만 새 버전을 보내며 관찰트래픽 분배 도구와 지표가 필요

⚠ 두 버전이 공존할 수 있어야 한다

롤링과 카나리는 옛 버전과 새 버전이 동시에 돈다. DB 스키마를 바꾸는 배포에서 이것이 문제가 된다. 컬럼을 지우는 마이그레이션을 먼저 돌리면 아직 살아 있는 옛 Pod이 즉시 터진다. 그래서 스키마 변경은 추가 → 양쪽 호환 코드 배포 → 정리 순으로 여러 배포에 나눠 한다.

되돌리기

kubectl rollout undo deployment/weatherboard      # 가장 빠른 방법 (Stage 8)

혹은 Git에서 revert 커밋을 만들어 파이프라인을 다시 태운다(Stage 3). 느리지만 이력이 남는다. 급할 때는 rollout undo로 지혈하고, 그다음 revert로 정리하는 것이 실무의 순서다.

💡 되돌리기를 미리 연습해 둔다

장애 한복판에서 처음 해보는 명령을 치게 되면 안 된다. 평소에 일부러 배포를 실패시키고 되돌려 보는 훈련이, 실제로 시간을 줄여 준다. 이 단계의 과제 4가 그것이다.

9. Jenkins와의 대응

사내 시스템에서는 Jenkins를 여전히 많이 만난다. 개념은 대응된다.

개념GitHub ActionsJenkins
정의 파일.github/workflows/*.ymlJenkinsfile
단위job / stepstage / step
실행 주체GitHub 러너 (또는 self-hosted)에이전트/노드
재사용액션 (marketplace)플러그인, 공유 라이브러리
시크릿Repository/Environment secretsCredentials 플러그인
운영 부담없음 (관리형)서버를 직접 운영
 
// Jenkinsfile — 같은 파이프라인의 다른 문법
pipeline {
  agent any
  stages {
    stage('Test')   { steps { sh 'pytest -q' } }
    stage('Build')  { steps { sh 'docker build -t weatherboard:$GIT_COMMIT .' } }
    stage('Deploy') {
      when { branch 'main' }
      steps { sh 'kubectl set image deployment/weatherboard app=weatherboard:$GIT_COMMIT' }
    }
  }
}

가장 큰 차이는 Jenkins 자체가 운영 대상이라는 점이다. 서버, 플러그인 업데이트, 보안 패치가 전부 우리 몫이다. 그 대가로 제약 없는 자유를 얻는다.

자주 하는 실수

로컬에서는 되는데 CI에서만 실패한다

가장 흔한 CI 문제이자, 대개 환경 차이다. 넷 중 하나를 의심한다.

  1. 의존성 — 로컬에만 설치된 패키지. requirements.txt에 빠졌다
  2. 파일 — .gitignore된 파일에 의존한다 (CI는 깨끗한 클론이다)
  3. 순서 — 테스트가 실행 순서에 의존한다. pytest -p no:randomly 없이도 통과하는가
  4. 대소문자 — 로컬이 macOS(대소문자 무시)면 import Utils가 리눅스에서만 깨진다
# CI와 같은 환경을 로컬에서 재현
docker run --rm -v "$PWD:/w" -w /w python:3.12-slim sh -c \
  "pip install -r requirements.txt -r requirements-dev.txt && pytest -q"

Error: Resource not accessible by integration

# Error: Resource not accessible by integration

GITHUB_TOKEN의 권한이 부족한 것이다. 필요한 권한을 명시한다.

    permissions:
      contents: write        # 커밋/태그를 만들 때
      packages: write        # GHCR push
      pull-requests: write   # PR에 코멘트

저장소 Settings → Actions → Workflow permissions에서 기본값이 읽기 전용으로 설정되어 있을 수도 있다. 다만 기본을 넓히지 말고 job마다 필요한 것만 주는 편이 낫다.

시크릿이 비어 있다

${{ secrets.API_KEY }}가 빈 문자열로 나온다면 셋 중 하나다. (1) 포크에서 온 PR이다(시크릿이 주어지지 않는다), (2) 이름 오타, (3) Environment secret인데 job에 environment:를 안 적었다.

      - run: |
          if [ -z "${{ secrets.API_KEY }}" ]; then
            echo "::error::API_KEY가 비어 있다" >&2
            exit 1
          fi

비어 있는 채로 진행해 이상한 곳에서 실패하는 것보다, 일찍 명확히 실패하는 편이 낫다. Stage 4에서 배운 ${VAR:?}와 같은 발상이다.

파이프라인이 점점 느려진다

사람들이 무시하기 시작하는 시점이 온다. 순서대로 손본다.

  • 독립된 job으로 쪼개 병렬로 돌린다 (lint와 test는 서로를 기다릴 이유가 없다)
  • 의존성과 Docker 레이어를 캐시한다
  • PR에서는 빠른 검사만, 무거운 것(E2E)은 main에서만
  • paths: 필터로 관련 없는 변경에는 아예 안 돌게 한다
on:
  push:
    paths:
      - 'src/**'
      - 'requirements.txt'

배포는 성공했다는데 옛 버전이 돈다

Stage 8에서 본 문제다. latest 태그를 쓰면 노드가 캐시된 이미지를 쓴다. 그리고 kubectl set image는 같은 태그로는 아무 일도 하지 않는다 — 쿠버네티스가 보기에 원하는 상태가 이미 그것이기 때문이다. 커밋 SHA 태그를 쓰면 이 문제 자체가 사라진다.

직접 해보기

과제 1 — CI 파이프라인

weatherboard 저장소에 lint(ruff) · shellcheck · pytest 세 job을 병렬로 돌리는 워크플로를 만든다. 의존성 캐시를 켜고, 테스트 리포트를 if: always()로 업로드한다.

검증: PR을 열었을 때 세 체크가 모두 뜨는가. 일부러 lint 오류를 넣은 커밋에서 lint만 실패하고 나머지는 계속 도는가. 두 번째 실행에서 캐시가 적중해 시간이 줄었는가.

과제 2 — 이미지 빌드와 태깅

테스트 통과 후 이미지를 빌드해 GHCR에 push한다. 태그는 커밋 SHA로 하고, 기본 브랜치일 때만 latest도 함께 붙인다.

검증: 패키지 목록에서 SHA 태그를 확인할 수 있는가. docker pull ghcr.io/<user>/<repo>:<sha>가 되는가. 테스트를 일부러 실패시키면 빌드 job이 실행되지 않는가(needs).

과제 3 — 실패를 읽는 연습

이 과제가 이 단계의 핵심이다. 다음 넷을 각각 만들고, 로그의 어느 줄에서 원인을 알 수 있었는지 기록한다.

  1. 테스트 실패 — 단언을 깨뜨린다
  2. 의존성 누락 — requirements.txt에서 한 줄을 지운다
  3. 권한 부족 — permissions에서 packages: write를 뺀다
  4. 시크릿 누락 — 존재하지 않는 시크릿을 참조한다

검증: 네 경우의 에러 메시지가 서로 어떻게 다른가. 로그를 처음부터 읽지 않고 실패한 step만 펼쳐서 원인에 도달할 수 있는가.

과제 4 — 배포와 되돌리기

Stage 8의 클러스터에 배포하는 job을 추가한다(로컬 클러스터라면 kubectl 단계를 echo로 대신해도 좋다 — 흐름을 만드는 것이 목적이다). 그다음 깨진 버전을 배포하고 시간을 재면서 되돌린다.

검증: rollout status가 실패했을 때 파이프라인도 실패하는가. 되돌리는 데 몇 초가 걸렸는가. 그 절차를 저장소의 README나 RUNBOOK.md에 적어 뒀는가.

과제 5 — 파이프라인 시간 줄이기

과제 1–2의 파이프라인 총 실행 시간을 재고, 병렬화·캐시·경로 필터로 줄여 본다.

검증: 몇 초에서 몇 초가 됐는가. 어떤 변경이 가장 크게 기여했는가. 5분을 넘는 단계가 남아 있다면 왜인지 설명할 수 있는가.
