1. 세 개의 공간

Git이 어렵게 느껴지는 이유는 명령이 많아서가 아니라, 파일이 세 곳에 동시에 존재한다는 걸 모른 채 명령을 외우기 때문이다. 이 그림 하나가 나머지를 설명한다.

공간무엇인가여기로 보내는 명령
작업 디렉터리지금 편집기로 보고 있는 파일—
스테이징(index)다음 커밋에 넣기로 고른 변경git add
저장소(.git)커밋으로 확정된 이력git commit
 
git status              # 세 공간의 차이를 한눈에
git diff                # 작업 디렉터리 vs 스테이징 (아직 add 안 한 것)
git diff --staged       # 스테이징 vs 마지막 커밋 (add는 했고 commit 안 한 것)

💡 스테이징은 귀찮은 절차가 아니다

한 번에 여러 가지를 고쳤을 때, 그중 관련된 것만 골라 하나의 커밋으로 만들라고 있는 공간이다. git add -p를 쓰면 같은 파일 안에서도 조각(hunk) 단위로 골라 담을 수 있다. 이 한 명령이 커밋 품질을 가장 크게 바꾼다.

git add -p              # 조각마다 y/n으로 고른다
git add .               # 전부 (편하지만 관련 없는 변경이 섞이기 쉽다)
git restore --staged file.txt   # 스테이징에서 빼기 (변경은 유지)
git restore file.txt            # 작업 디렉터리 변경 버리기 — 되돌릴 수 없다

2. 커밋 — 무엇을 얼마나 담나

좋은 커밋은 하나의 논리적 변경을 담고, 그것만으로도 코드가 동작한다. "오전 작업"처럼 시간으로 자르지 말고 의미로 자른다.

git commit -m "Add disk usage section to sysreport"
git commit                       # 편집기가 열린다. 본문을 쓸 땐 이쪽
git commit --amend               # 직전 커밋 수정 (push 전에만!)

커밋 메시지

널리 쓰이는 형태는 이렇다. 첫 줄은 50자 내외의 요약, 빈 줄, 그리고 본문이다.

Fix disk report skipping tmpfs mounts

df -h lists tmpfs entries that always show 100% used, which made
the report look alarming on healthy machines. Filter them out with
-x tmpfs instead of post-processing the output.

첫 줄은 명령형으로 쓴다("Fix", "Add", "Remove"). "무엇을"이 아니라 "왜"를 본문에 쓴다 — 무엇을 바꿨는지는 diff가 이미 말해주지만, 왜 그랬는지는 사람만 남길 수 있다.

⚠ 비밀은 커밋하는 순간 영구적이다

API 키나 .env를 커밋했다가 다음 커밋에서 지워도 이력에는 그대로 남는다. 이미 push했다면 그 키는 유출된 것으로 간주하고 즉시 폐기·재발급해야 한다. 이력에서 지우는 것은 그다음 문제다. 이 주제는 Stage 14에서 스캔 도구와 함께 다시 다룬다.

cat > .gitignore <<'EOF'
.env
*.log
__pycache__/
node_modules/
EOF
git add .gitignore && git commit -m "Add gitignore"

.gitignore는 아직 추적되지 않는 파일에만 적용된다. 이미 커밋한 파일은 git rm --cached <파일>로 추적을 먼저 끊어야 한다.

3. 이력 읽기

git log --oneline -10                 # 최근 10개 요약
git log --oneline --graph --all       # 브랜치 갈라짐을 그림으로
git log -p sysreport.sh               # 이 파일이 어떻게 변해왔나
git log --author="이름" --since="1 week ago"

git show <커밋>                        # 이 커밋이 무엇을 바꿨나
git blame sysreport.sh                # 각 줄을 마지막으로 바꾼 커밋

git blame은 범인을 찾는 도구가 아니라 맥락을 찾는 도구다. "이 이상한 줄은 왜 있지?"의 답은 대개 그 줄을 넣은 커밋의 메시지에 있다.

git bisect start
git bisect bad                  # 지금은 고장났다
git bisect good v1.0            # 이 시점엔 멀쩡했다
# git이 중간 커밋으로 이동시킨다. 테스트하고 good/bad를 답한다
git bisect reset                # 끝나면 원위치

bisect는 이진 탐색으로 "어느 커밋이 망가뜨렸나"를 찾는다. 커밋이 1000개여도 10번만 확인하면 된다. 커밋을 작게 나눠야 하는 실용적인 이유가 이것이다.

4. 브랜치

브랜치는 무거운 복사본이 아니라 커밋을 가리키는 이름표다. 그래서 만드는 비용이 거의 0이고, 부담 없이 만들었다 지우는 것이 정상적인 사용법이다.

git switch -c feature/disk-alerts     # 만들면서 이동 (구버전: git checkout -b)
git switch main                       # 이동
git branch -v                         # 목록과 각자의 최신 커밋
git branch -d feature/disk-alerts     # 삭제 (머지된 것만)
git branch -D feature/disk-alerts     # 강제 삭제 — 머지 안 된 커밋이 사라진다

💡 switch와 restore

예전에는 git checkout이 브랜치 이동과 파일 복원을 둘 다 했다. 헷갈린다는 지적이 많아 git switch(브랜치)와 git restore(파일)로 갈라졌다. 오래된 문서는 아직 checkout을 쓰지만, 새 명령이 실수를 줄여준다.

5. 합치기 — merge와 rebase

둘 다 "내 브랜치에 다른 브랜치의 변경을 가져온다"는 같은 목적을 갖지만, 이력에 남기는 모양이 다르다.

mergerebase
이력 모양갈라졌다 합쳐진 그대로 보존일직선으로 펴짐
커밋 해시유지새로 만들어짐
안전한 곳어디서나나만 쓰는 브랜치
충돌 해결한 번커밋마다 반복될 수 있음
 
git switch feature/disk-alerts
git merge main        # main의 변경을 내 브랜치로 가져온다

# 또는
git rebase main       # 내 커밋들을 main 위에 다시 얹는다

⚠ 남이 쓰는 브랜치는 rebase하지 않는다

rebase는 커밋을 다시 만든다. 해시가 바뀌므로, 그 커밋을 이미 받아 간 사람의 저장소와 이력이 어긋난다. 그 상태에서 push --force하면 상대의 작업이 사라질 수 있다. 규칙 하나만 기억하자: 공유된 브랜치는 merge, 내 로컬 브랜치는 rebase.

내 브랜치를 정리할 때는 대화형 rebase가 유용하다.

git rebase -i HEAD~3     # 최근 3개 커밋을 정리 (squash로 합치기, reword로 메시지 수정)

push하기 전에 "오타 수정", "다시 수정" 같은 커밋을 하나로 합쳐 두면 리뷰어가 읽을 이력이 깔끔해진다. 이미 push한 커밋에는 하지 않는다.

6. 충돌 해결

충돌은 같은 파일의 같은 줄을 양쪽에서 다르게 고쳤을 때 일어난다. Git이 어느 쪽이 옳은지 판단할 수 없어 사람에게 넘기는 것이지, 무언가 고장난 게 아니다.

git merge main
# Auto-merging sysreport.sh
# CONFLICT (content): Merge conflict in sysreport.sh
# Automatic merge failed; fix conflicts and then commit the result.

git status              # 어떤 파일이 충돌했는지

충돌한 파일을 열면 이렇게 표시된다.

<<<<<<< HEAD
df -h --output=source,pcent
=======
df -h -x tmpfs
>>>>>>> main
  • <<<<<<< HEAD부터 =======까지 — 내 브랜치의 내용
  • =======부터 >>>>>>>까지 — 가져오는 브랜치의 내용

해결은 "둘 중 하나 고르기"가 아니다. 양쪽 의도를 이해하고 올바른 최종 코드를 쓰는 것이다. 위 예라면 두 의도(사용률 표시 + tmpfs 제외)를 다 살린 한 줄이 답일 수 있다. 표시 기호(<<<, ===, >>>)는 반드시 전부 지운다.

git add sysreport.sh          # 해결했다고 표시
git merge --continue          # (rebase 중이면 git rebase --continue)

git merge --abort             # 포기하고 충돌 전으로 되돌리기

💡 막혔을 때는 abort가 정답이다

충돌 해결 중 뭐가 뭔지 모르겠으면 --abort로 깨끗하게 원위치할 수 있다. Git에서 되돌릴 수 없는 상황은 생각보다 훨씬 적다. 겁내지 말고 실험하자.

7. 되돌리기

Git 명령 중 가장 헷갈리는 영역이다. 기준은 하나다 — 이미 push했는가.

상황명령이력은
아직 add 안 한 변경을 버리기git restore <파일>—
add한 것을 스테이징에서 빼기git restore --staged <파일>—
직전 커밋 메시지/내용 수정 (push 전)git commit --amend덮어씀
최근 커밋 취소, 변경은 남김 (push 전)git reset --soft HEAD~1지움
최근 커밋과 변경 모두 버리기 (push 전)git reset --hard HEAD~1지움
이미 push한 커밋 되돌리기git revert <커밋>보존 + 취소 커밋 추가

⚠ push한 것은 revert로 되돌린다

reset은 이력을 지운다. 이미 공유된 커밋에 쓰면 남의 저장소와 어긋나고, 되돌리려면 push --force가 필요해 상대의 작업을 날릴 수 있다. revert는 "이 커밋을 취소하는 새 커밋"을 만들기 때문에 안전하고, "언제 왜 되돌렸는지"까지 이력에 남는다.

실수했을 때의 안전망

git reflog
# a1b2c3d HEAD@{0}: reset: moving to HEAD~1
# e4f5g6h HEAD@{1}: commit: Add disk alerts        ← 날린 줄 알았던 커밋

git reset --hard e4f5g6h     # 되살리기

reflog는 HEAD가 거쳐 간 모든 위치를 기록한다. reset --hard로 날린 커밋도 보통 30일간은 여기 남아 있다. Git에서 진짜로 잃어버리는 것은 커밋하지 않은 변경뿐이다.

8. 원격과 PR

git remote -v                                 # 연결된 원격 저장소
git remote add origin git@github.com:<user>/<repo>.git

git push -u origin main       # -u는 추적 설정 (다음부터는 git push만)
git fetch origin              # 원격 상태만 받아온다 (내 파일은 그대로)
git pull                      # fetch + merge

💡 pull보다 fetch가 먼저다

pull은 받아오면서 바로 합친다. 무엇이 올지 모르는 상태에서 합치는 셈이다. git fetch 후 git log --oneline HEAD..origin/main으로 무엇이 올지 먼저 보고 합치는 습관이 사고를 줄인다.

PR 흐름

  1. git switch -c feature/<이름> — 브랜치를 판다
  2. 작업하고 의미 단위로 커밋한다
  3. git push -u origin feature/<이름>
  4. GitHub에서 PR을 연다. 왜 이 변경이 필요한지와 어떻게 확인했는지를 쓴다
  5. 리뷰를 받고 수정 커밋을 push한다 (PR은 자동으로 갱신된다)
  6. 머지하고 브랜치를 지운다

머지 방식은 세 가지다. Merge commit은 이력을 그대로 남기고, Squash는 PR의 모든 커밋을 하나로 합치며, Rebase는 일직선으로 얹는다. 팀마다 규칙이 다르니 저장소의 관례를 따른다. 혼자 하는 저장소라면 Squash가 이력을 읽기 쉽게 유지해 준다.

9. 브랜치 전략과 태그

전략모양맞는 곳
Trunk-basedmain 하나 + 짧은 수명의 브랜치자주 배포하는 팀. CI/CD와 궁합이 좋다
Git Flowmain/develop/release/hotfix버전을 찍어 배포하는 제품
GitHub Flowmain + 기능 브랜치 + PR대부분의 경우 여기서 시작하면 된다

브랜치가 오래 살수록 충돌이 커진다. 어떤 전략이든 브랜치를 짧게 유지하는 것이 가장 중요한 규칙이다. 이틀 안에 머지될 크기로 자르자.

태그와 릴리스

git tag -a v1.0.0 -m "First release"    # 주석 태그 (누가 언제 왜)
git push origin v1.0.0
git tag                                 # 목록
git describe --tags                     # 지금 커밋이 어느 태그 이후 몇 번째인가

태그는 "이 커밋이 배포된 버전"이라는 표식이다. 장애가 났을 때 "어느 버전부터 문제인가"를 답할 수 있게 해주고, Stage 9의 CI/CD에서 태그를 눌러 배포를 트리거하는 데 쓴다.

자주 하는 실수

Updates were rejected because the remote contains work you do not have

git push
# ! [rejected]        main -> main (fetch first)
# error: failed to push some refs to 'github.com:user/repo.git'

내가 마지막으로 받아온 뒤 누군가 원격에 커밋을 올렸다는 뜻이다. 정상적인 상황이고, 받아서 합친 뒤 다시 올리면 된다.

git pull        # 또는 git fetch 후 확인하고 git merge origin/main
git push

여기서 git push --force로 뚫으면 남의 커밋을 지우게 된다. 이 에러에 대한 답은 절대 force가 아니다.

detached HEAD 상태입니다

git checkout a1b2c3d
# You are in 'detached HEAD' state...

브랜치가 아니라 특정 커밋을 직접 가리키고 있는 상태다. 고장이 아니다. 여기서 커밋하면 어떤 브랜치에도 속하지 않아 나중에 찾기 어려워진다. 그냥 둘러본 것이면 git switch -로 돌아가고, 여기서 작업을 이어가고 싶으면 브랜치를 만들어 붙잡는다.

git switch -c fix/from-old-commit

.gitignore에 넣었는데 계속 올라간다

.gitignore는 아직 추적되지 않는 파일만 무시한다. 이미 한 번 커밋된 파일은 계속 추적된다. 추적을 끊어야 한다.

git rm --cached .env      # 파일은 남기고 추적만 중단
git commit -m "Stop tracking .env"

다만 이렇게 해도 과거 이력에는 그대로 남아 있다. 비밀이었다면 폐기·재발급이 먼저다.

줄바꿈 때문에 파일 전체가 바뀐 것으로 나온다

git diff
# 파일 전체가 변경된 것처럼 보인다 (실제로는 CRLF ↔ LF 차이)

윈도우(CRLF)와 리눅스(LF)의 줄바꿈이 다르기 때문이다. 저장소에 규칙을 박아 두면 끝난다.

cat > .gitattributes <<'EOF'
* text=auto eol=lf
*.sh text eol=lf
EOF

커밋을 되돌리려다 작업을 날렸다

git reset --hard는 커밋뿐 아니라 작업 디렉터리의 변경까지 지운다. 커밋된 것이라면 git reflog로 되찾을 수 있지만, 한 번도 커밋하지 않은 변경은 되찾을 수 없다. 위험한 명령을 치기 전에 커밋하거나 git stash로 치워 두자.

git stash                 # 지금 변경을 잠시 치워 둔다
git stash list
git stash pop             # 되돌려 놓기

직접 해보기

과제 1 — sysreport를 저장소에 넣기

GitHub에 저장소를 만들고, Stage 1의 sysreport.sh를 올린다. 단, 한 커밋에 다 넣지 말고 최소 세 개의 의미 있는 커밋으로 나눈다(예: 초기 스크립트 / .gitignore 추가 / README 추가).

검증: git log --oneline의 각 줄만 읽고도 무엇을 한 커밋인지 알 수 있는가. "update", "fix" 같은 메시지가 없는가.

과제 2 — 충돌을 일부러 만들고 해결하기

이 과제가 이 단계의 핵심이다. 충돌을 겪어보지 않으면 실전에서 당황한다.

git switch -c feature/a
sed -i '2i echo "=== A 버전 헤더 ==="' sysreport.sh
git commit -am "Add header (A)"

git switch main
sed -i '2i echo "=== B 버전 헤더 ==="' sysreport.sh
git commit -am "Add header (B)"

git merge feature/a       # 여기서 충돌한다

충돌 표시를 읽고, 양쪽 의도를 살린 최종 형태로 직접 고친 뒤 커밋한다.

검증: grep -c '<<<<<<<' sysreport.sh가 0이고 bash sysreport.sh가 정상 실행되는가.

과제 3 — 잘못 올린 커밋 되돌리기

일부러 잘못된 커밋(예: 스크립트를 깨뜨리는 변경)을 만들어 push한 뒤, revert로 되돌린다. 그다음 reset --hard로도 시도해 보고 무엇이 다른지 git log로 비교한다.

검증: revert 후 이력에 원래 커밋과 취소 커밋이 둘 다 남아 있는가. 왜 push된 커밋에는 reset이 아니라 revert를 써야 하는지 한 문장으로 답할 수 있는가.

과제 4 — PR 한 바퀴

브랜치를 만들어 sysreport.sh에 기능 하나를 더하고, PR을 연다. PR 본문에는 무엇을·왜·어떻게 확인했는지를 쓴다. 스스로 리뷰어가 되어 diff를 읽고, 고칠 점을 찾아 커밋을 하나 더 얹은 뒤 머지한다.

검증: 머지 후 git log --oneline --graph에서 브랜치가 갈라졌다 합쳐진 모양을 확인할 수 있는가. 로컬의 병합된 브랜치를 정리했는가(git branch -d).

과제 5 — reflog로 되살리기

git log --oneline -1          # 지울 커밋 확인
git reset --hard HEAD~1       # 날린다
git reflog                    # 찾는다
git reset --hard <해시>        # 되살린다

검증: 되살린 뒤 git log --oneline -1이 원래 커밋을 가리키는가. 이 안전망이 커밋된 것에만 적용된다는 점을 이해했는가.
