1. 스크립트의 뼈대

#!/usr/bin/env bash
# sysreport.sh — 서버 상태를 한 화면으로 요약한다.
set -euo pipefail

main() {
  echo "host: $(hostname)"
}

main "$@"

첫 줄의 #!(셔뱅)은 이 파일을 무엇으로 실행할지 커널에 알려준다. #!/bin/bash보다 #!/usr/bin/env bash가 낫다 — bash 위치가 시스템마다 다를 수 있는데 env가 PATH에서 찾아준다.

chmod +x sysreport.sh
./sysreport.sh            # 셔뱅대로 실행
bash sysreport.sh         # 셔뱅을 무시하고 bash로 실행

⚠ sh와 bash는 다르다

많은 시스템에서 /bin/sh는 bash가 아니라 dash다. 배열, [[ ]], local 같은 bash 문법이 sh script.sh로 실행하면 깨진다. 셔뱅에 bash라고 썼으면 실행도 bash로 하자.

2. 안전 장치 — set -euo pipefail

bash의 기본 동작은 초심자에게 위험하다. 실패해도 다음 줄을 계속 실행하고, 없는 변수를 빈 문자열로 취급한다. 이 한 줄이 그 둘을 막는다.

옵션기본 동작바뀌는 동작
-e명령이 실패해도 계속 진행실패하면 즉시 중단
-u정의 안 된 변수는 빈 문자열정의 안 된 변수를 쓰면 에러
-o pipefail파이프라인은 마지막 명령의 결과만 본다중간이 실패하면 전체가 실패

왜 필요한지는 이 예가 설명한다.

# set -u 가 없으면:
BACKUP_DIR=""            # 오타로 값이 안 들어갔다고 하자
rm -rf "$BACKUP_DIR"/*   # → rm -rf /*  ← 시스템이 날아간다

# set -e 가 없으면:
cd /nonexistent          # 실패하지만 그냥 넘어간다
rm -rf ./old             # 엉뚱한 디렉터리에서 실행된다

# pipefail 이 없으면:
cat missing.txt | wc -l  # cat은 실패했는데 종료 코드는 wc의 0

예외 처리

-e가 걸린 상태에서 "실패해도 괜찮은" 명령이 있다면 명시적으로 표시한다.

grep -q "pattern" file.txt || true      # 못 찾아도 계속 진행

if grep -q "pattern" file.txt; then     # 조건문 안에서는 -e가 발동하지 않는다
  echo "찾았다"
fi

count=$(grep -c "x" file.txt || echo 0) # 실패 시 기본값

-u를 쓰면서 "없을 수도 있는 변수"를 다룰 때는 기본값 문법을 쓴다.

LOG_DIR="${LOG_DIR:-/var/log}"        # 없거나 비었으면 /var/log
: "${API_KEY:?API_KEY 환경변수가 필요합니다}"   # 없으면 메시지와 함께 종료

3. 변수와 인용부호

셸 스크립트 버그의 가장 큰 원인 하나를 꼽으라면 인용부호다. 규칙은 단순하다 — 변수는 항상 큰따옴표로 감싼다.

file="my report.txt"

rm $file        # rm "my" "report.txt"  ← 두 파일을 지우려 한다
rm "$file"      # rm "my report.txt"    ← 의도대로
표기동작예
"$var"변수를 펼치되 분리하지 않음거의 항상 이것
'$var'펼치지 않음. 글자 그대로echo '$HOME' → $HOME
$var펼치고 공백으로 분리의도적으로 쪼갤 때만
"${arr[@]}"배열의 각 원소를 하나씩배열은 이 형태로만
 
name="world"
echo "hello $name"        # hello world
echo 'hello $name'        # hello $name
echo "오늘은 $(date +%F)"  # 명령 치환 — $(...)를 쓴다 (백틱은 옛 문법)

readonly CONFIG="/etc/app.conf"   # 바뀌면 안 되는 값
local tmp                          # 함수 안에서는 local을 붙인다

유용한 변수 조작

path="/var/log/app.log"
echo "${path##*/}"     # app.log      — 마지막 / 뒤 (basename)
echo "${path%/*}"      # /var/log     — 마지막 / 앞 (dirname)
echo "${path%.log}"    # /var/log/app — 뒤에서 .log 제거
echo "${#path}"        # 길이

echo "${name:-기본값}"  # name이 없으면 기본값
echo "${name^^}"       # 대문자로

4. 조건과 반복

if [[ -f "$file" ]]; then
  echo "파일이 있다"
elif [[ -d "$file" ]]; then
  echo "디렉터리다"
else
  echo "없다"
fi

💡 [[ ]] 를 쓰자

[ ]는 옛 문법이라 변수가 비면 문법 오류가 나는 등 함정이 많다. bash에서는 [[ ]]가 더 안전하고 &&, ||, 정규식 =~도 쓸 수 있다. 다만 sh 호환이 필요하면 [ ]를 써야 한다.

검사뜻
-f "$f" / -d "$f"일반 파일 / 디렉터리인가
-e "$f"존재하는가 (종류 무관)
-r / -w / -x읽기 / 쓰기 / 실행 가능한가
-z "$s" / -n "$s"비었는가 / 안 비었는가
"$a" == "$b"문자열 같은가
"$a" -eq "$b"숫자 같은가 (-lt -gt -le -ge -ne)

반복

for f in /var/log/*.log; do
  echo "처리: $f"
done

for i in {1..5}; do echo "$i"; done

while read -r line; do          # -r 없으면 백슬래시가 먹힌다
  echo "줄: $line"
done < input.txt

case "$1" in
  start) echo "시작" ;;
  stop)  echo "정지" ;;
  *)     echo "알 수 없는 명령: $1"; exit 1 ;;
esac

⚠ ls의 출력을 for로 돌리지 않는다

for f in $(ls *.log)는 공백이 든 파일명에서 깨진다. 글롭(for f in *.log)을 쓰거나, 재귀가 필요하면 find ... -print0과 read -d ''를 조합한다.

while IFS= read -r -d '' f; do
  echo "$f"
done < <(find /var/log -name '*.log' -print0)

5. 함수와 종료 코드

log() {
  printf '[%s] %s\n' "$(date +%H:%M:%S)" "$*" >&2
}

die() {
  log "ERROR: $*"
  exit 1
}

check_disk() {
  local threshold="${1:-90}"
  local used
  used=$(df --output=pcent / | tail -1 | tr -dc '0-9')
  (( used >= threshold )) && return 1
  return 0
}

if ! check_disk 80; then
  die "디스크 사용률이 80%를 넘었다"
fi

함수 안의 변수에는 local을 붙인다. 안 붙이면 전역이 되어, 다른 함수의 같은 이름 변수를 조용히 덮어쓴다.

💡 로그는 stderr로, 결과는 stdout으로

위 log 함수가 >&2로 stderr에 쓰는 이유다. 진행 메시지가 stdout에 섞이면, 이 스크립트의 출력을 다른 명령에 파이프로 넘길 때 쓰레기가 된다. stdout은 결과, stderr는 사람에게 하는 말로 나누자.

종료 코드

command
echo $?          # 직전 명령의 종료 코드. 0이 성공, 나머지는 실패

exit 0           # 성공
exit 1           # 일반적인 실패
exit 2           # 잘못된 사용법 (관례)

종료 코드는 스크립트가 자동화 도구와 말하는 유일한 방법이다. cron, CI, 다른 스크립트는 출력이 아니라 이 숫자를 본다. 실패했으면 반드시 0이 아닌 값으로 끝내야 한다.

6. 인자 다루기

echo "$0"     # 스크립트 이름
echo "$1"     # 첫 번째 인자
echo "$#"     # 인자 개수
echo "$@"     # 모든 인자 (항상 "$@"로 감싼다)

플래그가 필요해지면 while과 case로 파싱한다.

usage() {
  cat <<EOF
사용법: ${0##*/} [옵션]

  -t, --threshold N   디스크 경고 임계값 (기본 90)
  -q, --quiet         결과만 출력
  -h, --help          이 도움말
EOF
}

threshold=90
quiet=false

while [[ $# -gt 0 ]]; do
  case "$1" in
    -t|--threshold) threshold="$2"; shift 2 ;;
    -q|--quiet)     quiet=true; shift ;;
    -h|--help)      usage; exit 0 ;;
    --)             shift; break ;;
    -*)             usage >&2; die "알 수 없는 옵션: $1" ;;
    *)              break ;;
  esac
done

인자를 받는 옵션(-t)에서 값이 없으면 $2가 없어 set -u에 걸린다. 그것이 정확히 원하는 동작이다 — 조용히 넘어가는 것보다 낫다.

7. 정리와 trap

스크립트가 임시 파일을 만들었다면, 성공하든 실패하든 지워야 한다. trap이 그 일을 맡는다.

tmpdir=$(mktemp -d)
trap 'rm -rf "$tmpdir"' EXIT

# 여기서 무슨 일이 일어나든 (성공, 실패, Ctrl+C) tmpdir은 지워진다
echo "작업 중..." > "$tmpdir/work"

EXIT는 어떤 이유로 끝나든 발동한다. 시그널을 따로 잡고 싶으면 이렇게 쓴다.

trap 'echo "중단됨"; exit 130' INT TERM

⚠ 중간에 실패해도 시스템을 어중간하게 남기지 않는다

서비스를 멈추고 → 파일을 바꾸고 → 다시 시작하는 스크립트가 중간에 죽으면 서비스가 멈춘 채로 남는다. trap으로 "무슨 일이 있어도 서비스는 되살린다"를 보장하자. 이것이 set -e와 trap을 함께 쓰는 이유다.

restore() {
  systemctl is-active --quiet myapp || systemctl start myapp
}
trap restore EXIT

systemctl stop myapp
# ... 위험한 작업 ...
systemctl start myapp

동시 실행 막기

exec 9>/var/lock/sysreport.lock
flock -n 9 || die "이미 실행 중이다"

cron으로 5분마다 도는 스크립트가 10분 걸리면 두 개가 겹쳐 돈다. flock 두 줄로 막는다.

8. ShellCheck와 테스트

shellcheck sysreport.sh
# In sysreport.sh line 12:
# rm -rf $tmpdir
#        ^-----^ SC2086: Double quote to prevent globbing and word splitting.

ShellCheck는 위에서 설명한 함정을 대부분 자동으로 잡아낸다. 경고 코드(SC2086)를 검색하면 왜 문제인지 설명이 나온다. 경고 0개를 목표로 삼자 — 셸에서 경고는 대체로 진짜 버그다.

정말 의도한 것이라면 이유를 적고 예외 처리한다.

# shellcheck disable=SC2086  # 의도적으로 단어 분리를 이용한다
command $args

디버깅

bash -n script.sh      # 실행하지 않고 문법만 검사
bash -x script.sh      # 실행되는 명령을 하나씩 출력
set -x                 # 스크립트 일부만 추적하고 싶을 때
set +x                 # 추적 끄기

간단한 테스트

함수 단위로 잘라 두면 테스트가 쉬워진다. 별도 프레임워크 없이도 이 정도는 된다.

#!/usr/bin/env bash
set -euo pipefail
source ./sysreport.sh --source-only   # main을 실행하지 않고 함수만 읽기

fail=0
assert_eq() {
  if [[ "$1" != "$2" ]]; then
    echo "FAIL: expected '$2', got '$1'" >&2
    fail=1
  fi
}

assert_eq "$(to_mb 2048)" "2"
exit "$fail"

스크립트 끝의 main "$@"를 조건부로 만들면 source가 가능해진다.

[[ "${1:-}" == "--source-only" ]] || main "$@"

9. 주기 실행 — cron과 systemd timer

crontab -e
# 분 시 일 월 요일  명령
  */5 *  *  *  *   /usr/local/bin/sysreport.sh >> /var/log/sysreport.log 2>&1
  0   3  *  *  *   /usr/local/bin/backup.sh          # 매일 새벽 3시

⚠ cron의 환경은 내 셸과 다르다

cron은 최소한의 PATH만 갖고 실행한다. 터미널에서는 되던 스크립트가 cron에서 command not found로 죽는 가장 흔한 이유다. 스크립트 안에서 절대 경로를 쓰거나 맨 위에서 PATH를 명시하자. 출력도 반드시 리다이렉트해야 한다 — 안 그러면 메일로 쌓이거나 그냥 사라진다.

요즘은 systemd timer를 더 많이 쓴다. 로그가 저널로 모이고, 실패를 systemctl로 확인할 수 있으며, 놓친 실행을 따라잡을 수 있다.

# /etc/systemd/system/sysreport.service
[Unit]
Description=Server health report

[Service]
Type=oneshot
ExecStart=/usr/local/bin/sysreport.sh

# /etc/systemd/system/sysreport.timer
[Unit]
Description=Run sysreport every 5 minutes

[Timer]
OnCalendar=*:0/5
Persistent=true

[Install]
WantedBy=timers.target
sudo systemctl daemon-reload
sudo systemctl enable --now sysreport.timer
systemctl list-timers sysreport.timer
journalctl -u sysreport.service --since today

Stage 1에서 배운 daemon-reload가 여기서 또 나온다. 유닛 파일을 고쳤으면 항상 먼저다.

💡 셸을 그만둘 때

다음 중 하나라도 해당되면 파이썬으로 넘길 때다 — JSON/YAML을 파싱한다, 숫자 계산이 필요하다, 자료구조가 중첩된다, 에러 처리가 ||로 감당이 안 된다, 스크립트가 200줄을 넘는다. 셸은 명령을 이어 붙이는 데 최고고, 데이터를 다루는 데는 최악이다. Stage 5가 그 지점을 이어받는다.

자주 하는 실수

rm: cannot remove '/*': Permission denied — 혹은 더 나쁜 일

BUILD_DIR=""          # 값이 안 들어갔다
rm -rf "$BUILD_DIR"/  # rm -rf /

set -u는 정의되지 않은 변수만 잡는다. 위처럼 정의됐지만 빈 변수는 통과한다. 위험한 경로를 다룰 때는 직접 검사한다.

[[ -n "${BUILD_DIR:-}" ]] || die "BUILD_DIR이 비었다"
[[ "$BUILD_DIR" != "/" ]] || die "루트는 안 된다"
rm -rf "${BUILD_DIR:?}"/*     # :? 는 비었으면 에러를 내고 멈춘다

syntax error near unexpected token `then'

if [ "$x" = "1" ]then     # ; 가 없다
# script.sh: line 3: syntax error near unexpected token `then'

if와 then 사이에는 ;나 줄바꿈이 필요하다. [ 뒤와 ] 앞의 공백도 필수다 — [는 문법이 아니라 명령이기 때문이다. bash -n이나 ShellCheck가 이런 것을 실행 전에 잡아준다.

unary operator expected

if [ $answer = "yes" ]; then   # answer가 비어 있으면 → [ = "yes" ]
# script.sh: line 5: [: =: unary operator expected

변수를 인용하지 않아서 빈 값이 사라진 것이다. [[ ]]를 쓰거나 "$answer"로 감싸면 해결된다. ShellCheck의 SC2086이 바로 이 경고다.

cron에서만 command not found

*/5 * * * * /usr/local/bin/sysreport.sh
# /usr/local/bin/sysreport.sh: line 8: jq: command not found

터미널의 PATH에는 있고 cron의 PATH에는 없는 것이다. 실제 cron 환경을 재현해서 확인할 수 있다.

env -i /bin/bash --noprofile --norc ./sysreport.sh   # 환경변수 없이 실행해 본다

고치는 방법은 스크립트 위쪽에 PATH를 명시하는 것이다.

export PATH="/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"

파이프라인이 실패했는데 성공으로 나온다

curl -s https://example.com/data.json | jq '.items'
echo $?    # jq가 성공했으면 0 — curl이 실패했어도

set -o pipefail이 없으면 파이프라인의 종료 코드는 마지막 명령의 것이다. 중간의 curl이 실패해도 모른다. 개별 결과가 필요하면 PIPESTATUS를 본다.

curl -s ... | jq ...
echo "${PIPESTATUS[@]}"   # 각 단계의 종료 코드 (예: "6 0")

직접 해보기

과제 1 — sysreport.sh 완성

Stage 1의 초안을 이 단계의 규격으로 다시 쓴다. 요구 사항은 다음과 같다.

  • set -euo pipefail과 #!/usr/bin/env bash
  • --threshold N, --quiet, --help 옵션 처리
  • 로그는 stderr, 결과는 stdout
  • 디스크 사용률이 임계값을 넘으면 종료 코드 1
  • 임시 파일을 쓴다면 trap ... EXIT으로 정리
  • 모든 변수 참조에 인용부호

검증: shellcheck sysreport.sh가 경고 0개인가. ./sysreport.sh --threshold 1이 종료 코드 1을, --threshold 100이 0을 내는가 (echo $?로 확인). --help가 0으로 끝나는가.

과제 2 — 실패해도 상태를 남기지 않는 스크립트

Nginx를 멈추고 → 설정 파일을 바꾸고 → 다시 시작하는 스크립트를 쓴다. 설정 검사(nginx -t)가 실패하면 원래 설정으로 되돌리고 서비스를 반드시 살린다.

검증: 일부러 잘못된 설정을 넣고 실행했을 때, 스크립트가 0이 아닌 코드로 끝나면서도 systemctl is-active nginx가 active이고 설정 파일이 원본으로 돌아와 있는가.

과제 3 — 로그 정리 스크립트

지정한 디렉터리에서 N일보다 오래된 .log 파일을 찾아 압축하고, M일보다 오래된 것은 지우는 스크립트를 쓴다. 기본 동작은 dry-run으로 하고, --apply를 줘야 실제로 지우게 한다.

검증: 공백이 든 파일명(touch "my log.log")에서도 깨지지 않는가. --apply 없이 실행했을 때 아무 파일도 사라지지 않는가.

과제 4 — 타이머로 돌리기

완성한 sysreport.sh를 systemd timer로 5분마다 실행하고, journalctl로 실행 기록을 확인한다. 그다음 스크립트가 실패하도록 만들어 실패가 어떻게 보이는지 본다.

검증: systemctl list-timers에 다음 실행 시각이 보이는가. journalctl -u sysreport.service에서 성공과 실패를 구분할 수 있는가.
