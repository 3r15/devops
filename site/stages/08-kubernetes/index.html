1. 왜 오케스트레이터가 필요한가

Stage 7의 Compose로 weatherboard는 잘 돈다. 하지만 서버 한 대다. 다음 질문들에 Compose는 답하지 못한다.

  • 그 서버가 죽으면? — 서비스도 죽는다
  • 트래픽이 3배가 되면? — 손으로 컨테이너를 더 띄우고 로드밸런서를 고친다
  • 컨테이너가 메모리를 다 먹고 죽으면? — 누군가 알아채고 재시작해야 한다
  • 새 버전을 배포하다 실패하면? — 손으로 되돌린다

쿠버네티스의 답은 선언적 상태다. "무엇을 어떻게 해라"가 아니라 "이런 상태이길 원한다"를 적으면, 컨트롤러가 현재 상태를 계속 그쪽으로 몰고 간다. Pod이 죽으면 다시 만들고, 노드가 죽으면 다른 노드에 띄운다. 사람이 개입하지 않는다.

⚠ 쿠버네티스가 항상 정답은 아니다

서비스 하나에 트래픽이 적다면 Compose 한 대나 관리형 PaaS가 더 낫다. 쿠버네티스는 그 자체로 운영해야 할 시스템이고, 배워야 할 것과 잘못될 수 있는 것이 많다. 여러 서비스를 여러 팀이 운영하고, 무중단과 자동 복구가 요구사항일 때 값을 한다.

3. Pod

Pod은 배포의 최소 단위다. 컨테이너 하나 이상을 묶으며, 같은 Pod의 컨테이너는 네트워크(같은 IP, localhost로 통신)와 볼륨을 공유한다.

# pod.yaml — 배우기 위한 것. 실제로는 Deployment를 쓴다
apiVersion: v1
kind: Pod
metadata:
  name: weatherboard
  labels:
    app: weatherboard
spec:
  containers:
    - name: app
      image: weatherboard:0.1
      ports:
        - containerPort: 8000
      env:
        - name: HOST
          value: "0.0.0.0"
kind load docker-image weatherboard:0.1 --name wb   # kind에 로컬 이미지 넣기
kubectl apply -f pod.yaml
kubectl get pods
kubectl port-forward pod/weatherboard 8000:8000    # 로컬에서 접근
curl localhost:8000/healthz

⚠ Pod을 직접 만들지 않는다

Pod은 일회용이다. 죽으면 그것으로 끝이고 아무도 되살리지 않는다. 노드가 재부팅되면 사라진다. 실제로는 항상 Deployment 같은 상위 리소스를 만들고, 그것이 Pod을 관리하게 한다. 위 예제는 개념을 보기 위한 것이다.

4. Deployment

Deployment는 "이 Pod을 N개 유지해라"를 선언한다. 죽으면 다시 만들고, 이미지를 바꾸면 순차적으로 교체한다.

# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: weatherboard
spec:
  replicas: 3
  selector:
    matchLabels:
      app: weatherboard          # 이 라벨을 가진 Pod을 내 것으로 여긴다
  template:                       # ↓ 여기부터가 Pod의 설계도
    metadata:
      labels:
        app: weatherboard         # selector와 반드시 일치해야 한다
    spec:
      containers:
        - name: app
          image: weatherboard:0.1
          ports:
            - containerPort: 8000
          env:
            - name: HOST
              value: "0.0.0.0"
kubectl apply -f deployment.yaml
kubectl get deploy,rs,pods            # Deployment → ReplicaSet → Pod 계층
kubectl delete pod <pod-이름>          # 하나 지워 보자
kubectl get pods                       # 몇 초 안에 새 Pod이 올라온다

Pod을 지워도 몇 초 안에 새것이 뜬다. 이것이 "선언적 상태"가 눈에 보이는 순간이다. Deployment는 ReplicaSet을 만들고, ReplicaSet이 Pod 개수를 지킨다.

💡 selector와 template의 라벨은 일치해야 한다

selector.matchLabels와 template.metadata.labels가 다르면 Deployment는 자기가 만든 Pod을 자기 것으로 인식하지 못하고 계속 새로 만든다. YAML을 처음 쓸 때 가장 많이 하는 실수다.

5. Service — 안정적인 주소

Pod은 죽고 다시 뜨며 그때마다 IP가 바뀐다. 그러니 Pod IP로 통신할 수 없다. Service가 변하지 않는 이름과 IP를 제공하고, 뒤의 Pod들에게 분배한다. Stage 7에서 컨테이너 이름으로 통신하던 것의 확장판이다.

# service.yaml
apiVersion: v1
kind: Service
metadata:
  name: weatherboard
spec:
  selector:
    app: weatherboard        # 이 라벨을 가진 Pod들에게 보낸다
  ports:
    - port: 80               # Service의 포트
      targetPort: 8000       # Pod의 포트
  type: ClusterIP            # 기본값 — 클러스터 안에서만
kubectl apply -f service.yaml
kubectl get svc
kubectl get endpoints weatherboard    # 실제로 어떤 Pod IP들이 붙었나 ← 중요

# 클러스터 안에서 이름으로 접근되는지 확인
kubectl run tmp --rm -it --image=curlimages/curl:8.10.1 --restart=Never -- \
  curl -s http://weatherboard/healthz
type범위쓸 때
ClusterIP클러스터 내부만기본. 대부분의 서비스
NodePort각 노드의 고정 포트개발·테스트
LoadBalancer클라우드 LB 생성클라우드에서 외부 노출

💡 endpoints가 비어 있으면 selector가 틀린 것이다

Service가 있는데 접속이 안 될 때 첫 번째로 볼 곳은 kubectl get endpoints다. 비어 있다면 selector가 어떤 Pod과도 맞지 않는 것이다 — 라벨 오타이거나, Pod이 아직 Ready가 아니거나(프로브 실패), 아예 안 떠 있는 것이다.

6. Ingress — 밖에서 들어오기

Ingress는 클러스터 밖의 HTTP 트래픽을 안의 Service로 보낸다. 호스트명과 경로로 라우팅하고 TLS를 종료한다 — Stage 6의 Nginx가 하던 일이다. 실제로 가장 흔한 Ingress 컨트롤러 구현이 Nginx다.

# kind에 Ingress 컨트롤러 설치
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/main/deploy/static/provider/kind/deploy.yaml
kubectl wait --namespace ingress-nginx --for=condition=ready pod \
  --selector=app.kubernetes.io/component=controller --timeout=90s
# ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: weatherboard
spec:
  ingressClassName: nginx
  rules:
    - host: weather.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: weatherboard
                port:
                  number: 80

⚠ Ingress 오브젝트만으로는 아무 일도 안 일어난다

Ingress는 규칙 선언일 뿐이고, 그것을 실행할 Ingress 컨트롤러가 클러스터에 설치되어 있어야 한다. 컨트롤러 없이 Ingress를 만들면 조용히 아무 일도 없다. kubectl get ingress의 ADDRESS가 비어 있으면 이것을 의심하자.

7. ConfigMap과 Secret

Stage 7에서 이미지에 설정을 넣지 않는 이유를 배웠다. 쿠버네티스는 그 설정을 별도 오브젝트로 관리한다.

apiVersion: v1
kind: ConfigMap
metadata:
  name: weatherboard-config
data:
  HOST: "0.0.0.0"
  PORT: "8000"
  LOG_LEVEL: "INFO"
---
apiVersion: v1
kind: Secret
metadata:
  name: weatherboard-secret
type: Opaque
stringData:                    # base64를 직접 안 해도 된다
  WEATHER_API_KEY: "실제-키-값"
      containers:
        - name: app
          image: weatherboard:0.1
          envFrom:
            - configMapRef:
                name: weatherboard-config
            - secretRef:
                name: weatherboard-secret

⚠ Secret은 암호화가 아니라 base64다

기본 설정의 Secret은 etcd에 base64 인코딩으로 저장된다. 인코딩은 암호화가 아니다. 누구든 kubectl get secret -o yaml과 base64 -d로 읽을 수 있다. 진짜 보호에는 (1) RBAC으로 접근 제한, (2) etcd 저장 시 암호화, (3) 외부 시크릿 관리 도구(Vault, 클라우드 Secret Manager)가 필요하다. 그리고 Secret YAML을 Git에 커밋하지 않는다 — Stage 3과 14의 주제다.

8. 프로브와 리소스

Stage 5에서 만들고 Stage 7에서 처음 쓴 /healthz가 여기서 본격적으로 쓰인다.

          livenessProbe:              # 실패하면 컨테이너를 재시작한다
            httpGet:
              path: /healthz
              port: 8000
            initialDelaySeconds: 10
            periodSeconds: 20
            failureThreshold: 3

          readinessProbe:             # 실패하면 Service에서 뺀다 (재시작은 안 함)
            httpGet:
              path: /healthz
              port: 8000
            initialDelaySeconds: 3
            periodSeconds: 5

          startupProbe:               # 느리게 시작하는 앱에 시간을 준다
            httpGet:
              path: /healthz
              port: 8000
            failureThreshold: 30
            periodSeconds: 2
프로브실패하면묻는 질문
liveness컨테이너 재시작"살아 있나? 죽었으면 다시 띄워라"
readiness트래픽 차단 (Service에서 제외)"지금 요청을 받을 수 있나?"
startup컨테이너 재시작"아직 뜨는 중인가?" (뜨면 나머지 프로브 시작)

⚠ liveness 프로브를 잘못 만들면 재시작 루프가 된다

DB 연결까지 확인하는 liveness 프로브를 만들면, DB가 잠깐 느려질 때 멀쩡한 앱 전체가 재시작된다. 그러면 부하가 더 커지고 다시 실패하는 악순환이 된다. liveness는 프로세스 자체가 살아 있는가만 보고(가볍게), 의존성 확인은 readiness에 둔다.

리소스 요청과 제한

          resources:
            requests:            # 스케줄러가 자리를 잡을 때 쓰는 값
              cpu: 50m           # 0.05 코어
              memory: 64Mi
            limits:              # 넘으면 제재
              cpu: 500m
              memory: 256Mi

requests는 "최소 이만큼 필요하다"로 어느 노드에 놓을지를 결정한다. limits는 상한선이다. 둘의 차이가 중요하다.

  • CPU 초과 → 쓰로틀링. 느려지지만 죽지는 않는다
  • 메모리 초과 → OOMKilled. 즉시 죽는다

requests를 안 적으면 스케줄러가 노드 용량을 잘못 판단해 한 노드에 몰아넣고, 결국 다 함께 느려진다. 둘 다 적는 것이 기본이다.

9. 업데이트, 롤백, 디버깅

kubectl set image deployment/weatherboard app=weatherboard:0.2
kubectl rollout status deployment/weatherboard      # 진행 상황을 지켜본다
kubectl rollout history deployment/weatherboard
kubectl rollout undo deployment/weatherboard        # 직전 버전으로
kubectl rollout undo deployment/weatherboard --to-revision=2

기본 전략은 RollingUpdate다. 새 Pod을 띄우고 Ready가 되면 옛 Pod을 내린다. readiness 프로브가 제대로 있어야 무중단이 성립한다는 뜻이다 — 프로브가 없으면 쿠버네티스는 컨테이너가 시작된 즉시 트래픽을 보내고, 아직 준비 안 된 Pod이 502를 낸다.

  strategy:
    rollingUpdate:
      maxSurge: 1              # 원하는 개수보다 몇 개 더 띄울 수 있나
      maxUnavailable: 0        # 몇 개까지 없어도 되나 (0이면 완전 무중단)

디버깅 순서

Stage 2의 장애 분류처럼, 여기도 순서가 있다.

kubectl get pods                          # 1. 상태가 무엇인가
kubectl describe pod <이름>                # 2. 맨 아래 Events를 본다 ← 가장 중요
kubectl logs <이름>                        # 3. 애플리케이션이 뭐라고 하나
kubectl logs <이름> --previous            # 4. 재시작 전 로그 (CrashLoopBackOff일 때)
kubectl exec -it <이름> -- sh              # 5. 안에서 확인
kubectl get events --sort-by=.lastTimestamp | tail -20

describe의 Events 섹션이 답의 8할이다. 이미지를 못 받았는지, 스케줄할 노드가 없는지, 프로브가 실패했는지가 전부 여기 한 줄로 적혀 있다.

Helm 맛보기

YAML이 늘어나면 환경별로 값만 다른 파일을 여럿 복사하게 된다. Helm은 템플릿과 값을 분리해 그 중복을 없앤다.

helm repo add bitnami https://charts.bitnami.com/bitnami
helm install my-redis bitnami/redis --set auth.enabled=false
helm list
helm upgrade my-redis bitnami/redis --set replica.replicaCount=2
helm uninstall my-redis

지금은 "남의 차트를 설치해 쓰는" 수준으로 충분하다. 직접 차트를 만드는 것은 운영할 서비스가 여럿이 된 뒤의 이야기다.

자주 하는 실수

ImagePullBackOff — 로컬에서 빌드한 이미지인데

kubectl describe pod weatherboard-xxx | tail -5
# Failed to pull image "weatherboard:0.1": rpc error: ...
# failed to resolve reference "docker.io/library/weatherboard:0.1"

클러스터의 노드는 내 로컬 Docker 이미지를 볼 수 없다. 레지스트리에서 받으려 하다 실패한 것이다. 로컬 클러스터에서는 이미지를 직접 넣어 준다.

kind load docker-image weatherboard:0.1 --name wb      # kind
minikube image load weatherboard:0.1                   # minikube

imagePullPolicy: Always가 기본인 태그(latest)를 쓰면 넣어 줘도 다시 받으려 한다. 버전 태그를 쓰거나 IfNotPresent로 명시하자.

Service에 붙었는데 응답이 없다

kubectl get endpoints weatherboard
# NAME           ENDPOINTS   AGE
# weatherboard   <none>      2m        ← 비어 있다

Service의 selector와 맞는 Ready 상태의 Pod이 없는 것이다. 셋 중 하나다.

  1. 라벨이 안 맞는다 — kubectl get pods --show-labels로 대조
  2. Pod이 Ready가 아니다 — readiness 프로브 실패
  3. targetPort가 컨테이너의 실제 포트와 다르다

CrashLoopBackOff

kubectl logs weatherboard-xxx --previous
# ModuleNotFoundError: No module named 'requests'

컨테이너가 떴다가 죽기를 반복한다. --previous가 핵심이다 — 지금 컨테이너는 방금 시작해서 로그가 없고, 죽은 직전 컨테이너의 로그에 원인이 있다. 로그가 비어 있다면 describe의 Events와 종료 코드를 본다 (137이면 OOMKilled, 1이면 애플리케이션 에러).

배포했는데 옛 버전이 돈다

latest 태그를 쓰고 있고 노드에 이미 그 이미지가 있으면, 쿠버네티스는 받아오지 않고 캐시된 것을 쓴다. Stage 7의 "latest를 쓰지 말라"가 여기서 실제 사고가 된다. 배포마다 다른 태그를 쓰는 것이 정답이고, 그 태그를 CI가 자동으로 붙이는 것이 Stage 9의 주제다.

Pod이 Pending에서 안 넘어간다

kubectl describe pod weatherboard-xxx | grep -A5 Events
# Warning  FailedScheduling  0/1 nodes are available:
# 1 Insufficient cpu.

requests로 요구한 자원을 줄 노드가 없는 것이다. 요청을 줄이거나 노드를 늘린다. 로컬 클러스터에서 requests를 크게 잡으면 자주 만나게 된다.

직접 해보기

과제 1 — weatherboard를 클러스터에 올리기

Deployment(replicas 3) + Service + Ingress를 만들어 배포한다. 프로브와 리소스 요청/제한을 모두 넣는다.

검증: kubectl get pods가 3/3 Running이고 모두 1/1 Ready인가. kubectl get endpoints에 IP 3개가 있는가. Ingress를 통해 curl -H "Host: weather.local" localhost/healthz가 응답하는가.

과제 2 — 죽여도 살아나는지 확인

이 과제가 이 단계의 핵심이다.

# 터미널 1 — 계속 요청을 보낸다
while true; do curl -s -o /dev/null -w "%{http_code} " -H "Host: weather.local" localhost/healthz; sleep 0.3; done

# 터미널 2 — Pod을 하나씩 죽인다
kubectl delete pod <pod-1>
kubectl get pods -w

검증: 터미널 1에서 200이 끊기지 않는가. 몇 초 만에 새 Pod이 Ready가 되는가. kubectl get events --sort-by=.lastTimestamp로 삭제부터 재생성, Ready까지의 과정을 순서대로 설명할 수 있는가.

과제 3 — 무중단 롤링 업데이트와 롤백

이미지를 0.2로 바꿔 롤아웃하면서 과제 2의 요청 루프를 계속 돌린다. 그다음 존재하지 않는 태그로 바꿔 실패를 만들고 롤백한다.

검증: 정상 업데이트에서 200이 한 번도 끊기지 않는가 (끊긴다면 maxUnavailable과 readiness 프로브를 확인). 실패한 롤아웃에서 옛 Pod이 살아 있어 서비스가 유지되는가. rollout undo 후 정상으로 돌아오는가.

과제 4 — 설정을 밖에서 주입하기

ConfigMap과 Secret을 만들어 envFrom으로 주입한다. ConfigMap의 값을 바꾸고 kubectl rollout restart로 반영한다.

검증: kubectl exec <pod> -- env | grep LOG_LEVEL로 주입을 확인했는가. ConfigMap만 바꾸고 재시작하지 않으면 왜 반영되지 않는지 설명할 수 있는가.

과제 5 — 고장을 만들고 진단하기

다음 넷을 일부러 만들고, 각각 describe/logs의 어느 줄에서 원인을 확인했는지 기록한다.

  1. 존재하지 않는 이미지 태그 → ImagePullBackOff
  2. Service의 selector 라벨 오타 → endpoints 비어 있음
  3. 프로브 경로를 /nope로 → Running이지만 0/1 Ready
  4. limits.memory: 8Mi → OOMKilled

검증: 네 경우 모두 로그가 아니라 describe의 Events에서 먼저 단서를 찾았는가. 각각의 STATUS 문자열만 보고 어디를 볼지 즉시 말할 수 있는가.
