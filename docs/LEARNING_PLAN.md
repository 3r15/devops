# DevOps 학습 계획

이 문서는 두 가지를 동시에 정의합니다.

1. **학습자의 계획** — 14단계를 어떤 순서로, 무엇을 기준으로 끝냈다고 볼 것인가
2. **집필 계획** — 이 사이트의 각 단계 페이지를 어떤 순서와 형식으로 채울 것인가

커리큘럼의 구조(파트·단계·예상 시간·공개 상태)는 [`data/curriculum.json`](../data/curriculum.json)이
단일 진실 공급원입니다. 이 문서는 그 위에 "왜"와 "어떻게"를 얹습니다.

---

## 1. 대상과 전제

- **대상**: 터미널을 열어본 적은 있지만 서버를 혼자 운영해본 적은 없는 사람
- **전제 지식**: 없음. 파일과 폴더 개념, 그리고 영어 문서를 읽을 인내심 정도
- **필요 환경**: 리눅스를 돌릴 수 있는 무언가 (VM, WSL2, 클라우드 프리티어 인스턴스 중 하나)
- **끝났을 때**: 작은 웹 서비스를 직접 컨테이너로 만들고, 파이프라인으로 배포하고,
  메트릭과 로그로 상태를 보고, 장애가 났을 때 어디부터 볼지 아는 상태

## 2. 학습 원칙

1. **손이 먼저다.** 개념 설명은 명령어를 이해하기 위한 최소한만. 각 단계의 절반 이상은 실습.
2. **한 단계 = 하나의 산출물.** 읽은 것으로는 끝나지 않는다. 매 단계는 남는 물건
   (스크립트, Dockerfile, 매니페스트, 파이프라인 정의)으로 끝난다.
3. **앞 단계 위에 쌓는다.** Stage 7의 컨테이너는 Stage 6에서 세운 웹 서버를 담고,
   Stage 9의 파이프라인은 Stage 7의 이미지를 배포한다. 예제는 하나의 가상 서비스를 계속 키운다.
4. **틀리는 법도 배운다.** 각 단계에 "자주 하는 실수" 절을 둔다. 에러 메시지를 먼저 보여주고
   그것을 읽는 법을 가르친다.
5. **검증 가능한 완료 기준.** "이해했다"가 아니라 "이 명령이 이 출력을 내면 통과"로 적는다.

### 관통 예제 — `weatherboard`

전 단계를 관통하는 하나의 예제 서비스를 둡니다. 아주 작은 HTTP 서비스 하나(날씨 API를
조회해 페이지를 그려주는 것)를 Stage 5에서 만들고, 이후 단계에서 계속 감쌉니다.

| 단계 | `weatherboard`에 일어나는 일 |
| --- | --- |
| 5 | 파이썬으로 서비스 자체를 작성 |
| 6 | Nginx 리버스 프록시 뒤에 배치하고 TLS 적용 |
| 7 | 컨테이너 이미지로 패키징, Compose로 의존 서비스와 함께 실행 |
| 8 | 쿠버네티스에 Deployment/Service/Ingress로 배포 |
| 9 | 커밋하면 빌드·테스트·배포되는 파이프라인 연결 |
| 10–12 | 인프라를 Terraform으로 정의하고 클라우드에 올림, Ansible로 구성 관리 |
| 13 | 메트릭·로그·대시보드·알럿 부착 |
| 14 | 시크릿 정리, 이미지 스캔, 파이프라인에 보안 게이트 추가 |

## 4. 단계별 계획

각 단계는 **학습 목표 / 다루는 것 / 산출물 / 완료 기준** 네 항목으로 정의합니다.
아래는 요약이며, 상세 내용은 해당 단계 페이지가 공개될 때 그 페이지에 담깁니다.

### Part 1 — 기반 다지기

**Stage 1. Linux (24h)**
- 목표: 서버에 SSH로 들어가 로그를 찾고, 권한을 고치고, 서비스를 재시작할 수 있다
- 다루는 것: 파일시스템 구조, 경로, 파일 조작, 텍스트 처리(grep/sed/awk), 권한과 소유권,
  프로세스와 시그널, 패키지 관리, systemd, 로그, 디스크/메모리 확인, SSH
- 산출물: 서버 상태를 한 번에 요약해주는 `sysreport.sh` 초안
- 완료 기준: 낯선 리눅스 서버에서 "왜 디스크가 찼는지", "왜 서비스가 죽었는지"를
  man 페이지만 보고 15분 안에 좁힐 수 있다

**Stage 2. Networking Fundamentals (16h)**
- 목표: "안 돼요"를 계층으로 쪼개서 어디가 끊겼는지 말할 수 있다
- 다루는 것: OSI/TCP-IP, IP·서브넷·CIDR, 라우팅, 포트, TCP 핸드셰이크, DNS 조회 흐름,
  HTTP/HTTPS와 TLS 핸드셰이크, NAT, 방화벽(iptables/nftables, 보안 그룹)
- 산출물: `dig`/`curl -v`/`ss`/`tcpdump`로 만든 장애 분류 플로차트
- 완료 기준: 접속 실패 상황에서 DNS·라우팅·방화벽·애플리케이션 중 어디 문제인지 근거를 대고 특정

**Stage 3. Git + GitHub (14h)**
- 목표: 혼자가 아니라 팀에서 쓰는 방식으로 이력을 관리한다
- 다루는 것: 3-tree 모델, 브랜치, merge vs rebase, 충돌 해결, `.gitignore`, 태그와 릴리스,
  PR 리뷰 흐름, 되돌리기(revert/reset/reflog), 브랜치 전략(trunk-based vs git-flow)
- 산출물: 충돌을 일부러 만들고 해결한 실습 저장소 + PR 하나
- 완료 기준: 잘못된 커밋을 이력을 망가뜨리지 않고 되돌리고, 그 방법을 고른 이유를 설명

### Part 2 — 자동화의 언어

**Stage 4. Shell Scripting (16h)**
- 목표: 매번 치던 명령 묶음을 안전하게 재실행 가능한 스크립트로 만든다
- 다루는 것: 파이프와 리다이렉션, 변수·인용부호, 조건/반복, 함수, 종료 코드,
  `set -euo pipefail`, trap, 인자 파싱, cron
- 산출물: Stage 1의 `sysreport.sh`를 인자·에러 처리·로깅을 갖춘 형태로 완성
- 완료 기준: ShellCheck 경고 0개, 중간에 실패해도 시스템을 어중간한 상태로 남기지 않음

**Stage 5. Python (Basics) (20h)**
- 목표: 셸로는 버거운 자동화를 파이썬으로 넘긴다
- 다루는 것: 자료형과 자료구조, 함수/모듈, 예외, 파일 IO, `subprocess`, `requests`,
  JSON/YAML 처리, 가상환경과 의존성, `argparse`, `pytest` 기초
- 산출물: `weatherboard` 서비스 v0 (HTTP 서버 + 외부 API 호출 + 테스트)
- 완료 기준: 저장소를 클론한 사람이 README만 보고 실행하고 테스트를 통과시킬 수 있음

### Part 3 — 서비스와 컨테이너

**Stage 6. Web Servers (14h)**
- 목표: 애플리케이션 앞단을 직접 세운다
- 다루는 것: Nginx 설정 구조, 가상 호스트, 리버스 프록시, 정적 자원, 캐시 헤더,
  TLS 인증서(Let's Encrypt), 로드밸런싱, 액세스/에러 로그, Apache와의 차이
- 산출물: `weatherboard` 앞에 붙는 Nginx 설정 + HTTPS 적용
- 완료 기준: 502/504가 났을 때 애플리케이션 문제인지 프록시 설정 문제인지 로그로 구분

**Stage 7. Docker (20h)**
- 목표: "제 컴퓨터에선 되는데요"를 없앤다
- 다루는 것: 이미지와 레이어, Dockerfile, 캐시 최적화, 멀티스테이지 빌드, 볼륨,
  네트워크, 환경변수와 시크릿, `docker compose`, 이미지 크기와 베이스 이미지 선택
- 산출물: `weatherboard`의 멀티스테이지 Dockerfile + Nginx까지 포함한 compose 파일
- 완료 기준: 이미지 200MB 이하, 코드만 바꿨을 때 재빌드가 캐시를 타고 수 초 안에 끝남

**Stage 8. Kubernetes (32h)**
- 목표: 컨테이너 여러 개를 사람이 아니라 시스템이 돌보게 한다
- 다루는 것: 클러스터 구조, Pod/ReplicaSet/Deployment, Service, Ingress,
  ConfigMap/Secret, 리소스 요청과 제한, 프로브, 롤링 업데이트와 롤백,
  네임스페이스, `kubectl` 디버깅, Helm 맛보기
- 산출물: `weatherboard`의 k8s 매니페스트 일습 (kind 또는 minikube에서 동작)
- 완료 기준: 파드를 강제로 죽여도 서비스 중단 없이 복구되고, 그 과정을 이벤트 로그로 설명

### Part 4 — 배포와 인프라

**Stage 9. CI/CD (20h)**
- 목표: 손으로 배포하는 일을 없앤다
- 다루는 것: 파이프라인 단계 설계, GitHub Actions 워크플로 문법, 매트릭스 빌드,
  캐시, 아티팩트, 시크릿과 OIDC, 환경별 배포와 승인, Jenkins와의 개념 대응
- 산출물: 푸시 → 테스트 → 이미지 빌드/푸시 → 배포까지 이어지는 워크플로
- 완료 기준: 실패한 파이프라인 로그만 보고 원인을 특정하고, 배포를 한 번의 되돌리기로 취소

**Stage 10. Terraform (20h)**
- 목표: 인프라를 클릭이 아니라 리뷰 가능한 코드로 만든다
- 다루는 것: HCL 문법, provider, resource/data, 변수와 출력, state와 원격 백엔드,
  모듈, `plan`/`apply` 워크플로, 드리프트, `import`, 상태 잠금
- 산출물: `weatherboard`가 올라갈 네트워크·컴퓨트 정의 모듈
- 완료 기준: 전부 destroy한 뒤 apply 한 번으로 동일 환경이 되살아남

**Stage 11. Ansible (14h)**
- 목표: 서버 안쪽 구성을 재현 가능하게 만든다
- 다루는 것: 인벤토리, 애드혹 명령, 플레이북, 변수와 템플릿(Jinja2), 롤,
  멱등성, 핸들러, `ansible-vault`
- 산출물: 빈 서버를 `weatherboard` 실행 가능 상태로 만드는 플레이북
- 완료 기준: 두 번 연속 실행했을 때 두 번째는 changed=0

**Stage 12. Cloud Platforms (28h)**
- 목표: 남의 데이터센터를 내 것처럼 쓴다
- 다루는 것: IAM과 최소 권한, 리전/가용영역, VPC·서브넷·보안그룹, 컴퓨트(EC2 등),
  오브젝트 스토리지, 매니지드 DB, 로드밸런서, 매니지드 쿠버네티스, 비용 구조와 예산 알럿
- 산출물: Terraform으로 정의한 실제 클라우드 환경 + 비용 알럿
- 완료 기준: 월 예상 비용을 항목별로 설명하고, 쓰지 않는 자원을 찾아 정리

### Part 5 — 운영과 보안

**Stage 13. Monitoring & Logging (20h)**
- 목표: 사용자보다 먼저 안다
- 다루는 것: 메트릭·로그·트레이스의 차이, Prometheus 데이터 모델과 PromQL,
  exporter, Grafana 대시보드, 알럿 룰과 알럿 피로, 로그 수집 파이프라인(ELK),
  SLI/SLO 기초
- 산출물: `weatherboard`의 대시보드 1장 + 의미 있는 알럿 3개
- 완료 기준: 인위적으로 장애를 넣었을 때 알럿이 울리고, 대시보드만으로 원인 후보를 좁힘

**Stage 14. Security (DevSecOps Basics) (18h)**
- 목표: 보안을 마지막에 붙이는 검사가 아니라 파이프라인의 일부로 만든다
- 다루는 것: 최소 권한 원칙, 시크릿 관리(저장소에 넣지 않기, vault류),
  의존성/이미지 취약점 스캔, SAST 기초, 컨테이너 하드닝, 공급망 보안(SBOM, 서명),
  파이프라인 보안 게이트, 로그에서의 민감정보
- 산출물: 취약점 스캔과 시크릿 스캔이 붙은 파이프라인
- 완료 기준: 일부러 심은 취약 의존성과 커밋된 키가 머지 전에 차단됨

1. **히어로** — 단계 번호, 제목, 한 줄 요약, 예상 시간, 상태 배지
2. **이 단계를 끝내면** — 검증 가능한 학습 목표 3–5개
3. **준비물** — 필요한 환경과 앞 단계 산출물
4. **목차**
5. **본문** — 개념 → 명령/코드 → 확인 방법 순의 절 5–9개
6. **자주 하는 실수** — 에러 메시지와 원인, 최소 3개
7. **직접 해보기** — 정답이 아니라 검증 방법이 붙은 실습 과제 2–4개
8. **체크리스트** — 브라우저에 진행률이 저장되는 완료 기준
9. **더 읽을거리** — 공식 문서 위주 3–6개
10. **페이저** — 이전/다음 단계

### 작업 흐름

```bash
# 1. 커리큘럼 상태 갱신 (planned → wip → done)
$EDITOR data/curriculum.json

# 2. 파생 페이지 재생성 (단계 본문은 건드리지 않음)
python3 tools/scaffold.py

# 3. 본문 작성
$EDITOR site/stages/01-linux/index.html

# 4. 검사 — CI와 동일
python3 tools/scaffold.py --check
python3 tools/check_links.py

# 5. 로컬 확인
python3 -m http.server 8000 --directory site
```

## 6. 진행 상태 관리

- **단계 공개 상태**는 `data/curriculum.json`의 `status` 필드가 유일한 기록입니다
  (`planned` → `wip` → `done`). 메인·파트 페이지의 배지와 "공개된 단계 N개"는 여기서 나옵니다.
- **학습자 개인 진행률**은 각 단계 체크리스트가 브라우저 `localStorage`에 저장합니다.
  서버로 가지 않으므로 기기 간 공유되지 않습니다.
- **집필 진행률**은 이 문서 5절의 릴리스 표에서 관리합니다.
